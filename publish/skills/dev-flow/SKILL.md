# dev-flow

作業の進め方の既定。PJ と利用者の指示ファイル（CLAUDE.md など）に規定があればそちらが優先する。このスキルは発動したときだけ読まれ、常に効く指示ファイルとは違う。全作業で守らせたい項目は、利用者の CLAUDE.md に写すことを勧める。

## 事実の扱い

- **状態・中身・値を書く前に、それを決める一次情報を今のコンテキストで開く**。対象について書かれたもの（自分の記録・成果物の前の版・メモ・依頼文）は対象そのものではない。デプロイの挙動は実際の設定で、受け取ったファイルの中身はそのファイルで決める
- **調べられることは調べてから提示する**。「未確認」のまま提示しない。調べられなかったものだけ、何を開けなかったかを添えて書く
- **主張が依存する層を全部開く**。表の種別・計算規則は数式・定義・非表示要素の層にあり、レコードは全フィールドを1件取ってスキーマを確認する。既定の取得範囲（親メッセージだけ・既定フィールドだけ）で「無い」と結論しない
- **相手に聞く前・「先方待ち」と書く前に、自分側を確認する**
- **対外に出す下書き・帳票は、事実を述べる各文と案件固有の各フィールドに出所を並記して提示する**（送る本文には書かない）。出所を書けない文は外す
- 測った数値は、報告や判断に使う前に、何がその値の上限を決めているかと、別のもの（エラー・キャッシュ・実行されなかったコード・ばらつき）を測っていないかを確認する。報告には試行回数とばらつきを添える
- 曜日は暗算せず `date` で求める
- 外部ライブラリ・SDK・ランタイム・外部サービスの挙動に依存する変更は、着手前に公式ドキュメントで仕様を確認する。テストで検出できない設定値を新しく使うときは実機で1回試してから採用する
- 過去の指摘・レビュー履歴を根拠にするときは、スレッドの決着まで読む
- 要件・仕様が明示する挙動を変える／実装しない決定は、原文の該当箇所を引用してから下し、差分を1行で記録する
- 「全件」「全期間」と言われた走査に、絞り込み・サンプリング・件数上限を自分の判断で加えない

## 進め方の既定

- **判断は中長期の最適で決める**。今回の工数、差分の大きさ、既存機構に収まるかどうかは理由にしない。中長期の最適とは、今の要件を将来の再作成が少ない形で満たすことで、使う予定の無い拡張点や抽象化を追加することではない
- **新しく作る前に、作らずに済むか → 既存の仕組み（PJ の helper・既存のスクリプト）→ 標準ライブラリやプラットフォームの機能 → 導入済みの依存、の順に探し、どれでも対応できないときだけ新しく書く**。頼まれていない機能・オプションは追加せず、追加しなかったものを報告に1行で書く。呼び出し元・テスト・設定など変更が届くべき箇所は全部修正する。信頼境界の検証・データ損失を防ぐエラー処理・セキュリティ・アクセシビリティは削らない
- 同じ前提に立った修正や試行が2回続けて同じ確認で失敗したら、次を試す前にその前提を1文で書き出し、前提が偽なら結果が変わる観察を1つして確認する
- 同じ手順の編集や確認を何か所にも当てるときは、手で繰り返さずスクリプトにして実行する
- ユーザーに手作業を頼む前、「できない」と答える前に、自分でできる手段を探す。人にしかできない操作（ログイン・承認・物理作業）だけを、具体的な手順にして頼む
- **既存の規約に合わせる**。PJ のテンプレート・設定値・採番・書式・コード構成から外れるならユーザーに確認する。踏襲するのは形だけで、既存の成果物に含まれる案件固有の値は当該案件の一次情報で決める
- 品質チェック・副作用の大きいコマンドは、PJ の CLAUDE.md が規定するコマンドで実行する
- **変更は自分で動かして確認する**。lint・typecheck・test の通過は挙動の保証にならないので、変更した機能をローカルで起動し、変えた操作を実際に通す。画面が変わる変更は変更後の画面のスクリーンショットを撮る。確認できなかった範囲は理由と一緒に報告する
- 自分の作業の後片付けは、確認せずに済ませる。対象は、自分が作った検証用のデータ・一時ファイル、マージ済みの worktree とブランチ（`git branch -d`）。未マージ・未 push のコミットを含むものは削除せずに報告する
- 依頼に含まれない別の作業（依頼外の相手への連絡、関連する別課題の修正、頼まれていないテストや CI 設定の追加）は提案に留める

## 確認が必要なもの

ここに挙げたもの以外は、確認を挟まずに進める。

- **確認必須カテゴリ**: 日程 / 金額・数量の確定 / 事実関係の正誤の判断 / 対外コミュニケーションの内容 / スコープの縮小・除外・先送り（「別 PR で」を含む）/ レビュー指摘など他者由来の機構拡大（ラウンドをまたいだ累積で見る）/ 依頼に含まれない付随作業の追加
- **外に出る作用**: push・PR 作成・投稿・対外送信・main への直コミット（許容したリポジトリを除く）は、可否を問う質問への肯定か、その作用を名指しした指示があるときだけ行う。範囲を狭める発話（「〜だけでいい」）や提示を求める発話（「〜を出して」）は承認に数えない。承認を得て出した PR のブランチへ、CI の修正やレビュー対応のコミットを push するのは、その承認に含まれる
- ユーザー裁定は、下された案件にだけ使う。別の案件の同種の判断は改めて確認する
- **質問のしかた**: 質問の前に、背景・判断材料・各選択肢の trade-off を地の文で説明する。推奨を1つ選んで先頭に置き、その理由を先に書く

「任せる」「自律で」と言われても、次は緩めない。

- 事実の一次確認と、確認必須カテゴリの確認
- 破壊的な git 操作（`git push --force`・`git reset --hard`・`git branch -D`）は実行前に確認する
- 破壊的なデータ操作（DB・バケットの削除、大量 DELETE）は、確認に加えて、実行前に復旧手段（バックアップ・エクスポート）を用意する
- シークレットは環境変数かファイルで渡し、チャット出力・コマンドライン引数に平文で書かない
- 作業フロー（Phase 0-5）の対象タスクでは、計画の承認なしに実装へ入らない。不可逆な変更を含む計画は外部レビューを通してから入る
- 外部サービスの挙動を確認するために作る一時オブジェクトは、運用中の環境・本番の名前空間に作らない

## 作業フロー（Phase 0-5）

次のどちらかに当たったら Phase 0-5 で進める。当たらなければそのまま着手する。

- ユーザーが「大規模」「複数日」「段階的に」「計画を立てて」などの語を使った
- 実装方針が既存コード・仕様の調査結果で分岐し、調査前に変更箇所を名指しできない

Phase: 0 準備（メモリディレクトリ）→ 1 調査 → 2 計画 → 3 実装 → 4 品質確認 → 5 完了報告。当たったら着手前に `context/workflow-rules.md` を Read する。

- 計画の既定値は PJ の運用実績から取る。ユーザーが過去に覆した判断は、覆された側を既定にする
- **外部レビュー**は、別ベンダーの LLM で行う（手順は `context/agent-cli-guide.md`）。対象は、不可逆な変更（認証・認可・secret・migration・データ削除・対外公開）を含む計画と実装、設計文書、人に共有する長文、ユーザーが求めたもの。自分がレビュアーとして呼ばれた側なら、自分で完遂する
- **完了報告**には、確認した操作と結果（スクリーンショットを含む）、手動で確認してほしい画面・操作・期待結果、自律で決めたこと、ブランチ名、片付けたもの、残課題、実行した検証とその検証が担保しない範囲を書く。lint や CI の通過を内容の品質の担保として書かない
- 問題の原因を報告する前に、自分の直前の操作が原因でないかをログ・差分で確認する

## メモリ・issue ディレクトリ

- ワークフローメモリは `${MEMORY_DIR}/memory/YYMMDD_<context_name>/`、issue は `${MEMORY_DIR}/issues/`。MEMORY_DIR は PJ ルートからの相対パスで、未定義なら `.local/`（gitignore に追加する）。各ファイルの形式は `context/memory-file-formats.md`
- 同じタスクの進行中のディレクトリがあれば再利用する。Phase 0 で絶対パスを確定して 05_log.md の冒頭に書き、worktree に移ってもその絶対パスで読み書きする
- 記録から引き継ぐのは経緯であって状態ではない。自分の記録が持つ外部の状態（済・未済・所在・待ち）は書いた時点の観測なので、それを前提に報告や作業をする前に対象を開き直す。書く側は状態の欄に時点と開いたものを添える

## コミット・PR

- コミットは意味のまとまりごとにこまめに作る。チーム開発のリポジトリでは作業ブランチを使う
- PR は既定で1本にし、分けるのは次のどれかに当たるときだけにする: 先にマージ・デプロイしないと後続が動かない / レビュアーかリポジトリが違う / 差分が大きすぎ、分けた各 PR が単独でレビューと動作確認ができる / ユーザーの指示
- push・PR 作成・レビュー対応の後は、CI の結果と conflict の有無を自分で確認してから報告する
- 変更で CLAUDE.md・README の記述が古くなるなら、同じ変更で修正する

## 文章とスキル

- 人に宛てる文（チャット・メール・PR の本文とコメント・共有する計画書や報告書）を作るなら、提示・投稿の前に `/writing-prose` を実行する
- プロダクションコードの差分を作るなら `/writing-code` を実行する
- 委譲先・外部 CLI が作った文章やコードは、全文を読み、既存の記述との矛盾を確認してから採用する

## バックグラウンドプロセス

- 自分が起動した長時間プロセス（テストランナー・dev サーバ・watch）は、そのターン内で終了を確認する
- 背景で動かすコマンドは出力をファイルに書き、`| tail` などのパイプを付けない（終端がバッファして進み具合が見えなくなる）。前景の実行がタイムアウトで背景に回ったら異常として調べる
- 終了しないことが正常なプロセスは、起動と kill を同じスクリプトに書く。タスク完了時に自分由来の残留プロセスを掃除する
