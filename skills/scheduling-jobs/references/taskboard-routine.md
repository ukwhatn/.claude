# taskboard の定期起動で巡回を作る

目次: 作るもの / プロンプト / 手順書 / 状態ファイル / 登録 / Gotchas

各回は taskboard の daemon が herdr の tab を作り、エージェントを起こしてプロンプトを送る。前回の会話は残らない。ユーザーはその場にいない。

## 作るもの

ジョブのディレクトリを、定期起動の `cwd` の下に `.<ジョブ名>/` で作る（このマシンの実値を含むので `~/.claude` には置かない）。

| ファイル | 中身 | 誰が書くか |
|---|---|---|
| `RUNBOOK.md` | 毎回の手順の真実源 | 人（手順を変えるときはここを編集する） |
| `ROUTINE.md` | 定期起動の登録内容（名前・規則・agent・引数・常設タスク・プロンプトの全文） | 人 |
| `state.json` | 回をまたいで引き継ぐ状態 | 各回 |
| `log/YYYY-MM.md` | 1回1行の実行記録 | 各回 |
| 秘密情報のファイル（例: `notify.curl`） | Webhook URL 等。権限 600 | 人 |

単純な作業（1〜3文で言い切れて、状態を引き継がない）なら手順書と状態ファイルは要らない。プロンプトに直接書き、`ROUTINE.md` だけ残す。

## プロンプト

プロンプトは手順書を読ませる短い入口にする。手順をプロンプトに書くと、変えるたびに `schedule_update` が要り、登録の実体と手順書が食い違う。次の順で書く:

1. `<ジョブのディレクトリ>/RUNBOOK.md を読み、そこに書かれた手順で1巡だけ実行してください。`
2. 前提: 無人実行であること、前回の記憶が無く引き継ぐ状態は `state.json` だけであること
3. やることの要約（手順書の Step の見出しを1行ずつ）
4. **手順書が読めなくても守る絶対条件**: 書き込んでよい範囲、外部サービスへの書き込みの禁止、使ってはいけない tool（`ask_user`・`review_request`・`doc_publish`・`session_start`・`session_prompt`・`schedule_*`。答える人がいない・自分を増やすため）、`task_create` は `link_session: false`
5. 手順書が読めなかったときの動作: 何も変えず、通知を1通だけ送って終わる（`curl -K <秘密情報のファイル>` の1行を書いておく）
6. 出力: 最後に1〜3行の結果だけ

## 手順書（RUNBOOK.md）の章立て

| 章 | 書くこと |
|---|---|
| 実行前提 | 各回は独立したセッション、回は飛ばされうる（スリープ・daemon 停止・重なりの skip）、cwd、権限確認なしで動くので安全は禁止事項で守ること |
| 固定値 | 状態ファイル・ログ・秘密情報のファイルのパス、対象のアカウント・チャンネル・リポジトリ。**対象外にしたものと理由**も書く（各回が範囲を広げないように） |
| Step 0: 起動チェック | `date` で現在時刻を取る、`state.json` を読む（無ければスキーマの初期値）、必要な MCP が繋がっているかを確かめ、無ければ通知して終わる。前回成功時刻から処理範囲を決める |
| Step 1〜: 収集・判定・適用 | ソースごとの取り方と、何をしたら何をするかの判定表 |
| 通知 | 通知する条件。**前回の通知と同じ内容なら送らない**（毎回同じ通知が来ると読まれなくなる） |
| 記録 | `state.json` の更新規則と、ログに書く1行の形式 |
| エラーの扱い | 状況ごとの動作の表（認証切れ・tool が無い・コマンドの失敗・連続失敗） |
| 禁止事項 | プロンプトの絶対条件の詳細版 |
| 1回の実行の上限 | 実行時間の目安と、ソースごとの件数の上限。超えたら打ち切って通知に書く |
| state.json スキーマ | 初期値と各キーの意味 |

## 状態ファイル（state.json）

```json
{
  "version": 1,
  "last_run_at": null,
  "last_success_at": null,
  "consecutive_failures": 0,
  "cursors": {},
  "seen": {},
  "last_notification": null
}
```

- **`last_success_at` は全ソースが成功した回だけ進める**。一部が失敗した回に進めると、失敗したソースの分を取りこぼす。失敗したソースの `cursors` も据え置く
- `seen` は処理済みのもののキー（URL 等）と判断。古いものを消す日数を決めておく（無限に増えて各回の読み込みが重くなる）
- `last_notification` は送った回だけ更新する。送らなかった回に上書きすると、「前回と同じなら送らない」の比較の基準がずれる
- 連続失敗の回数が閾値（例: 3）を超えたら通知に書く

## 登録

/taskboard スキルの手順で `schedule_create` を呼ぶ。

| 引数 | 値 |
|---|---|
| `name` | ジョブ名 |
| `cwd` | ジョブのディレクトリの親 |
| `cron` / `interval_minutes` | cron はマシンのローカル時刻。間隔は5分以上 |
| `agent` / `agent_args` | `claude` と `["--dangerously-skip-permissions", "--model", "<モデル>", "--effort", "<effort>"]`。無人なので、権限の確認を出すと誰も答えずに止まる |
| `overlap` | `skip`（同じ状態ファイルを2回分が同時に書かないように） |
| `new_task: true` + `board` か `task_id` | 常設タスクに結ぶ。結ばないと各回のセッションがボードから辿れない |
| `prompt` | 上の「プロンプト」 |

登録したら `schedule_list` の内容を `ROUTINE.md` に写す。

## Gotchas

- `task_create` を既定のまま呼ぶと、その回のセッションが起票した全タスクに結ばれ、各カードに無関係のセッションが並ぶ。`link_session: false` を必ず渡す
- 巡回はボード全体を触るので、/taskboard の「自分のセッションに紐づくタスクだけを動かす」を適用できない。代わりに手順書で「列は前進だけ」「終端の列（完了・見送り）へは自分の判断で動かさず通知して待つ」と決める
- 試運転（`schedule_run`）は重なりの設定を見ない。前の回が動いている最中に起こすと、2回分が同時に状態ファイルを書く
