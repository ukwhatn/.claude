# {{JOB_NAME}} RUNBOOK

taskboard の定期起動 `{{SCHEDULE_NAME}}`（`{{CRON}}`）が毎回の実行で従う手順書。
定期起動のプロンプトはこのファイルを読ませるだけの短い入口になっている。手順を変えるときはこのファイルを編集する。登録内容は `ROUTINE.md`。

## 実行前提

- **各実行は独立したセッション**。前回の会話は残らない。引き継ぐ状態は `state.json` だけ
- **実行は飛ばされうる**（Mac のスリープ・daemon の停止・前回がまだ動いている回の skip）。taskboard の定期起動は止まっていた間の回をさかのぼらない。だから「前回成功した時刻から今まで」を処理して取りこぼしを回収する
- cwd は `{{CWD}}`
- 起動は `--dangerously-skip-permissions`。tool は確認なしで動く。安全は「禁止事項」を守ることで担保する
- 各回のセッションは常設タスク `{{STANDING_TASK}}` に結ばれる（定期起動の設定）。このタスクの列・作業項目は巡回から動かさない
- **`timeout` / `gtimeout` コマンドは macOS の標準に無い**。使わない（入っていると思って使うと、そのコマンドが失敗して処理が飛ぶ）

## taskboard スキルとの関係

/taskboard スキルは「自律的に動かしてよいのは自分のセッションに紐づくタスクだけ」と定めている。**この巡回はボード全体の維持が役割なので、その制約は適用しない。** 代わりに「列は前進だけ・終端の列は通知して指示を待つ」で安全側に倒す。作業項目（`work_*`）は他のタスクのものを触らない。

それ以外の規定（列は案件の列の説明に従う、列 id をハードコードしない、重複は URL で判定する、PR の状態による前進は daemon に任せて手で追わない）はすべて従う。

**`task_create` には必ず `link_session: false` を渡す。** 既定（true）のままだと、巡回のセッションが起票した全タスクに結ばれ、各カードに無関係のセッションが並ぶ。

## Step 0: 起動チェック

1. `date -Iseconds` で現在時刻を取る（システムプロンプトの日付を推測で使わない）
2. `state.json` を読む。無ければ「state.json スキーマ」の初期値で作る
3. `board_overview` を呼ぶ。tool が無い・エラーなら通知して終了する（「■ エラー」に `taskboard: MCP 未接続` か `taskboard: daemon 停止（launchctl kickstart -k gui/$UID/uk.whatn.taskboardd）`）
4. ソースが使う MCP が繋がっているかを確かめる。繋がっていないソースは Step 1 でスキップし、`errors[]` に積む
5. `since` を決める:
   - `state.last_success_at` があればそれ
   - 無ければ **初回モード**（2-3）
6. ボードの state を作業コピーに落とし、案件ごとの列を読む:
   ```bash
   {{TASKBOARD_CLI}} debug state > {{JOB_DIR}}/.tb-state.json
   jq -r '.boards[] | select(.archived|not) | "\(.id) \(.name): \([.columns[].id]|join(","))"' {{JOB_DIR}}/.tb-state.json
   ```
   列 id は案件ごとにここから読む（ハードコードしない）。タスクの列は、そのタスクの `boardID` の案件の列で判定する。**列の並び順がそのまま列の前後関係**になる。案件をまたいでタスクを移さない

| `N ってどれ？` / `タイトル出して` | 次の通知でそのタスクのタイトルを添える |
| `改善して` | 巡回自身の改善。この手順書の中で完結するなら同じ回で直す。外のリポジトリを触るなら taskboard に起票する |

### 1-1. taskboard の現状（固定）

Step 0 で取った `.tb-state.json` を使う。refresh は要らない（daemon が PR を 60 秒ごと、Jira を 5 分ごとに取っている）。

```bash
F={{JOB_DIR}}/.tb-state.json
# タスク（全案件）
jq '[.tasks[] | {number, boardID, columnID, title, due, note, links:[.links[].url]}]' "$F"
# リンクの live 状態（URL がキー）
jq '[.links[] | {url, fetchedAt, pr:.pullRequest, jira:.jira}]' "$F"
```

`links[]` は URL ごとに live 状態を持つ。既存タスクの状態の突き合わせはここだけで済ませる（`task_get` を件数分呼ばない。`task_get` には live 状態が出ない）:

- GitHub PR: `.pullRequest` に `state`（OPEN / MERGED / CLOSED）/ `isDraft` / `reviewDecision`
- Jira: `.jira` に `statusName` / `category`（`new` / `indeterminate` / `done`）/ `summary`

**鮮度の判定**: `fetchedAt` が PR は15分、Jira は30分より古いリンクと、タスクにあるのに `links[]` に無い URL は「取得失敗」として扱う。そのリンクに依存する判定を保留し、通知の「■ エラー」に出す（古い状態で列を動かさない）。全リンクが古いときは daemon の巡回が止まっているので `taskboard: リンク取得が停止` と出す。

## Step 2: 判定

### 2-1. 既存タスクの列（前進だけ自動）

列の前後関係は Step 0 で読んだ案件の列の並び順。**今の位置より後ろへの移動だけ実行する。後退はしない。**

**PR の状態による前進は taskboard の daemon が自動で行う**（60 秒ごと。前進だけ、終端以外の全タスク）。巡回はこれを手で追わない（同じ移動を二重に撃たない・通知にも出さない）:

| live 状態 | daemon の動き |
|---|---|
| `state=OPEN`, `isDraft=false` | レビュー中の列へ |
| `state=MERGED` | 案件の「マージしたら」の列（`boards[].mergeTarget`）へ |
| レビュー依頼の列で、リンク PR が全部 MERGED か CLOSED | 完了の列へ |

巡回が判定するのは daemon が動かさない分だけ:

| live 状態 | 列 |
|---|---|
| `state=OPEN`, `isDraft=true` | 作業中（今の列が未着手・計画のときだけ） |
| `state=MERGED`、かつ今の列が「マージしたら」の列より手前 | 動かさない。daemon が進めるのを待つ |
| `state=CLOSED`（未 merge、レビュー依頼の列以外） | **見送り候補 → 通知だけ** |

<!-- 貼る: 使う sources/*.md の「2-1 に足す判定」（Jira のステータス対応・release tag 等） -->

- **PR と Jira が両方リンクされている場合**は、**より後ろの列**に合わせる
- **PR が複数リンクされている場合**は、**最も手前の PR** に合わせる。複数の PR は全部終わって初めて1つの完了なので、1本が approve でも別の1本が draft なら作業中が正しい（「より後ろ」を当てると、未完了の draft を残したまま先の列へ飛ぶ）
- **リンク PR が MERGED であることを完了候補の根拠にしない**。「マージしたら」の列にいる時点で merge は済んでいる。完了候補の根拠は、本番への到達（release tag 等）か、チケットの完了だけにする
- **見送りの列のタスクは、状態確認・提案の対象から外す**。例外は 2-2 の重複判定でヒットしたとき（リンク・note の追記はする）
- **レビュー依頼の列（他人の PR）は巡回から動かさない**。リンク PR が全部 MERGED か CLOSED になると daemon が完了へ移す。daemon の移動は事後報告に出さない（アプリに出る）
- `due` はチケットの期日があれば `task_update(task_id, due)` で揃える

### 2-2. 新規起票

起票を自動でするか、候補として通知するだけにするかはソースで分ける。各部品の「起票の既定」に従う（チケットと自分の PR は自動、会話とメールは候補が既定）。

**重複判定は URL で行う**（タイトルは表記が揺れて照合できない）:

```bash
jq --arg u "$URL" '[.tasks[] | select(any(.links[]?; .url == $u)) | {number,title,columnID}]' {{JOB_DIR}}/.tb-state.json
```

ヒットしたら起票せず、リンクや note を足すか列を動かす。`state.seen[key]` に記録があるものも起票しない（`decision` が `created` でも `ignored` でも再検討しない）。

**起票対象から恒久的に外す領域**（**候補としても通知しない**）:

- {{EXCLUDED_AREAS}}

自分が「対応します」と明言していても、この領域は起票しない（確度の判断より優先する）。見つけたら `seen[key].decision = "ignored"` にして通知にも出さない。**明示指定が無い限り、この領域を巡回の側から蒸し返さない**（「前回無視したが本当に良いか」の確認も出さない）。

**除外の解除（明示指定）**: `@{{JOB_NAME}}` を宛先に名指しして起票・列の移動を指示した発言があれば、その発言が指すものだけは起票する。領域全体の除外は解けない（`decisions` にも `seen` にも領域の解除は書かない）。`seen[key]` が `ignored` でも `created` に置き換え、note に「@{{JOB_NAME}} の明示指定で除外を解除」と書く。列の指定が無ければ未着手。

**確度の判断**（会話・メール由来）:

- 起票してよい: 自分が「対応します」「やります」と明言した / 名指しで依頼され、作業内容が一意に読み取れる / 議事録の次のステップに自分が担当として書かれている
- 起票しない（候補として通知）: 依頼か雑談か曖昧 / 担当が自分か不明 / 作業内容が読み取れない / 誰かの発言の伝聞

起票の書き方:

- タイトルは**何が終われば完了かが読み取れる形**にする。チケット由来なら先方の表題をそのまま使う（後から照合できるため）
- 粒度は「1タスク = 1つの完了判定」。複数の PR にまたがる作業は1タスクにリンクを複数付ける
- **調査・計画のタスクと、その実行のタスクを切り分けない**。既存の調査・計画タスクがある領域の PR を見つけたら、新規に起票せずそのタスクへリンクを足し、note に統合した旨を書く。実行分を別タスクに切り出すのは実作業をしているセッションの判断で、巡回から派生タスクを起こさない。URL の重複判定だけでは分からないので、**タイトルの領域（調査対象・コンポーネント）でも突き合わせる**
- **会話・メール・議事録由来の起票には、参照先 URL を必ずリンクで付ける**（後から何を見ればよいかが分かるように）。読み取れないときは省かず、note に「参照先 URL 不明」と書く

### 2-3. 初回モード

`state.last_success_at` が null のときは、**起票も列の移動もしない**。検出したものを全部「候補」として番号付きで通知し、`state.seen` には入れない。ユーザーが「起票 3」等と返したら次の回で起票する（初回に十数件を一気に起票してボードを壊さないため）。

### 2-4. 裁定済みのものを再通知しない

**毎回同じ「要判断」「候補」を並べ直すと通知が読まれなくなる。** ユーザーが一度裁定したものは `state.decisions` に記録し、**その裁定の前提が崩れるまで通知に出さない**。

| decision | 意味 | 再通知する条件 |
|---|---|---|
| `hold` | 「保留」「まだ」「そのままで」等。列は動かさない | live 状態が記録時と変わったとき（`trigger` に何を待っているかを書く） |
| `auto_done_on_ticket_done` | 「チケットが完了になったら done にしといて」 | 再通知しない。チケットが完了の分類になったら**通知なしで完了の列へ移し**、事後報告だけ出す |
| `auto_advance_on_ticket_status` | 「チケットが進んだら＜列＞にしといて」等、目的の列を伴う自動前進の予約 | 再通知しない。`trigger` のステータスの変化を見つけたら 2-1 の対応に従い**通知なしで列を移し**、事後報告だけ出す |
| `pin_column` | 「まだ planning」等、自動前進を止める指定 | 再通知しない。2-1 の自動前進の対象から外す |
| `ignored` | 「無視」「いらない」 | 再通知しない。`seen` にも入れて再起票しない |

`hold` の再通知の条件は**具体的な観測値**で書く（「<チケット> が <ステータス> から変わったら」「本番のタグに入ったら」）。「そのうち」では判定できないので、判定できる形にできないときはユーザーに聞き返す。

裁定と同じ内容は taskboard の note にも残す（`decisions` は巡回の状態、note は人が読む文脈）。

## Step 3: 適用

MCP server `taskboard` の tool で書く:

| 操作 | 呼び出し |
|---|---|
| 起票 | `task_create(title, column, links:[URL], note, link_session:false)`（`due` があれば添える） |
| 列の移動 | `task_update(task_id, column)` |
| リンクの追加 | `task_update(task_id, add_links:[URL])` |
| note の追記 | `task_update(task_id, note: <今の note> + "\n" + <追記>)` |
| 期日・題 | `task_update(task_id, due:"YYYY-MM-DD")` / `task_update(task_id, title)` |

- **`task_create` は必ず `link_session: false`**。省くと巡回のセッションが起票したタスクに結ばれる
- `task_create` は `column` を必ず明示する（省くと既定の列に入り、意図しない場所になることがある）
- 同じ URL のタスクがあると `task_create` はエラーで止まる。そのときは返ってきた番号に `task_update` で足す（ほかのセッションの Stop hook が open の PR から自動で起票していることがある）
- **`task_update` の `note` は置き換え**。追記は `.tb-state.json` の今の note を前に付けて渡す。同じ回の中で同じタスクに2回追記するときは、1回目に渡した値を「今の note」として使う
- 完了の確認: 応答の「移した先の列」が意図した列 id と一致していること
- note には**セッションをまたいで要る文脈だけ**書く（起票の根拠 URL、判断した理由）。作業ログは書かない
- 作業項目（`work_add` / `work_update`）は使わない（作業項目はそのタスクの作業セッションが持つ）

## Step 4: 通知

**1回の実行につき通知は1通だけ。** **前回の通知から変化が無ければ送らない**（無音が正常）。

送るのは、次のどれかに**前回の通知には無かったもの**が含まれるときだけ:

| セクション | 「新しい」と判定する基準 |
|---|---|
| 指示の反映 | 今回処理した指示がある |
| 起票 | 今回起票したタスク番号がある |
| 前進 | 今回動かした列がある |
| 外部への書き戻し | 今回実行した書き戻しがある（部品で許可したものだけ。Jira の遷移等） |
| 要判断 | 前回の通知に無かった要判断がある |
| 候補 | 前回の通知に無かった候補がある |
| エラー | 前回の通知に無かった種別のエラーがある |
| 期限 | 「期限通知の発火条件」に当たるものがある |

**巡回で何か作業をしても、ユーザーに伝える内容が前回と同じなら送らない。**

判定は**セクションごとのキー集合の差分**で行う。今回の集合から `state.last_notification.fingerprint` の集合を引いた**新規分が全セクションで空なら送らない**（ログにだけ書く）。

- **「減っただけ」の回は送らない**。要判断が3件から2件に減った、候補が解決した等は新規分ゼロなので無音が正しい（集合の完全一致で判定すると、この回に送ってしまう）
- **未回答の要判断・候補は単独では再掲しない**。ほかに新しいものがあって送る回にだけ「■ 要判断（未回答）」として併記する。同じ行を毎回並べると通知全体が読まれなくなるため、催促はしない（pending は state に残るので、次に何か変化があった回に必ず目に入る）

### 期限通知の発火条件

期限は「変化」ではなく「状態」なので、due が48時間以内というだけで毎回出さない。次のどちらかに当たるタスクだけを「■ 期限」に載せる。載せるものがあれば、それ単独でも送ってよい:

- due が**初めて48時間を切った**（`state.notified_due` にそのタスクの記録が無い）
- **due の当日**、または**due を過ぎていて**、その日はまだ通知していない

`state.notified_due[<task_id>]` に**最後に期限を通知した日付**（`YYYY-MM-DD`、`date +%F`）を入れ、同じ日に二度出さない。対象から外すもの:

- 終端の列へ移ったタスク（`notified_due` のエントリも消す）
- `decisions[<id>]` が `hold` / `pin_column` のタスク（据え置きの指示が出ているので、期限だけを理由に蒸し返さない）
- due が48時間より先のタスク

due が編集で先送りされたら `notified_due` のエントリを消す（新しい due で初めて48時間を切ったときに再び1回出す）。

### 送り方

```bash
jq -n --arg m "$MESSAGE" '{"{{NOTIFY_FIELD}}": $m}' | curl -s -K {{JOB_DIR}}/notify.curl \
  -X POST -H 'Content-Type: application/json' -d @-
```

- 宛先は `notify.curl` の `url` だけ。**コマンドラインに URL を足さない**（足すと両方に送られる）。`notify.curl` が無い・読めないときは通知を送らず、ログに「notify.curl 不在」と書く
- 改行を含むので `jq -n --arg` で組み立てる（`-d "{\"...\":\"...\"}"` を手で書かない）

### 本文の形

```
{{JOB_NAME}} MM-DD HH:MM

■ 指示の反映
done へ: #41 / #29
保留（再通知しない）: #22 <チケット> のデプロイ待ち

■ 起票
#48 <チケットの表題>  (jira / todo)
#49 Review <repo>#<番号>  (pr / review_req)

■ 前進
#12 planning → working  (Jira: 進行中)

■ 要判断
a) #33 はチケットが完了。done でよければ「done 33」

■ 候補（未起票）
1) <チャンネル> で <相手> から〜の依頼。起票するなら「起票 1」

■ 期限
#9 MM-DD（明日）

■ エラー
gmail: 認証切れ。再認証が必要
```

- セクションは上から「■ 指示の反映 / ■ 起票 / ■ 前進 / ■ 外部への書き戻し / ■ 要判断 / ■ 候補 / ■ 参考 / ■ 期限 / ■ 打ち切り / ■ エラー」の順。該当が無いセクションは丸ごと省く
- **■ 指示の反映**は、前回の指示に対して何をしたかを1行ずつ。指示を受けて何もしなかった場合も理由を書く
- **■ 参考**は、列も起票も動かさないが知っておくと得な観測。無理に埋めない
- **候補と要判断の番号は state に保存する**（次の回の返信の解釈に使う）
- 会議の文字起こし・メールの本文をそのまま貼らない。要約と参照先だけにする（他者の発話・私信を含む）
- 取得を上限で打ち切った場合は「■ 打ち切り」に書く（黙って切らない）

## Step 5: 記録

1. `state.json` を更新する:
   - `last_run_at` は常に更新する
   - **`last_success_at` は全ソースが成功したときだけ更新する**（一部が失敗した回に進めると、失敗したソースの分を取りこぼす）
   - 失敗したソースの `cursors.*` は据え置く
   - `seen` に今回の判断を足す。`at` が90日より古いエントリは消す（無限に増えて各回の読み込みが重くなる）
   - `pending` に今回の要判断・候補を番号と対応付けて保存する
   - `decisions` に今回ユーザーが裁定したものを足す（2-4）。裁定の前提が消えたエントリは消す
   - `processed_instructions` に今回処理した指示のキーを足す。90日より古いものは消す
   - **`last_notification` は送った回だけ今回の fingerprint で更新する**。送らなかった回に上書きすると、「前回と同じなら送らない」の比較の基準が今回の値にずれ、次の回以降も出なくなる
   - 全体が失敗なら `consecutive_failures` を +1、成功なら 0
2. `log/YYYY-MM.md` に1行追記する: `- HH:MM 起票2 前進1 要判断2 候補1 エラー0`
   - **送らなかった回はログに理由を書く**（`通知スキップ: fingerprint 一致`）。通知が無音でも巡回の記録は残す

## エラーの扱い

| 状況 | 動作 |
|---|---|
| MCP の認証切れ | そのソースをスキップする。通知の「■ エラー」に再認証の手段を書く |
| `.tb-state.json` のリンクが古い・欠けている（1-1 の鮮度の判定） | そのリンクの判定を保留する。列を動かさない |
| taskboard の MCP が無い・daemon が応答しない | Step 0 で通知して終わる（収集もしない）。`last_run_at` と `consecutive_failures` だけ更新し、`last_success_at` と cursor は進めない |
| コマンド（`gh` / `curl` 等）の失敗 | そのソースをスキップする。cursor を進めない |
| 3回連続で全体が失敗 | 通知に「連続 N 回失敗」と書く |

## 禁止事項

1. **外部サービスへ書き込まない**: コメント・レビュー・PR の操作・merge・メッセージの送信。外への出力は**通知の Webhook への curl だけ**。例外は、貼った部品が明示的に許可した書き戻し（`sources/jira.md` の許可した遷移等）だけ
2. **taskboard でタスクを消さない・セッションを起こさない・定期起動を触らない**: タスクの削除、`session_start` / `session_prompt`、`schedule_create` / `schedule_update` / `schedule_run`、`doc_publish` / `ask_user` / `review_request`（答える人がいない）、他タスクの `work_*` を使わない。`task_create` は `link_session: false` 以外で呼ばない
3. **終端の列（完了・見送り）へ自分の判断で移さない**。通知して指示を待つ（指示があれば移してよい）。例外は `decisions` の `auto_done_on_ticket_done`（2-4）だけで、事後報告する。レビュー依頼の列の完了送りは daemon が行い、巡回は動かさない
4. **列を後退させない**
5. **git の操作・コードの変更をしない**
6. 書き込んでよいのは `{{JOB_DIR}}/` の下だけ（部品が名指しした生成物は例外）
7. 会議の文字起こし・メールの本文を外部（通知を含む）に出さない
8. 秘密情報（Webhook URL・トークン）を表示しない・ログに書かない・コマンドラインの引数に載せない（会話ログとプロセス一覧に残る）
9. `timeout` コマンドを使わない

## state.json スキーマ

```json
{
  "version": 1,
  "last_run_at": null,
  "last_success_at": null,
  "consecutive_failures": 0,
  "cursors": {},
  "seen": {},
  "decisions": {},
  "pending": [],
  "processed_instructions": [],
  "notified_due": {},
  "last_notification": null
}
```

- `cursors`: 部品の「cursor」が足すキー。失敗したソースの分は据え置く
- `seen` のキー: 部品の「起票の既定」が決める（URL・permalink・`<ソース>:<id>`）
- `seen` の値: `{"decision": "created|ignored|notified", "task_id": <int|null>, "at": "<ISO8601>"}`
- `pending` の要素: `{"label": "a"|"1", "kind": "terminal|candidate", "task_id": <int|null>, "source_key": "<key>", "summary": "<text>", "at": "<ISO8601>"}`（受け口の部品が `notify_ts` 等を足す）
- `decisions` のキー: taskboard のタスク番号（文字列）。値は `{"decision": "hold|auto_done_on_ticket_done|auto_advance_on_ticket_status|pin_column|ignored", "trigger": "<再通知・発火の条件>", "reason": "<ユーザーの言い分>", "at": "<ISO8601>"}`
- `processed_instructions`: 処理済みの指示のキー（二度実行しないため）。90日より古いものは消す
- `last_notification`: 前回**送った**通知の要旨。`{"at": "<ISO8601>", "fingerprint": {...}}`。`fingerprint` は各セクションのキー集合:
  ```json
  {"instructions": ["<key>"], "created": [48], "advanced": ["12:planning→working"],
   "writeback": ["<KEY>:<前>→<後>"], "terminal": ["33"],
   "candidates": ["<source_key>"], "errors": ["gmail:auth"], "due": ["9"]}
  ```

## ソースを足すときの型

sources/ に無いソース（議事録・ローカルのファイル・別のチケット管理）を足すときは、部品と同じ項目を決めてから書く。決めずに足すと、失敗したときの扱いと二重起票の防ぎ方が抜ける。

| 項目 | 決めること |
|---|---|
| 固定値の行 | アカウント・サーバー名・パス |
| 収集 | `since` 以降の差分の取り方。件数の上限とページの追い方 |
| 起票の既定 | 自動か候補か。`seen` のキー |
| cursor | `cursors` に足すキーと、進める条件（成功したときだけ） |
| 失敗時 | スキップして `errors[]` に積む。エラーの種別名 |
| 本文の扱い | 他者の発話・私信を含むなら、通知には要約と参照先だけ出す |

重い前処理（全件の同期・インデックスの再生成）が要るソースは、**その回で待たない**。background で投げてすぐ抜け、前回の処理が残した結果を読む。多重起動は lockfile（`mkdir` の成否）で防ぎ、一定時間より古い lockfile は消して投げ直す。結果のファイルの更新時刻が長く止まったままなら、処理が回っていないので「■ エラー」に出す。全件をやり直すオプションは付けない（毎回の予算を使い切る）。
