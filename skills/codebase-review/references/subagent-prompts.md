# codebase-review 委譲先向け指示書テンプレート

各観点の委譲先（herdr pane 上の Claude Code）に渡す指示書のテンプレート。
SKILL.md 本文の Phase 1 でこのファイルをReadし、`## あなたの担当観点` に references/review-aspects.md の該当観点を挿入し、`{...}` を実値で埋めて、観点ごとに1ファイルずつ書き出す。タスク1〜5はすべて必須（一部を省くとマルチモデル検証や網羅性が担保できなくなるため）。委譲の経路・起動・結果の回収は @context/herdr-delegation.md に従う。

## 目次

- [指示書テンプレート](#指示書テンプレート) — 委譲先に渡す本体（タスク1〜5）
- [issueファイル形式](#issueファイル形式) — 委譲先が生成するissueの形式
- [観点サマリ形式](#観点サマリ形式) — 委譲先が必ず1つ書く成果物の形式

## 指示書テンプレート

以下を1つのファイルに書き出し、そのパスを委譲先へ渡す。`{...}` は実行時に埋め、`## あなたの担当観点` には review-aspects.md の該当観点を挿入する。**パスはすべて絶対パスで書く**（委譲先は lead の会話履歴を共有せず、相対パスの起点が伝わらないため）。

```
# タスク: 「{観点名}」観点のコードベースレビュー

## 目的
{リポジトリパス} を「{観点名}」の観点から網羅的にレビューし、発見した問題をissueファイルとして記録する。leadは6観点分の成果物をファイルから読んで統合する。

## 成果物
- **観点サマリ（必須・1ファイル）**: {メモリディレクトリフルパス}/aspect-{観点略語}.md — 問題が0件でも必ず書く
- **issueファイル（0件以上）**: {MEMORY_DIRフルパス}/issues/{優先度}-{観点略語}-{日本語タイトル}.md

## 入力
- リポジトリ: {リポジトリパス}
- メモリディレクトリ: {メモリディレクトリフルパス}
- PJルール: {CLAUDE.mdの内容}
- コードベース構造: {ディレクトリ構造}
- 担当観点とレビュー基準: 本指示書の「あなたの担当観点」節
- 成果物の形式: {subagent-prompts.md の絶対パス} の「issueファイル形式」「観点サマリ形式」節

## あなたの担当観点
{観点別の詳細指示}

## タスク

### 1. コードベース全体の網羅的確認
以下の手順ですべてのディレクトリとファイルを確認する（一部だけ見て終わらせると担当観点の問題を見落とすため）:

1. ディレクトリ構造を把握
   find {リポジトリパス} -type d -not -path '*/node_modules/*' -not -path '*/.git/*'
2. 各ディレクトリ内のファイルを走査（apps/, src/, lib/, batch/, misc/ 等の主要ディレクトリをすべて。隠れたサブディレクトリも見落とさない。ファイル数が多い場合はGlobで効率的に検索）
3. 担当観点に関連するファイルを特定し、すべて読む（「たぶん問題ない」で飛ばさない。類似ファイルも個別に確認）

### 2. ベストプラクティスの調査
問題を発見した、または問題が疑われる場合:

1. context7 で関連ライブラリのドキュメントを確認（resolve-library-id → query-docs の順。例: Drizzle ORMのN+1対策、Reactのメモ化）
2. WebSearch で業界標準のベストプラクティスを確認（例: "OWASP timing attack prevention 2025"）
3. 調査結果をissueファイルの「改善案」「追加情報」に反映

### 3. agent cliによる並行レビュー
`--skip-multimodel` が明示指定されない限り実行する（別モデルとの突き合わせで検出漏れ・誤検出を減らすため）。

外部CLI（codex優先／cursor fallback）で同じ観点のレビューを実行する。CLI判定・コマンド形式・jq抽出は @context/agent-cli-guide.md「使用するCLIの選択」「基本コマンド」に従う。外部CLIが両方使えない場合は自分で fable subagent を spawn せず、観点サマリの「マルチモデル検証」欄に未実施と理由を書いた上で lead に連絡する（連絡方法は本指示書冒頭のヘッダ。fallback の判断は lead が行う）。渡すプロンプト本文（共通）は以下:

    あなたは「{観点名}」の専門レビュアーです。

    ## コンテキスト
    - リポジトリ: {リポジトリパス}
    - PJルール: {CLAUDE.mdの内容}
    - コードベース構造: {ディレクトリ構造}

    ## あなたの担当観点
    {観点別の詳細指示（レビュー項目一覧）}

    ## 優先度判断基準
    {観点別の優先度基準}

    ## タスク
    1. コードベース全体を網羅的に確認（すべてのディレクトリ・ファイルを走査。担当観点の関連ファイルをすべて読む。「たぶん問題ない」で飛ばさない）
    2. 問題を特定し優先度を付与
    3. 発見した問題を以下のJSON形式で出力:
       {"issues": [{"title": "問題のタイトル（日本語）", "priority": "critical|major|minor|trivial", "files": ["ファイルパス:行番号"], "description": "問題の詳細説明", "suggestion": "改善案", "bestPractice": "参照したベストプラクティス（あれば）"}], "checkedDirectories": ["確認したディレクトリ一覧"], "summary": "レビュー概要"}

    注意: 問題がなければ issues: []。推測ではなくコードを実際に読んで判断。優先度は厳格に（critの乱用禁止）。コードベースの一部だけを見て終わりにしない。

結果を突き合わせて採用を判断する:

| 状況 | 対応 |
|------|------|
| 両者が同じ問題を検出 | 高信頼度として採用 |
| 自分のみ検出 | 妥当性を再確認、妥当なら採用 |
| agent cliのみ検出 | 該当コードを確認、妥当なら採用 |
| 優先度が異なる | 根拠を比較し適切な方を採用 |

マージ結果をissueファイルに追記:

## マルチモデル検証
- Claude Code: 検出
- agent cli: 検出 / 未検出
- 信頼度: 高 / 中
- 優先度差異: なし / あり（Claude Code={X}, agent cli={Y} → 採用: {Z}）

### 4. 問題の特定と記録
- 各問題に優先度（critical/major/minor/trivial）を付与
- 問題ごとにissueファイルを作成（形式は「issueファイル形式」節）
- ベストプラクティス調査結果とマルチモデル検証結果を含める

### 5. 観点サマリの作成
{メモリディレクトリフルパス}/aspect-{観点略語}.md を「観点サマリ形式」節のとおりに書く。**問題が0件でも必ず書く**（このファイルがleadの完了判定に使われるため、書かずに応答を終えると失敗として扱われる）。

## やらないこと
- 担当観点以外の観点でissueを立てる（同じ問題が複数観点に該当する場合は、最も重要な観点の担当が1つだけ作成する）
- 対象リポジトリのコードを変更する（本作業は読み取りとレビュー記録のみ）
- 他観点の観点サマリ・既存のissueファイルを編集・削除する
- 成果物を書かずに画面へ結果を出して終える（leadはファイルからしか結果を受け取らない）

## 完了基準
- 観点サマリが1ファイル作成されている
- 観点サマリの「確認した範囲」に走査したディレクトリが列挙され、未確認の範囲が明示されている
- 観点サマリのissue件数と、実際に作成したissueファイルの数が一致している
- タスク3を実行した場合、各issueにマルチモデル検証結果が記載されている

## 注意事項
- 問題がない場合はissueファイルを作成しない（観点サマリは0件と書いて必ず作成する）
- 推測ではなく、コードを実際に読んで判断する
- 優先度は厳格に判断する（critの乱用禁止）
- コードベースの一部だけを見て終わりにしない
- ベストプラクティス調査は問題発見時に必須
```

## issueファイル形式

場所: `{MEMORY_DIR}/issues/{優先度}-{観点略語}-{日本語タイトル}.md`

```markdown
---
priority: {critical|major|minor|trivial}
category: {観点略語}
type: {bug|improvement|feature}
---

# {タイトル}

## 概要
{問題の簡潔な説明}

## 現状の問題点
{何が問題なのか、どこで発生しているか}
- 対象ファイル: {パス:行番号}
- 対象ファイル: {パス:行番号}

## 改善案
{どう改善すべきか}
- ベストプラクティス: {context7/WebSearchで調査した内容}

## 期待される効果
{改善後のメリット}

## 対象範囲
{影響を受けるファイルや機能}

## 追加情報
- 参考: {調査したドキュメントURL等}
- 関連issue: {あれば}
```

## 観点サマリ形式

場所: `{メモリディレクトリフルパス}/aspect-{観点略語}.md`（観点略語: perf / sec / test / arch / cq / docs）

**問題が0件でも必ず作成する。** このファイルの有無が委譲の完了判定になる。

```markdown
# [{観点略語}] 観点サマリ

## 担当観点
{観点名}

## 確認した範囲
- 走査したディレクトリ: {一覧}
- 重点的に読んだファイル: {一覧}
- 未確認の範囲: {あれば理由付きで。無ければ「なし」}

## issue件数

| 優先度 | 件数 |
|--------|------|
| critical | X |
| major    | X |
| minor    | X |
| trivial  | X |
| **合計** | **X** |

## 生成したissueファイル
- {ファイル名}
（0件の場合は「なし」と書く）

## マルチモデル検証
- 実行: あり（使用CLI: {codex|cursor}）/ なし（理由: {--skip-multimodel 指定 / 外部CLI が両方使用不可}）
- 突き合わせ結果: 両者一致 X件 / 自分のみ X件 / agent cli のみ X件 / 優先度差異 X件
```
