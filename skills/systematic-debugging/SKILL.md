# Systematic Debugging

修正の前に根本原因を特定する。症状への修正は、同じ原因から別の場所で再発するため。

## Phase 1: 根本原因調査

1. **エラーメッセージを最後まで読む**。スタックトレースの行番号・ファイルパス・エラーコードを控える
2. **確実に再現する**。再現できないうちは、修正でなくデータ収集を続ける
3. **直近の変更を確かめる**。git diff・最近のコミット・依存や config の変更・環境差分
4. **原因を一次情報で特定する**。エラーの意味は公式ドキュメント（context7 / WebSearch）で確かめる
5. **複数コンポーネントの系では境界に診断ログを入れる**。各境界で入る値・出る値・環境変数の伝播を記録して一度実行し、どの層で値が不正になるかを確かめてから、その層を調べる
6. **データフローを遡る**。エラーが出た場所ではなく、不正な値の発生源を突き止める（[references/techniques.md](references/techniques.md) の root-cause-tracing）

## Phase 2: パターン分析

1. 同じコードベースで動いている類似コードを探す
2. リファレンス実装・公式サンプルがあれば全行読む（パターンだけ真似ると部分理解のバグになる）
3. 動くものと動かないものの差分をすべて列挙する。「関係ないはず」で外さない

## Phase 3: 仮説検証

1. 仮説を1つ書き出す（「X が根本原因。理由は Y」）
2. 1仮説につき1変数だけ変えて検証する。複数の修正を同時に入れると、どれで直ったか切り分けられない
3. 外れたら新しい仮説を立てる。外れた修正の上に修正を積まない
4. 分からないなら「X が分からない」と書き、調査を続けるかユーザーに聞く

## Phase 4: 実装

1. 失敗するテストケースを先に作る（最小の再現。フレームワークが無ければ使い捨てスクリプトでよい）
2. 特定した根本原因だけを直す。ついでの改善やリファクタを混ぜない。修正コードを書く前に `/writing-code` を発動する
3. 元の再現手順で解消を確かめる
4. 必要なら、実際にバグが通った経路に多層の防御を足す（[references/techniques.md](references/techniques.md) の defense-in-depth）

調べ尽くしても環境・タイミング・外部が原因なら、調べた内容を記録したうえで、リトライ・タイムアウト・エラーメッセージ・監視で扱う。

## 修正が3回失敗したら

4回目を試す前に止まり、アーキテクチャを疑う。修正のたびに別の場所で問題が出る、修正に大規模なリファクタが要る、のどちらかなら、仮説の外れではなく構造の問題であることが多い。ユーザーと構造を相談してから先へ進む。
