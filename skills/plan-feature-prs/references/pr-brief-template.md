# 31_pr_briefs.md テンプレート（PR別実装ブリーフ）

各PRブリーフは自己完結させる: そのブリーフ + 30_plan.md + 20_survey.md だけで実装セッションが詳細設計に入れること。
ファイル冒頭に全PR共通の前提を置き、以降はPRごとに1セクション。

```markdown
# PR別実装ブリーフ（<機能名>）

各PRの実装セッションは、着手前に必ず以下を読むこと:
1. `30_plan.md`（スコープ・全体設計判断 D1..Dn・検証方針）
2. `20_survey.md` の該当セクション（既存実装のファイルパス:行番号）
3. このファイルの該当PRブリーフ
4. <デザインファイル等、実装時に直接参照するソース>

共通ルール:
- ブランチ: <epic branch> 起点（依存PRは被依存PRの head branch 起点）。<worktree 等の環境構築手順への参照>
- <PJのコーディング規約スキル・エラーメッセージ規約等への参照>
- E2E・横断テスト: <30_plan.md §6 で確定した方針の要約>
- 完了条件: 30_plan.md §6（品質チェック + 動作検証 + テスト同梱）
- PR作成: <使用スキルと base の明示指定>。PR本文に対応する要件節とデザイン参照を記載

---

## PR-A: <機能名>（<対応する要件節>）

**base**: <epic / PR-X head> / **依存**: <なし / PR-X> / **設計判断**: <D番号> / **デザイン**: <ノード参照>

### 1. 調査
- [ ] <確認すべき既存コード（ファイルパス:行番号、20_survey.md からの主要参照を再掲）>
- [ ] <実装前に確定が必要な外部仕様・挙動>

### 2. 計画（詳細設計）
- [ ] <設計すべき論点。全体設計判断で確定済みの部分は D番号 を参照し再検討しない>
- [ ] <高リスクPRの場合: 着手時に外部レビューを実施する旨>

### 3. 実行
- [ ] <実装内容の塊とコミット分割方針>
- [ ] <テスト（正常系・境界・エラー系の列挙）>

### 4. レビュー・検証
- [ ] <動作検証の具体シナリオ（操作手順と期待結果）>
- [ ] 品質チェック（30_plan.md §6）

---

## PR-B: ...
```

## 記載時の注意

- **4ステップ構造**（調査→計画→実行→レビュー）は @context/workflow-rules.md Phase 2 に従う
- 「調査」には 20_survey.md の該当ポインタを再掲する（実装セッションに survey 全文を読ませない）
- 「計画」に全体設計判断の再検討余地を残さない。ブリーフ内で判断が必要な点は「詳細設計で確定」と明示し、判断材料（参照先）を添える
- 動作検証シナリオは done/not-done が判定できる粒度で書く（「〜を確認」ではなく「<操作>→<期待結果>」）
- 依存PRの base 指定（被依存の head branch）をブリーフ内に明記する。実装セッションはブランチ戦略を推測しない
