# Lead

複数のタスクの会話（委譲先）を lead として預かり、ユーザーが各会話を開かずに済む状態を保つ。ユーザーが見るのは lead の会話だけ、という前提で動く。

## 1. 預かる範囲を決める

着手の前に、次の 2 つを 1 つのメッセージでユーザーに示し、承認をもらう。承認は、この lead の間は常設の承認として扱う（同じ論点で何度も聞き直さない）。承認と各裁定はメモリの `05_log.md` に書く。

- **委任の範囲**: 既定は、実装 → push → `/create-draft-pr` → CI 全 success → `gh pr ready` → reviewer の確認 → レビュー対応の push まで。ユーザーが別の範囲を指定したらそれに従う
- **判断の振り分け**（下の表）

| lead が決める（委譲先は推奨と根拠を lead に送る） | ユーザーに聞く |
|---|---|
| データで効果・必要が無いと示せた案を実装しない（範囲の縮小） | 費用が増えるもの |
| 自分のタスクのチケット（Notion 等）への調査結果の追記・ステータスの変更 | 本番のデータへの書き込み、本番の設定・secret |
| 推奨がはっきりしている設計の選択（中長期の最適で決める） | 他人に届く投稿（Slack・メール・他人宛のコメント） |
| 2 つのタスクが同じ変更を計画しているときの統合（下の 4） | merge（委任に含まれていなければ） |
| 完了の定義の調整（PR が出ない成果物など） | ユーザーしか持たない情報が要るもの |

範囲の縮小を確認必須にしている AGENTS.md の規定は、この表への承認で満たす。表に無い判断は、迷ったら lead が推奨を付けてユーザーに聞く。

## 2. 起動する

- 起こす前に `usage_get` で各アカウントの利用枠を見て、**リセットが近いアカウント**を選ぶ（`session_account`）。体数が 6 以上なら、起こす前に体数と残量を示す（`context/tool-claude-code.md`「委譲判断」）
- 既存の会話は再開せず、新しく起こす（古い会話は文脈が膨らんでいて、指示書と食い違う前提を持っている）
- 各タスクに `session_start` で起こす（`task_id` にそのタスク、`disallowed_tools: ["Agent", "Workflow"]`）。`bin/taskboard-delegate.sh` は委譲先を lead のタスクに結ぶので、タスクごとに結びたいこの用途では使わない。そのため定型のヘッダが付かない。連絡の方法と再委譲の禁止は、共通の指示書に書く
- **`notify: true` を起動時に渡す。** 別のタスクに起こした会話は既定で知らせが切られていて、後から `session_control` で入れようとしても「知らせる先（parent）が無い」で断られる。起動時に渡せば、別のタスクの会話でもターンの終わりが lead に届く。知らせが来ない会話（渡し忘れ・知らせの前に止まったもの）は、下の 5 の wake で見回る。PR の動きは 5 の watch で待つ
- 起こしたら、会話の id とタスク番号を `05_log.md` に書く。compaction の後は、この記録と `session_list` を突き合わせる（記録にある委譲は起こし直さない）

## 3. 共通の指示書を送る

起動の後に、全会話へ同じ指示書を `session_prompt` で送る。ひな形は [references/brief-template.md](references/brief-template.md) にある。メモリディレクトリに `common-brief.md` として書いてから送る。

- 同じファイルや関数を複数のタスクが触る見込みなら、該当するタスク番号とファイルを指示書に並べ、衝突を避ける決まりを入れる（最新の main から切る、差分を絞る、PR を出す前と ready にする前に rebase する、共通の型や関数を変えるなら先に lead に連絡する）
- 指示書を後から変えたら（委任の範囲の変更など）、全会話へ同じ文面で送り直し、`common-brief.md` も直す

## 4. 委譲先の報告に答える

知らせか見回りで最後の返事を読み、その場で答える。保留にしてよいのは、何を待つのかと、それが届いたら判断がどう変わるかを書けるときだけ。

- **PR の完了報告**は、`gh` で CI・reviewer・mergeable・人のレビューの有無を lead が自分で確かめてから完了として扱う
- **2 つのタスクが同じ変更を計画している**（同じ API 呼び出しを足す、同じ関数を変えるなど）と分かったら、1 本の PR に統合する。片方のタスクを担当にして、もう片方は引き継ぎのファイルを書かせてから会話を閉じる。統合したことは両方のタスクの報告に残す
- **別の経路で決まった質問**（lead が答えた、ユーザーがこの会話で答えた、実装がもう済んだ）が残っていたら、担当の会話に `ask_cancel` させる。見回りのたびに `inbox_list` で、取り下げ忘れの質問を探す
- **ユーザーがこの会話で裁定したら**、担当の会話へ裁定を送り、質問を取り下げさせる。ユーザーに、各会話を開いて答え直すことを求めない
- 委譲先の発見が別のタスクに効く（原因の手がかり、資料の置き場所など）なら、そのタスクの会話に転送する
- 委譲先のコンテキストが 75% を超えたら、区切りで `/handoff` を残させる

## 5. watch で待ち、届かないものだけ wake で見回る

待つ対象ごとに、動きが起きたら lead に届く経路を張る。時刻の見回りは、動きの無い回にも確認の手間がかかり、動きに気づくのも最大で間隔の分だけ遅れるので、届く経路の無いものにだけ使う。

| 待つもの | 経路 |
|---|---|
| 委譲先の会話のターンの終わり | 起動時の `notify: true`（2） |
| PR のレビュー・コメント・CI の失敗・conflict・マージ | PR ごとに `watch_create`（`url`・`events`・`link: false`）。`prompt` には、その動きが来たら lead がすること（マージの条件・担当の会話）と `05_log.md` の絶対パスを書く（compaction の後でも、その文から再開できるようにする） |
| このマシンで確かめられる状態（コマンドの終わり・ファイルの出現） | `watch_create` の `command` |
| 上の経路で届かないもの（知らせが落ちた会話、Slack の返事など外部の状態） | `wake_create` で時刻を決めて見回る |

- PR を預かったら（委譲先が ready にした、レビュー待ちの PR を引き継いだ）、その場で watch を張る。マージを通知すると watch は終わる
- watch は自分の gh アカウントのコメント・レビューを通知しない。lead が自分で出した操作の結果は、その場で `gh` で確かめる
- 知らせや watch の通知で起きたら、その対象を `gh` と `session_history` で開き直してから 4 に従って答え、`05_log.md` に確かめた時点・開いたもの・判断を追記する

wake で見回るときは、時刻を `date` で今を確かめてから決める（過去の時刻は断られる）。`prompt` には `05_log.md` の絶対パスと「今回特に確かめること」を書く。1 回の見回りは次の順で行い、届かない待ちが残っていれば次の wake を作る。

1. `session_list` で状態を見る。running でない会話は `session_history`（`limit` は 1〜2 から）で最後の返事を読み、4 に従って答える
2. watch を張っていない PR を `gh` で確かめる。CI・reviewer・mergeable・人のレビューの有無を見る。人のレビューが付いていたら、担当の会話に `/pr-comment` で対応させる
3. `05_log.md` に、確かめた時点・開いたもの・判断を追記する
4. ユーザーへの報告は、状況報告の型（完了・進行中・待ち・ユーザーに要るもの）で全件を書く

## 6. ユーザーに判断を頼む

ユーザーは lead の会話しか見ない。判断を頼むときは、各会話の `ask_user` を指して済ませず、**この会話の中で答えられる形**にする。

- 受信箱の質問文は省略されている。書く前に、`doc_list`・`doc_read` で各質問の元の文書を開いて読む
- 1 件ごとに、次を書く
  - 何で止まっているか（どのタスクの、どの作業の手前か）
  - 選択肢と、それぞれの利点と欠点
  - 推奨とその理由
  - 答えるとどうなるか
- 回答を受けたら、4 のとおり各会話へ送って質問を取り下げさせる
- 止まった原因が lead の振り分け（聞く必要の無いものを聞かせていた）なら、そう書いて、1 の表と指示書を直す

## 7. 片付ける

- 委譲先が自分の単位を終えたら（成果物が別のタスクの PR に入った、wontfix になった）、`session_stop` の `close` で閉じる
- PR のレビュー対応を担当している会話は、merge まで残す
- 完了の報告の前に、自分が作った wake・watch のうち不要になったものを取り消す

## Gotchas

- **このマシンのシェルが fish のとき、`for` や `set --` を含むループは `bash -c '...'` で包む。** fish の構文で解釈されて、エラーも出さずに何も出力しないことがある
- **`gh` が `dial tcp ... i/o timeout` で失敗することがある**（GraphQL・REST の両方で起きる）。同じ前提で 2 回失敗したら、`curl -s -o /dev/null -w '%{http_code}' https://api.github.com/zen` で疎通を確かめ、数秒の間隔を置いた再試行のループで取る
- **委譲先が自分で `gh pr ready` したことによる「ready になった」の知らせは、委譲先にも lead にも新しい対応は無い。** 中身を読まずに読み飛ばさず、新しい動きが混ざっていないかだけを見る
- **PR のコメントの数だけでレビューの有無を判断しない。** github-actions などの bot のコメントが入る。送り主を見て、人のレビューかどうかを確かめる
