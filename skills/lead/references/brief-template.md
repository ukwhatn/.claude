# 共通の指示書のひな形

`<...>` を埋め、該当しない節は消してから送る。委任の範囲と判断の振り分けは、ユーザーに承認をもらった内容をそのまま写す（言い換えると、委譲先には要件そのものに見える）。

```markdown
[lead からの指示] このタスクは、タスク #<lead のタスク番号> の会話（lead）がまとめて見ています。<ユーザー名> から lead に、次の範囲の進め方を任されています。

## 任されている範囲（承認済み）
- 実装 → commit → push → `/create-draft-pr` で Draft PR を作る → CI が全部 success になったのを `gh pr checks` で確かめる → `gh pr ready` で ready にする、まで。push・PR 作成・ready 化は、この指示で承認済みです
- reviewer は <CODEOWNERS で自動 / `--reviewer <login>` で付ける>。ready にした後、付いているかを `gh pr view --json reviewRequests` で確かめてください
- ready にした後のレビュー対応（指摘への修正 push）も、この承認に含みます。返信の投稿は、lead に文面を見せてからにしてください

## 判断の振り分け
- 次は、<ユーザー名> に聞かず、lead に推奨と根拠を送ってください。lead がその場で決めます
  - データで効果や必要が無いと示せた案を実装しない（範囲の縮小）
  - 自分のタスクのチケットへの調査結果の追記と、ステータスの変更
  - 推奨がはっきりしている設計の選択（中長期の最適で決め、根拠を PR 本文に書く）
  - 完了の定義の調整
- 次だけは、<ユーザー名> に `ask_user` で直接聞いてください: 費用が増えるもの、本番のデータへの書き込みと本番の設定・secret、他人に届く投稿
- merge は lead の判断です。別のタスクの範囲の修正はしないで、見つけたら報告に書いてください

## 同じ箇所を触る別タスク
<ファイルと関数>は、次のタスクが並行して触る見込みです: <#番号 題> / <#番号 題> / ...
- 自分の worktree で、最新の origin/main から切る
- 差分は自分のタスクに必要な範囲に絞る（ついでのリファクタをしない）
- PR を出す前と ready にする前に、origin/main へ rebase する
- 共通の関数や型の形を変えるなど、別のタスクに影響する変更をするなら、先に lead に伝える

## lead への連絡
- 子エージェント（Agent・Workflow）は起動しないでください。分けたほうがよい作業があれば、分け方を lead に提案してください
- 連絡は、そのターンの最後の返事に書いてターンを終えてください（taskboard が lead に届けます）
- 連絡するのは次のときです: (1) 判断が必要になった (2) PR を ready にして reviewer を確かめた（完了） (3) 進められない
- 完了の連絡には、PR の URL・CI の結果・reviewer・自分で決めた設計判断（1 行ずつ）・確かめた操作と確かめていない範囲を書いてください
- コンテキストが 75% を超えたら、区切りで `/handoff` を残してください
```
