# GitHubの書き分け

PR概要欄 / レビュー指摘 / レビュー返信 の3つ。共通して **絵文字・感嘆符は控えめ（指摘時はほぼ無し）**、技術用語は原語＋ `inline code`、件数・パス・ハッシュは具体で書く。文末は SKILL.md STEP 3 の働きごとの形で書く。**AIを使って書いた旨の開示（「AIと共同で」「Generated with 〜」等）は入れない。**

---

## 1. PR概要欄

### 固定見出しテンプレ（チーム開発）
日本語見出しを順に並べる。**`## やらなかったこと` を立てる**（スコープ外があれば理由付きで明示、なければ「特になし」と1行で書く。軽微PRでも見出しは残すが中身は簡潔に）。

```
# 概要
<1〜2文。何をするPRか。背景がいるなら一言>
- closes #<Jira/Issue番号>（このPRが閉じるissueがあるときだけ書く）

## 動機
<何が起きているか（事実）→ だからこのPRで何をするか（判断）。関連スレッドのリンクを添える>

## やったこと
- `path/to/file.ts` に `xxx` を追加。<何をするか>
- <体言止め・常体で箇条書き。inline codeでパス/関数/設定値を囲む>

## やらなかったこと
- <していないこと。理由（事実）を添える。どこで扱うかが決まっていれば書く>

## 影響範囲
- <影響する機能・経路>

## テスト方法
- ローカル
  - [x] `bun run typecheck` 通過
- ユーザー手動確認
  - [ ] <手動確認項目>

## レビュー時チェック
- <見てほしい観点: 境界ケース、すり抜け経路など>
```

箇条書きは、層や領域（DB / API / 画面）、担当（ローカル / ユーザー手動確認）、論点を親項目にし、中身を子項目にしてネストする。1項目に複数の事実を詰めない。

### 動機とやらなかったことの書き方

- **動機**は、事実（何が起きているか・何が困るか）と、このPRの判断（何をするか）に分ける。判断は「〜します」「〜にしました」で書き、「〜したいです」にしない（希望なのか決定なのかが読めないため）
  - 例: 「`<パッケージ>` の `<版>` が `<脆弱性ID>` に該当し、`<CIのジョブ>` が落ちています。`<影響する範囲>` のCIがすべて止まるため、このPRで先に直します。」
- **やらなかったこと**は、していないこと → 理由 の順で書く。理由は事実で書き、「〜したいため」にしない。どこで扱うか（issue・後続PR）が決まっているときだけ添え、決まっていない予定を書かない
  - 例: 「`<対象>` は上げていない。`<範囲>` を含む移行になるため、今回の修正とは分ける」

### バリエーション
- **軽微PR**: `## やったこと` を数行、`## やらなかったこと` は「特になし」、`## レビュー時チェック` は「特にありません」。
- **大規模PR**: カテゴリ別見出し＋件数併記（`### セキュリティ修正（8件）`）、冒頭に総数集計（`全73件（critical 4, major 22, minor 34, trivial 13）`）。`| カテゴリ | 件数 | 対応 |` の表で整理。
- **OSS/外部repo**: 英語見出し（`## Summary` / `## Test plan`）＋箇条書きのみの簡素版に切替。
- **運用注意・PoC警告**: 冒頭にGitHub alert。
  ```
  > [!IMPORTANT]
  > developマージ後、terraform applyを各環境に対して実行します
  ```
- **同時マージ等の運用指示**: 末尾に `---` 区切りで太字注意。`**本PRは hotfix の同時PR3本の1つです。…可能な限り同時にマージしてください。**`
- `## やったこと` の中に `### 原因` を入れ子にして根本原因を説明する型もある。

### 例
`## 検証` は `## テスト方法` の別名（検証手順を書くPRで使う短縮版）。
```
## 概要
dependabotで `<型チェッカー>` が `<版>` に上がると、厳格になった型チェックで既存コードの型エラーが出て `<lintのジョブ>` が落ちます。型注釈の追加だけで直します（ロジックの変更なし）。

## 検証
- `<型チェックのコマンド>`（`<版>`）→ error 0件（残る警告3件は設定で `warn` にしてあるため exit 0）
```

## 2. レビュー指摘（レビュアーとして）

### 2-0. レビュー本文と行コメントの役割分担（最重要）

**指摘の中身は必ず行コメントに置き、レビュー本文には書かない。** 本文は交通整理と結論だけで、ほぼ常に1〜2文。

| 本文に書くこと | 型 |
|---|---|
| どれが必須でどれがnitsか | `<ファイル名> へのコメントだけ必須の確認で、それ以外はnitsです` |
| 必須対応の名指し | `<ファイル>:L<行> だけ必須で直してください（確実に落ちるため）` |
| 指摘はあるがapproveする旨 | `一点コメントしていますが、全体LGTMです` / `気になったところにコメントしましたが、今のままでも問題ないと思います` / `すべて軽微な指摘なのでapproveします` |
| 自信度の留保 | `ドキュメントを読んだ範囲でのコメントなので、実際の挙動と違うかもしれません` |
| approveの付帯条件 | `conflictを解消していただければLGTMです` |
| 再レビュー時の進捗 | `対応ありがとうございます。前回の指摘は全て確認しました。…N件コメントしています` |
| 指摘対応の裁量を返す | `内容に問題はありませんでした。指摘に対応するかはお任せします。` |

本文に指摘内容の要約・観点別の見出し・「統合サマリ」表の類を置かない（行コメントと重複するだけ）。**本文に書くことが無いなら本文なしで行コメントだけ投稿する。**

### 2-1. 指摘なしのapprove

本文は `LGTM` / `LGTMです` / `LGTMです、ありがとうございます`。遅れたときは `遅くなりました 🙇 LGTMです`。

### 2-2. 行コメントの型

**1指摘1コメント。複数論点を1つに詰めない。** **根拠の一次ソースURL ＋ 代替案** をセットにする。絵文字なし。

- **言い切る**: 仕様違反・CI失敗・再現済みバグなど事実、およびコード・一次ソースで経路を追って確かめた挙動（実機で再現していなくても言い切る）（「`個人情報を含ませないでください。` に違反します」「lintも落ちています」「この状態だと完了登録が通りません」）。確かめられる事実（ドキュメントに載っている仕様など）は、推測の形で書く前に確かめる
- **推測は一度だけ、根拠と一緒に示す**: 確かめていない推測は「〜なので、〜だと思います」。「〜ではないかと思います（おそらく）」のように重ねない。裏取りした指摘では、推測の形にするのは修正案の部分だけにする
- **直してほしい変更は依頼の形で書く**: `timezoneを入れてください` / `<関数> のテストも足してください`。採否を相手に任せるなら提案の形にする（`.default(50) を入れるのはどうでしょうか`）
- **相手の意図を確かめる質問は、何を問うかを文末で分ける**: 意図を問うなら `このガードは意図して外していますか`、許容の確認なら `既存の <値> が消えなくなる点は問題ないでしょうか`
- **代替案を添える**: 指摘だけで終わらず「`team_reviewers` を使えばここの処理自体を削除できると思います」
- **対応の要否をラベルで示す**: 必須でない指摘には先頭にラベルを付ける。`[nits]` は直すかどうかを任せる細部、`[minor]` は直してほしいがマージは止めない指摘。必須の指摘にはラベルを付けず、必須である理由を書く。ラベルの意味がそろっていないと、作者が対応の要否を読めないため
- **相手の裁量に返す**: `お任せします` / `ご意見をお願いします`
- typo・命名は超短文で `A` → `B` だけ書く。名前の提案は `<名前B>` のほうが中身に合うと思います（<理由>）
- 公式ドキュメントは `#:~:text=` フラグメント付きで該当箇所を直リンクする。リンクには何の根拠かを添える
- コード片・ログは ```code block``` で引用してから論じる

### 2-3. AI草案から削るもの

AI草案は**量と構造が過剰**になる。次を削ると読み手が要点をつかみやすくなる。

| AI草案に出るもの | 直し方 |
|---|---|
| 1コメントに3段落以上・複数論点 | 論点ごとに別コメントへ分ける |
| `<file>:<line>` 参照の多量列挙 | 指摘に必要な1〜2箇所に絞る |
| 「なお」「あわせて」での論点ぶら下げ | 別コメントにする |
| レビュー本文への指摘要約・サマリ表 | 本文は交通整理1〜2文に削る（無ければ本文なし） |
| 必須でない指摘の `[minor]` / `[nits]` ラベルの欠落 | 付ける |
| 願望形の要望（「〜しておきたいです」「〜を足したいです」） | 依頼・提案・質問の文末に直す（SKILL.md STEP 3） |
| 相手が知っている用語の中身の説明（`N+1` の後のクエリ数の内訳や「（100件で101クエリ）」の括弧書き） | 削る（SKILL.md STEP 2 原則1） |

### 例
- `` lintが落ちています。`permissions` に `members` scopeはありません（<ドキュメントのURL>） ``
- `` このAPIは `org:read` が要るので、`pull_request_target` のGITHUB_TOKENでは呼べないと思います。PATを別に発行するか、<代替案> にするのはどうでしょうか ``
- `` `timezone` を入れてください。入れないと <環境> では <ずれ方> になります（<ドキュメントのURL>） ``

## 3. レビュー返信 / 作業報告（自分のPRで）

指摘時よりやや柔らかく書く。**インラインコメントへの返信は短く（3-1/3-2）、自分から出す作業報告だけ構造化する（3-6）**。

### 3-1. 指摘への回答（意図どおり・仕様判断）

**結論を1文で言い切り、判断理由を1〜2文。全体3文以内・100字前後**。

- 冒頭は結論だけの独立行（`意図して実装しました。` / `意図した実装です。`）
- 3文を超える内容が要るときは論点ごとに段落を分け、段落間に空行を置く（1段落は2文まで）。1段落に詰めない
- **レビュアーの分析を復唱しない**（`ご指摘のとおり〜は〜です` は書かない。相手はコードを読んだうえで指摘している）
- **調査の証跡を貼らない**（`file:line`・経路の列挙・ログ）。調べた結果は結論に織り込むだけ
- 理由は1つに絞る。実装コスト・文言追加の手間などを積み増して正当化しない
- 採らなかった案は主体的に書く（`〜という選択はしませんでした`）
- 判断は「〜と判断しました」「〜にしました」と言い切る。「〜かなと思い」は判断の確度が読めない
- 確信が持てない点は議論で押し切らず、次にすることを書く（`念のため仕様を確認します。`）
- 見出し・太字・箇条書きを使わない（プレーンな段落）

#### 例
```
意図して実装しました。

そのまま送信しても受信側で既存のエラー画面が出るので、ここに新しく状態判定を入れる選択はしませんでした。
```
```
意図した実装です。

グループの管理者が変わっても、旧管理者が過去に行った同意は無効にならないと判断しました。念のため仕様を確認します。
```

### 3-2. 修正した指摘への返信

**短縮sha（7桁前後）＋「で修正しました」/「で対応しました」が基本形**。何をどう直したかは書かない（差分を読めば分かる）。

```
<sha> で修正しました
```

補足が要るときだけ1〜2文足す（`<既存ファイル> にあわせる形で <sha> で修正しました`）。

コミットURL形式も使うが、こちらはやや重い。**採らなかった判断や残した箇所を1〜2文添えるとき**に向く。

```
https://github.com/<org>/<repo>/pull/<n>/commits/<sha> で対応しました、ありがとうございます。

<採らなかった選択と理由を1〜2文>
```

### 3-3. 指摘を採らないときの返信

自分のPRで指摘を採らない・保留するときは、**直さない結論と理由を1文で書く**。保留なら、いつ・どこで扱うか（issue番号・後続PR）を添える。「あとで」「一旦放置」だけでは、次に何が起きるかが読み手に分からない。

- `型の整合は取れているので、このままにします`
- `時間がかかる処理ではないので、キャッシュは入れません`
- `トランザクションでロールバックされるので、問題ありません`
- `revertする可能性があるので、<issue番号> で扱います`
- `このPRの範囲外なので、<後続PR> で対応します`
- `<既存処理> との整合を優先して、このままにします`

却下してよいかどうかの**判断軸**は `~/.claude/context/code-review-checklist.md` §16（双方向で使う棄却類型）。本節はその結論を書くときの文体だけを規定する。

### 3-4. 受領・次アクション宣言
- `ありがとうございます！念のためupdate branchしてからマージします`
- close/保留判断（短く逃げ道付き）: `一度closeします、必要であればreopen / recreateしてください`
- closeは理由1行で: `急ぎのhotfixは不要なのでcloseします` / `<後続フェーズ>で回収するのでcloseします`
- 謝罪は感嘆符 + 🙇: `修正漏れです！<判断>したので削除しました` / `すみません！<経緯>` / `申し訳ありません、<観点>が抜けていたので<対応>しました`
- 他人のスレッドへの割り込みは `横からすみません 🙇` で入る

### 3-5. PR会話コメント（行コメント以外）
- `@メンション` は独立行で先頭に置く
- 相手の発言は `>` で引いてから答える（引用→回答を論点ごとに繰り返す）
- 返答の要らない補足は先頭で分かるようにする（`memo:`）。残作業は `TODO:` + チェックボックス
- bot / CIの呼び出しは1行だけ投げる（`/review` / `/devin review` / `@<review-bot> re-review` / `@dependabot <subcommand>`）

### 3-6. 自発的な作業報告は構造化
**指摘への返信ではなく、自分から出す報告（dependabot一括対応等）のみ**。見出し＋番号＋表。`**問題**:` → `**対応**:` → `**TODO**:` のラベル太字で因果を整理。
```
## dependabot一括更新に対する手動修正
### 2. tsc型エラー修正 (`<sha>`)
71パッケージ更新に伴い39件のtsc型エラーが出たので、次のとおり直しました。
| カテゴリ | 件数 | 対応 |
|---------|------|------|
| react-hook-form 判別共用体変更 | 35 | ... |
### 3. `<外部SDK>` を 3.19.4 に固定
**問題**: ESM-onlyパッケージを `require()` できず77テストスイートが失敗。…のため対応困難。
**対応**: `<外部SDK>` を `3.19.4` に固定。
**TODO**: Jest のESM対応と合わせて、別PRで個別に対応します。
```

## Markdownの書き方
- インラインコードを多用（パス・関数・変数・設定値・コマンドは必ず `` ` `` で囲む）
- 対応の要否のラベルは角括弧で先頭に置く（`[nits]` `[minor]`。2-2）
- チェックリストは担当主体を親項目にしてネストする（`- ローカル` / `- ユーザー手動確認` の下に `- [x]`）
- 対応関係は表、Slack依頼文/bot指摘/引用は `>` blockquote、運用注意は `> [!IMPORTANT]`
- リンクは `[ラベル](URL)`。公式ドキュメント・Slackスレッド・Jira・関連PR番号(`#<番号>`)を密に相互リンク
- 強調 `**…**` は要点語にピンポイント（乱用しない）
- 「やったこと」箇条書きは体言止め/常体（「〜を追加」「〜化」）、地の文・対人コメントは敬体
