# Slackの書き分け

Slackは相手と用途で文体を切り替える。社内では**社内の目上・公的（完全敬語）**と**業務の依頼・確認・報告（敬体で端的）**の2レジスタを使い分ける。社外の相手とのチャット（Teams・Slack Connect等）は**レジスタD**で書く。雑談・timesの投稿は本スキルの対象外。

挨拶を置くかどうかは、レジスタより先に会話の状態で決まる（SKILL.md「チャット（Slack・Discord）の共通規則」）。

- **新しく話しかけるとき**（スレッドの最初の投稿・初めての相手への連絡）: 各レジスタの書き出しで始める
- **続いているスレッドへの返信・DM のやり取りの続き**: 挨拶を置かず、受けた内容への返答か用件から入る。締めの「よろしくお願いします」も、依頼を含むときだけにする

---

## レジスタB: 社内の目上・公的（他部署/全社/事務局/上長）（完全敬語）

ビジネス敬語。**新しく話しかけるときは「お疲れ様です。」で開始 → 文脈1〜2文 → 「〜でしょうか。」で問う → 「よろしくお願いいたします」で締め**。絵文字は付けない（カスタム絵文字はワークスペースによって存在しない）。

名乗らず、「お疲れ様です。」だけで始める。名前と所属はSlackのプロフィールで分かる。「お疲れ様です」は社内の挨拶なので、社外の相手にはこのレジスタを使わない（レジスタD）。

### 構成: 文脈 → 問い（結論先行ではなく、背景を置いてから用件）

### 質問・確認の定型
- 「〜でしょうか。」「〜という認識／理解で良いでしょうか。」「〜してもよろしいでしょうか。」
- 許可は必ず可否を問う形にする。自分の理解を確認して合意を取る。

### 書き出しの例
```
<@担当者> san
お疲れ様です。
<対象環境>において<条件>の場合、<期待した挙動>が利用できないようなのですが、こちらは意図した制限でしょうか。
```
```
お疲れ様です、<対象>を対象として参加させていただきたいのですが、一点確認させてください。
```
- 依頼＋配慮: `こちら、何か操作方法が間違っていればご教示いただきたく、お手隙でご確認いただけますと幸いです`
- 依頼の締め: `お手数おかけして申し訳ありません、よろしくお願いいたします`
- お礼: `承知いたしました、ありがとうございます` / `素早いご対応ありがとうございました！！`

### 配慮表現（的確に、ただし要件は曖昧にしない）
「お手数ですが」「お手隙で結構です」「念のため」「（メンション失礼します）」を使う。配慮しつつ、可否・対象・期限は具体で書く。根拠リンク（Wiki/Notion/Slackパーマリンク/GitHub）を併記する。

### 事実・依頼が3つ以上なら構造化
用件と問いを先に1〜2文で書き、その下にネストした箇条書きを置く。親項目は要点を言い切る1文、値や理由は子項目にする（SKILL.md STEP 2 原則1）。
```
お疲れ様です。
<用件>について、<問い>でしょうか。

- <要点を言い切る1文>
    - <項目>: <値>
    - <項目>: <値>

お手数おかけしますが、よろしくお願いいたします
```
事象の報告では、箇条書きと `=>` で「期待値 vs 実測」を対比する。箇条書きは `- ` で書き、`•` を文字として打たない（描画される経路とされない経路は「MCP経由で投稿するとき・markdownのまま貼る下書きの書式」）。
```
事象の詳細です

- <画面A>で<操作> => 出る
- <画面B>で<操作> => 出ない
```

## レジスタC: 業務の依頼・確認・報告（自チーム/対等な実務相手）（敬体で端的）

敬体（です・ます）で書く。**新しく話しかけるときは「お疲れ様です。」で開始 → 用件 → 依頼 → 「よろしくお願いします。」で締め**。Bとの差は2つで、文脈の説明を省いて用件から入ることと、重い敬語（「いたします」「ご教示」「させていただく」）を使わないこと。依頼は「お手数ですが、〜をお願いします」「〜お願いします」（問いの形の依頼は SKILL.md STEP 3 のとおり使わない）。絵文字は付けない。

### 例（題材は架空）
```
お疲れ様です。
ディスク容量を拡張するため、検証環境のデータベースを停止します。

- 停止するのは明日の10時〜11時です
    - 延びる場合は、終了の見込みをこのスレッドで連絡します
- その間は検証環境へのデプロイを控えてください
    - 停止中に始めたデプロイは、マイグレーションの途中で失敗します
- 作業が終わったら、このスレッドでお知らせします

よろしくお願いします。
```
- 続いているスレッドでの返答: `確認しました、<対象>は<結果>でした`（挨拶なし）
- 催促: `本件何らかアップデートありますか？`
- 判断の共有: `既に離任されているようですが、<担当者>からつないでもらうのがよいという結論になりました`
- 回答・注意喚起: `postmanはアカウントを作るとエンドポイントやmessage bodyの情報が強制的にクラウドに同期されるので、そこだけ注意が必要です`
- 前提の問い返し: `「geminiを利用できる状態」=「GeminiシリーズのAPIを呼び出せる状態」ですか？`

### 続いているスレッドで、作業の権限を持つ相手に頼むとき

相手がマージ・リリース・承認などの操作を持ち、こちらは状況を知らせて動いてもらう場面。相手は同じ件の経緯を追っているので、知らせるのは「今どうなっていて、何をすれば解消するか」だけにする。メンションの後に状況と依頼を1文ずつ段落に分けて書き、箇条書き・コマンド・手順の番号は使わない。

- 状況は「何が反映され、何がまだで、その結果どうなっているか」を1文にまとめる。変更は PR 番号を並べず、中身の短い名前で呼ぶ（番号はリンクが運ぶ）
- 依頼は、相手が取る操作の結果で示す（「<PR のリンク> のマージで<あるべき状態>になりますので、早めにご対応いただけますと幸いです」）。マージや再実行の手順までは指示しない。どう動くかは操作を持つ相手が決める
- 相手が判断に使う事実がほかにあるとき（同じ相手の操作で解消する別の失敗など）だけ、付記の段落を1文置く。無ければ置かない
- 付記を含め、「こちらで実行してよいでしょうか」のような許可取り、コマンド、確認済みの報告、お礼の前置き、内部の識別子（ロックの ID・run の試行回数）、出所は書かない

## レジスタD: 社外とのチャット（顧客・取引先・ベンダー。Teams・Slack Connect等）（完全敬語）

敬語の重さはBと同じ。違うのは書き出しで、**「お疲れ様です」は使わない**（社内の挨拶で、社外の相手には馴れ馴れしく読める）。

- **続いているスレッドへの返信**: 挨拶も名乗りも置かず、受けた内容への返答から入る（「ご確認いただきありがとうございます。」「とんでもございません、こちらこそ〜」）。名前と所属は表示名で分かり、毎回の挨拶は往復のたびに冗長になる
- **新しくスレッドを立てるとき**: 「お世話になっております。」で始める。相手が自分を知らない可能性があるときだけ、読点でつないで名乗る（「お世話になっております、<所属>の<名字>です。」）
- 締めは「よろしくお願いいたします。」
- **同じ相手との過去のやり取りがあれば、その書き出しと締めを型にする**（この節の一般則より優先する）

### 相手の一覧に状況を返すとき（宿題・依頼の棚卸しなど）

相手が項目を並べて状況を尋ねてきたときは、相手が自分の一覧と突き合わせて読めることを優先する。

- **見出しは相手の番号と項目名をそのまま使う**。言い換えると、相手はどの項目への返事かを探し直すことになる。同じ件を指す項目は「② <項目名> / ⑤ <項目名>」と並べてまとめる
- **同じ件か確信が持てないときは、こちらで決めずに相手に尋ねる**。尋ねる理由も添える（「もし別件であれば片方を認識できていない可能性があるため、お手数ですがご教示いただけますと幸いです」）。こちらの解釈で統合すると、相手が持つ別件を落とす
- **状況は相手が知りたい段階まで書き、内部の経過は書かない**。「<相手先>の回答をお待ちしている状況です」「問い合わせ中です」で足りる。送った日付・自動応答・催促の予定・問い合わせの件数は、相手の次の行動を変えないので省く
- **待たせている件には詫びを添える**（「お待たせしており大変申し訳ありません」）
- **自分の動作は謙譲で書く**（「共有させていただきます」「再確認させていただきます」）。冒頭の詫びは「大変失礼いたしました」まで重くする
- **手を付けていない件は、未着手を詫びる文にせず、次にすることを書く**（「こちらについては担当者に再確認させていただきます」）
- **原因の見立ては、前に伝えた内容とつないで「〜と考えております」で書く**（「定例の中でもお伝えしましたが、<原因>ものと考えております」）。「未検証です」のような断り書きは付けない。根拠となる記載があれば、見立ての前に事実として並べる
- **Markdownの記号（`**` `-`）を使わず**、見出しの行と本文の行を改行で分け、項目の間に空行を入れる
- 添付があるときは、本文の最後の項目で触れる（「ひとまずこちらで<作業>させていただいた内容を添付いたします。ご確認いただけますと幸いです。」）
- 締めは、こちらの一覧から漏れている項目の指摘を頼む1文と「引き続きよろしくお願いいたします。」にする（「ほかに漏れているものがあれば、ご指摘いただけますと幸いです。」）。相手の一覧とこちらの一覧が食い違っている可能性を、相手が確認できるようにするため

## 共通の注意

- B・C・Dはどれも敬体。相手と立場で、敬語の重さと文脈説明の量を切り替える（B: 社内の目上、C: 自チーム・対等、D: 社外）。
- 質問への回答では、まず相手の前提を `=` で言い換え確認してから答えることがある（認識ズレ防止）。
- 締めはBが「よろしくお願いいたします」、Cが「よろしくお願いします」。
- 書き出しの「お疲れ様です。」は新しく話しかけるときだけ。続いているスレッド・DM のやり取りの続きでは置かない（冒頭の節）。
- 自嘲の `（）`・三点リーダの引き伸ばし・フィラー（`あと、` `たぶん` `一応` `なんか` `べつに`）は使わない（SKILL.md STEP 3）。
- **1メッセージの中でレジスタを混ぜない**。砕けた語り口（タメ口・「おまたせ」・「〜でどうでしょう」）と構造化装飾（太字見出し・表・番号付き節）を同居させると芝居がかった文になる。業務の報告（レジスタC）は敬体を保ったまま事実を並べ、装飾は箇条書きまでにする。

## MCP経由で投稿するとき・markdownのまま貼る下書きの書式

**目的: 箇条書き・強調・コード・引用が、受け手の画面でネイティブの書式として描画される状態で届ける。** 記号を文字として打った箇条書き（`•` `◦` の直書き）や、変換されずに文字のまま残った箇条書きは、階層の無い平坦なテキストになる。

Slack MCPの送信ツール（`slack_send_message`）と下書き作成ツール（`slack_send_message_draft`）はどちらも `blocks` を受け付けず、`message`（markdown文字列）だけを取るが、**保存される書式が経路で異なる**:

| 経路 | 書式の扱い | 乗せてよい文 |
|---|---|---|
| 送信ツール | 標準markdownをネイティブ書式に変換する（`- ` とインデントの箇条書き、`_斜体_`、`` `code` ``、コードブロック、引用、リンク） | 構造を持つ文を含む全て |
| 下書き作成ツール | レガシーのプレーンテキスト書式で保存する。強調は変換されるが、**箇条書きは文字の `•` に変換される** | 段落だけの文（箇条書き・見出し・表を含まないもの） |

- 箇条書きは `- ` とインデントで書き、`•` `◦` を文字として打たない（送信ツールが変換するのはこの形）
<!-- publish:omit -->
- Slack.app のセッションで投稿する経路（`slack-app-mcp` の `slack_post`・`slack_update`）は、本文を `chat.postMessage` の `markdown_text` で送り、標準 markdown をネイティブの箇条書きとして描画する。文案は送信ツールと同じ形（`- ` と4スペースの字下げ）で書き、`<@U...>` のメンションと `<URL|語>` のリンクもそのまま使える
  - `•`・`◦` を文字として打った行は、ネイティブの箇条書きにならない（字下げした記号付きの文字列として表示される）
<!-- /publish:omit -->
- 箇条書きの前後には空行を1行置く。文の行の直後に空行なしで `- ` の行を続けると、箇条書きにならず `- ` が文字のまま表示される。箇条書きの直後の文の行も、空行が無いと最後の項目の続きとして扱われる
- 入れ子の子項目は、親の行より4スペース下げる。Slack の markdown 変換は2スペースの字下げを入れ子と見なさず、全項目を同じ階層に並べる。ユーザーが markdown のまま Slack に貼る下書き（<!-- publish:omit -->taskboard の文書・<!-- /publish:omit -->チャットの本文）も同じ変換を通るので、同じ字下げで書く
- ユーザーグループのメンションは `<!subteam^グループID>` 形式で書く
- ツールの変換挙動は版で変わる。初めて使う経路・ツールの版が変わった後は、構造を持つ文を検証先に1度送って画面で描画を見る（ドキュメントの記載は実機の挙動を保証しない。AGENTS.md「事実の扱い」の、新しく使う設定値を実機で1回試す規則と同じ扱い）

### 承認が必要な投稿（対外・公的なもの）の経路

内容の承認と描画の実物確認を両方満たす経路を、文の形で選ぶ:

- **段落だけの文**: 下書き作成ツールを使う。チャンネルの下書き欄に入り、本人が画面で確認・編集して自分で送れる
- **構造を持つ文（箇条書き・見出し・表）**: 下書き経路に乗せない（書式が正しく描画されない状態のものを承認することになる）。次の順で進める
  1. 本文をチャットで提示する（各文の出所を添える。AGENTS.md「事実の扱い」）
  2. 送信ツールで検証先へ投稿し、本人が画面で描画と内容を確認する。描画が意図と異なれば修正して再投稿する。検証先は自分宛DMでよい（送信ツールの宛先に自分のuser_idを渡せる）。使えないワークスペースでは本人だけが見る場所を1つ決めておく
  3. 確認が取れてから、本番の宛先へ送信ツールで投稿する。本番への投稿は名指しの承認を受けてから行う（AGENTS.md「確認が必要なもの」の外に出る作用）
