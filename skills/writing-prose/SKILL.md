# writing-prose

読み手が一度読めば分かる日本語と英語の文章を書く。判断の軸は「読み手にとってわかりやすくなるか」で、書き手の過去の文の癖を再現することは目的にしない。本人の代わりに書く文章も、本人の文の癖ではなく本スキルの規則で書く。

AIが書く文章は、予告とまとめの言い直し、難しい語、翻訳調、自明なことの説明、働きの読めない文末で読みにくくなる。本スキルはこれを書く段階で避ける。

## 対象

- **対象**: 日本語の文章と、運営間チャットなどで書く英語の文章。特にPR概要欄 / GitHubレビュー（指摘・返信）/ Slack・Discordのメッセージ / Confluence等のドキュメント / 対外ビジネスメール。
- **対象外**: コミットメッセージ（`/commit` スキルの git-cz 形式に従う）。コードコメント・docstring（`/writing-code` スキルに従う）。画面に出る文言（ラベル・ボタン・見出し・空状態・エラー文。文章とは別の規約に従うため `/writing-ui-text` スキルを実行する）。

## STEP 1: 読み手・媒体・用途を決める

最初に「誰に・どの媒体で・何の用途で」を決め、下表で文体と参照先を決める。読み手が期待する文体（敬語の重さ・挨拶の有無・構造）に合わせると、読み手は形に引っかからず中身を読める。

| 場面（媒体・用途） | 相手 | 文体 | 詳細 |
|------|------|------|------|
| Slack: 社内の目上・公的 | 他部署・上長・全社/事務局宛 | 完全敬語。新しく話しかけるときはお疲れ様です→〜でしょうか→よろしくお願いいたします。名乗らない。続いているスレッドでは挨拶を置かない | @references/slack.md |
| チャット（Teams・Slack Connect等）: 社外 | 顧客・取引先・ベンダー | 完全敬語。続いているスレッドでは挨拶も名乗りも置かず、受けた内容への返答から入る。新しくスレッドを立てるときは「お世話になっております。」で始める。「お疲れ様です」は使わない | @references/slack.md |
| Slack: 業務の依頼・確認・報告 | 自チーム・部下・対等な実務相手 | 敬体で端的に。新しく話しかけるときはお疲れ様です→用件→よろしくお願いします。続いているスレッドでは用件から。重い敬語と絵文字は使わない | @references/slack.md |
| Discord: 運営・コミュニティのチャンネル | 運営メンバー・コミュニティの参加者 | 敬体で端的に。挨拶を置かず用件から入る。英語のチャンネルは下の英語の行 | 下の「チャット（Slack・Discord）の共通規則」 |
| GitHub: レビュー指摘（行コメント） | 同僚PR作者 | 1指摘1コメント。事実は言い切り、推測は根拠を添えて一度だけ示す。一次ソースのURLと代替案を添える | @references/github.md |
| GitHub: レビュー本文 / approve | 同僚PR作者 | 交通整理と結論だけで1〜2文。指摘の中身は書かない。指摘なしは `LGTM` | @references/github.md |
| GitHub: 指摘への回答 | レビュアー | 結論1文＋理由1〜2文で3文以内。証跡・復唱・箇条書きなし | @references/github.md |
| GitHub: 指摘の却下・保留 | レビュアー | 直さない結論と理由を1文。保留ならどこで扱うかを添える | @references/github.md |
| GitHub: 修正報告/受領 | レビュアー | 「`<sha>` で修正しました」。補足が要るときだけ1〜2文 | @references/github.md |
| GitHub: 自発的な作業報告 | レビュアー | 見出し＋番号＋表で構造化 | @references/github.md |
| GitHub: PR概要欄 | レビュアー全般 | 固定見出しテンプレ。「やらなかったこと」を立てる | @references/github.md |
| Confluence: 設計書・思考整理・負債メモ・リサーチ | 自分・チーム内 | 常体。代替案＋採用理由をセットで | @references/confluence.md |
| Confluence: 対外告知・手順・相談 | 他チーム・Biz | 敬体。目的提示＋各ステップに理由 | @references/confluence.md |
| メール: 対外ビジネス（協賛打診・取引先・業者・参加者） | 社外の企業担当者等 | 完全敬語。宛名（新規=社名+名字様/リプライ=名字様のみ）・読点1文名乗り・定型骨格に従う | @references/email.md |
| フォーラム: コミュニティサイトの告知・スレッドのクローズ | サイト利用者 | 敬体で改まった定着語（移行・〜に伴い）。役職つきで名乗り、変わること/変わらないことを親1文＋子項目で | @references/forum.md |
| 運営チャット: 告知文面の合意形成 | 運営メンバー | 成果物のラベル＋URL一覧 → `--------` → 作業の宣言 → コードブロックの文面 | @references/forum.md |
| 英語: 国際的なコミュニティの運営間チャット・技術者間のやり取り | 他チームの運営者・技術者 | チームを代表して短い文で。用件を1行目に、事実は言い切り知っている範囲を明示、提案は具体案まで出して採否を相手に返す | @references/english.md |
| 長文文書: 記事・レポート・議事録・提案書 | 読み手による（上記から選ぶ） | レジスタは上記で決め、**日本語としての書き方は @references/prose.mdの長文層と工程に従う** | @references/prose.md |

迷ったら、相手が**社外**なら社外向けの完全敬語（チャットはSlack D、メールはemail.md）、**社内の目上・公的**なら完全敬語（Slack B）、**自チーム・対等な実務相手**なら敬体の端的な文（Slack C）、**自分用メモ・チーム内の思考整理**なら常体を選ぶ。
**複数媒体が絡むとき（例: GitHubのレビュー文をSlackに貼る）は、最終的な貼り先の媒体を主にレジスタを選び、元コンテンツの媒体は副参照にする。**

### チャット（Slack・Discord）の共通規則

- **挨拶**: 続いているスレッドへの返信・DMのやり取りの続き・Discordでは、挨拶を置かず用件から入る（往復のたびに挨拶があると冗長になるため）。社内の人へ新しく話しかけるとき（スレッドの最初の投稿・初めての相手への連絡）は「お疲れ様です。」で始める。社外とのチャットは references/slack.md のレジスタDに従う
- **並ぶ事実・依頼が3つ以上**なら、ネストした箇条書きにする（STEP 2 原則1）。`- ` とインデントで書き、`•` を文字として打たない
- **リンク**は実際のURLを埋める。スレッド・PR・ドキュメントを開いて取り、`<リンク>` のような置き場で済ませない
- **下書きはコードブロックで包まない**（ワークフロー末尾の「下書きの出し方」）

## STEP 2: わかりやすさの原則

レジスタに関わらず、すべての文章で守る。

1. **結論・用件を先に置き、短く書く。自明なことは書かない。** 「説明しなくても伝わること」は削る。前置き・能書き・まとめの再説明をしない。一文に論点を詰め込みすぎない（日常メッセージは1行で切る）。
   - **相手が知っている用語の中身を言い直さない。** `N+1` と書いたら「100件で101クエリ」のような括弧書きの言い換えも付けない
   - **見出しや箇条書きの直前に、導入文・まとめ文を置かない**（「原因は2つある」「原因ごとに1案ずつある」の類）
   - **並ぶ事実・依頼が3つ以上なら、ネストした箇条書きにする。** 第一階層は太字のラベル（`**停止**` `**お願い**`）にし、中身を子項目に置く。Slackのメッセージも同じ。長文では見出しの下にこの形で置く
   - **読み手にしてほしいこと（返答・判断・作業）があれば、それを1文で書く。** 何を・いつまでにが分かる形にする。状況だけを伝えて終えると、読み手は自分が動くべきかを推し量ることになる
2. **難語・翻訳調を避ける。** 和語・口語で書く。「〜することが可能です」→「〜できます」、「〜に関しまして」→「〜について」、「活用」「実施」「対応」の乱用を避ける。ただし**専門用語は原語のまま `code` 表記で正確に**（無理にカタカナや和訳にしない。例: `auto mode` `worktree` `org:read`）。
3. **事実・要件は具体で、曖昧にしない。** 件数・対象・可否・パス・コミットハッシュ・session_idは具体で書く（「39件のtsc型エラー」「496 pass / 0 fail」）。「いくつかの」「適宜」「必要に応じて」で濁さない。
4. **事実と推測と意見を書き分ける。** 事実・仕様と、コードや一次ソースで確かめたことは言い切る。推測は根拠を添えて「〜だと思います」と一度だけ示し、「〜ではないかと思います（おそらく）」のように重ねない。確かめられる事実は、推測の形で書く前に確かめる。意見・提案は提案の形で書く（STEP 3）。読み手が文末だけで確度を読み取れるようにするため。
5. **非自明なことには理由を併記する。** 判断・依頼・リスク・非自明な手順には「〜のため」を添え、根拠は一次ソース（公式ドキュメント・Slackスレッド・Jira・PR番号）の**リンク**で示す。**ただし原則1と両立させる**: 既知の文脈・自明な手順・軽い連絡では理由を書かず省く。「念のため理由を全部書く」のはAIの冗長癖なので避ける。
   - **理由は結論より前に畳んで一文にする。** 「〜です。〜ので。」と理由を後置きの断片で足さない（言い訳を付け足したように読める）。「〜ので、〜です／〜します」の順で書く。
   - **理由は事実で書く。** 「〜したいため」のように書き手の希望を理由にしない。希望の元になっている事実（「原因が別なので」「CIが止まっているので」）を書く
6. **スコープを明示する。** PR概要・設計書などの構造物では、やったこと/やらなかったこと、検討した代替案/採用理由をセットで残す。軽いSlack・レビュー返信には適用しない（冗長になる）。
7. **読み手と立場でレジスタを切り替える**（STEP 1）。

## STEP 3: 文末で文の働きを示す

日本語は主語を省くことが多く、文末が「誰が動くのか」「決まったことか、頼みか、提案か」を伝える。文末を選ぶ前にその文の働きを決め、次の形で書く。

| 働き | 文末の例 |
|---|---|
| 事実・状態 | 〜です／〜しています／〜でした |
| 自分の判断・予定 | 〜します／〜にしました／〜と判断しました |
| 依頼（相手にしてほしい変更・作業） | 〜してください／〜をお願いします／〜していただけますか |
| 提案（採否は相手が決める） | 〜するのはどうでしょうか／〜がよいと思います |
| 相手の意図・判断を問う | 意図して〜していますか／〜で問題ないでしょうか |
| 推測 | 〜だと思います／〜の可能性があります（根拠を添える） |

- **願望形（〜したいです・〜しておきたいです・〜したいため）は、書き手の希望そのものを伝えるときだけ使う。** 依頼・提案・判断・理由を願望形で書くと、誰が動くのか、決まったことか希望かが文末から読めない（「先に直したいです」→「先に直します」、「timezoneを入れておきたいです」→「timezoneを入れてください」）
- **働きが一度で読めない文末を使わない。**
  - 「〜の判断でしょうか」: 意図を問うなら「意図して〜していますか」、要否を問うなら「〜は不要でしょうか」と分ける
  - 「〜となります」「〜という形になります」: 「〜です」「〜します」で足りる（フォーラムの告知で定着した「〜に伴い〜は終了となります」のような改まった言い方は references/forum.md に従う）
  - 「〜かなと思い」「〜な気がしています」: 判断なら「〜と判断しました」、推測なら根拠と「〜だと思います」
- **フィラー（「あと、」「たぶん」「一応」「なんか」）を置かない。** 情報を足さず、確度を曖昧にする。確度を示すなら原則4の形で一度だけ書く
- 同じスレッドや同じ相手の過去の投稿を型にするとき（ワークフロー1）も、文末とフィラーはこのSTEPで決める。過去の投稿の癖を写し直さないため

## STEP 4: AIの書き方の直し方

AIが書きがちな文と、その直し方の対比。推敲時はこの方向に直す。

| AIの癖（直す対象） | 直し方 |
|---|---|
| 「本対応につきましては、以下の通り実施いたしました」 | 「やったこと」を箇条書きで即列挙 |
| 「〜することが可能となっております」 | 「〜できます」 |
| 「ご確認のほどよろしくお願いいたします」（毎回フル定型） | 自チームなら「ご確認お願いします」。対外なら定型でOK |
| 結論前に長い背景説明 | 用件・結論を先に（社内の目上・社外のチャットは「文脈1〜2文→問い」も可）。冗長な前置きは削る |
| 全項目を均等に詳しく書く | 要点だけ `**強調**`。自明な項目は1行 or 省略 |
| 難しい漢語で言い換え（「具備」「鑑みる」「俯瞰」） | 平易な語（「ある」「考えると」「全体を見る」） |
| 意見を事実の形で書く（「〜すべきです」） | 意見・提案と分かる文末にする（「〜がよいと思います」「〜するのはどうでしょうか」） |
| 推測を重ねる（「〜ではないかと思います（おそらく）」） | 根拠を添えて一度だけ（「〜なので、〜だと思います」） |
| 願望形で依頼・判断・理由を書く（「〜しておきたいです」「先に直したいです」「別に扱いたいため」） | 依頼は「〜してください」、判断は「〜します」、理由は事実（「原因が別なので」） |
| 結論を言い切ってから理由を別文で後置き（「〜にします。〜が見つからないので。」） | 理由を前に畳んで一文にする（「〜が見つからないので、〜にします」） |
| 読点の代わりに全角スペースで区切る | 読点か句点で切る |
| 絵文字を機械的に大量装飾 | 付けない。GitHubのお詫びにだけ 🙇 を1個添えてよい。Slackのカスタム絵文字（`:bow-nya:` 等）はワークスペースによって存在しないので使わない |
| 「以上、ご査収ください」等の堅い締め | 自チームは「よろしくお願いします」、対外は「よろしくお願いいたします」 |

## 日本語としての書き方は @references/prose.md

STEP 2〜4は「何を書くか・どう振る舞うか・文末をどう選ぶか」を決める。**「日本語としてどう書くか」（LLM口調の語彙・論証の厳密さ・演出の抑制・段落の作り方・整形）は @references/prose.md** と `/yomiyasu` スキルが定める（分担は次節）。prose.mdの適用する層は成果物の種別で決まる。

| 成果物 | prose.mdで適用する層 |
|---|---|
| Slack、GitHubのレビュー指摘と返信 | 共通層のみ |
| PR概要欄、負債メモ、リサーチメモ | 共通層 + 原則6（スコープの明示） |
| 設計書・手順・告知・記事・レポート・議事録・提案書 | 共通層 + 長文層 + 工程 + 完成時の外部レビュー |

**規則が衝突したときの優先順位**: 事実性と安全 → 媒体固有のレジスタ（STEP 1のreference）→ STEP 2〜4、prose.mdの共通層と `/yomiyasu` → prose.mdの長文層と整形。

### 書き上げた日本語の推敲は `/yomiyasu` に任せる

本スキルは書く前と書いている間（何を、どの文体・構造・文末で書くか）を受け持つ。書き上げた日本語の推敲（統語の復元＝誰が・何を・どうした、非生物主語と比喩動詞の書き換え、前置きフィラーの削除、ダッシュの除去）は `/yomiyasu` スキルが担う。`/yomiyasu` は文の働きを保って直すので、願望形のような文末の選び方は直さない。文末は書く段階でSTEP 3に従って決めておく。

下書きを書き終えたら `/yomiyasu` スキルを実行して推敲する。呼ぶときは、推敲する下書きのパスか本文を引数で渡す（名前だけで呼ぶと、直前の返答や作業フォルダのファイルを推敲の対象に選ぶため）。`skills/yomiyasu/` は外部リポジトリの無改変コピーなので、本スキルと食い違う規則はここで上書きする（コピー側は編集しない）。

和欧文間の半角空白は本スキルで扱う。日本語と英数字のあいだに半角空白を入れない（`/yomiyasu` は空白を原文のまま保つ）。コード・コマンド・URLの中の空白と、太字を表示させるための空白は残す。

| `/yomiyasu` の規則 | 本スキルから呼ぶときの扱い |
|---|---|
| 「類似スキルを無効化する」注意書き | 適用しない。併用時の優先順位は上の段落で決まっている |
| 書き直す前の問い（文書の種類・読者・読み手との関係） | 問わない。本スキルから呼ぶときは「ほかのスキルの途中」に当たる。文書の種類は下の行のとおり渡し、読者と読み手との関係は渡さない |
| 文書の種類（`--doc-type`） | STEP 1 の場面で決めて渡す。Slack・Discord・チャット・メールは `mail`、PR概要欄は `pr`、議事録は `minutes`、提案書は `proposal`、手順書は `manual`、記事は `article`。レビュー指摘・返信、設計書、フォーラムの告知は渡さない |
| ペルソナと敬語（読み手との関係を渡すと敬語を引き上げる。詫びを「申し訳ございません」にそろえる） | 適用しない。敬語の重さは STEP 1 のレジスタと媒体の reference で決める |
| `mail` の「ご〜させていただく」を「〜いたしました」に直す規則 | 適用しない。email.md と slack.md の定型（「ご相談させていただきたく」など）を残す |
| 出力フォーマット（「書き直した本文」「変えたところ」「残したAIっぽいところ」「書き手に確かめたい点」「事実の確かめ」「確認の記録」） | 使わない。本スキルの「下書きの出し方」で出す。事実の出所は AGENTS.md「対外に出す下書き」の並記で示す |
| 事実の確かめ（資料にない値・主張を書き手への問いで返す） | 問いをユーザーに回す前に、自分で一次情報（スレッド・PR・チケット・ファイル・MCP の取得結果）を開いて埋める。開けなかったものだけを問いとして残す |
| 相対の日付（昨日・先週）に日付を添える | 長文文書だけで適用する。Slack・GitHub・メールの短文には添えない |
| 小説・随筆のダッシュを残す | 適用しない。ダッシュは種類によらず外す（prose.md §3-1） |
| 太字のラベルとコロンで始まる箇条書き（ラベルを外して1文にする。2つ以上重なれば太字を外す） | 適用しない。第一階層の太字のラベル（STEP 2 の原則1）と「**用語**：説明」（prose.md §3-1）は残す |
| 絵文字・補足カッコの排除 | Unicode絵文字（GitHubの 🙇 など）はレジスタに従って残す。Slackのカスタム絵文字は使わない（ワークスペースによって存在しない）。補足カッコのうち、指す内容を特定する同格挿入（prose.md §3-3）は情報を足すので残す |
| 言い切りの強さの保持（推量・可能性の語尾をそのまま残す） | STEP 2の原則4で一度だけ置いた推測の語尾は残す。根拠を持たない緩和は prose.md §2-1 に従って削る |
| 主語と目的語の明確化（前後にある語の補完） | 補うのは、文単体で動作主や対象を取り違えられる箇所だけ。見出し・前の文・親の箇条書きから分かる主語は補わない。推敲後に原文より長くなった文は、補った語が誤読を防いでいるかを見直し、防いでいない語は削る（原則1「短く」が優先する） |
| 箇条書きを地の文に統合、箇条書き比率の上限（tech domainの15%、lintの比率警告） | 適用しない。構造を持つ内容（3項目以上の並列、手順、条件と例外、親子関係）は箇条書きにし、階層はネストで示して1項目を1〜2文に収める。地の文で書くのは、前の文を受けて一方向に進む論証だけ。媒体テンプレが定める構造（PR概要欄の見出しと箇条書き、作業報告の表）もそのまま残す |
| 文書の立場と文末（勧め・決まり・説明による文末の整理） | 敬体／常体はレジスタに合わせる。文末の形はSTEP 3で決め、`/yomiyasu` は文の働きを保つ範囲で直す |
| ドメイン判定（tech / business / essay） | 長文文書に限って行う。記事・設計書・手順はtech、PR概要欄・レポート・議事録・提案書はbusiness、個人の記事・雑記はessay |
| 検査（Step 2 の原文の lint、Step 3 の `scripts/yomiyasu_check.py run`、Step 5 の `verify`） | 長文文書をファイルに書いたときだけ実行する。Slack・レビュー返信などの短文では実行しない。検査の記録には原文と最終稿の全文が残るので、`--state-dir` でメモリディレクトリの `yomiyasu/`（メモリディレクトリが無ければ scratchpad）に向ける（既定の置き場は作業中のリポジトリの最上位） |

`slop-catalog.md` §3の語（「突き合わせる」「既定」「照合」など）は、比喩として使われているときだけ直す。字義どおりの用法は書き換えない。

### 英語の推敲は `/humanizer` に任せる

英語の文章では、STEP 2の原則2（和語・口語）、STEP 3、prose.md、`/yomiyasu` を適用しない。代わりに、下書きを書き終えたら `/humanizer` スキルを実行して推敲する。`skills/humanizer/` は外部リポジトリの無改変コピーなので、本スキルと食い違う規則はここで上書きする（コピー側は編集しない）。

| `/humanizer` の規則 | 本スキルから呼ぶときの扱い |
|---|---|
| What to return（下書き・残った癖の一覧・最終版を返す） | Embedded modeとして扱い、最終版だけを本スキルの「下書きの出し方」で出す |
| Voice（書き手の文例に合わせる） | @references/english.md を書き手の文例として渡す。同ファイルの型は humanizer の各パターンより優先する |
| §19 太字のラベル | 英語では太字のラベルを付けない。3項目以上の並列は、太字なしの行を並べる（STEP 2原則1のラベル付き箇条書きは日本語にだけ適用する） |
| §9 修飾の重ね | 推測の示し（`I think` `as far as we understand`）は、STEP 2の原則4として1つだけ残す |
| §22 チャットボットの名残（`let me know` など） | 締めの申し出は、追加で出せるものを具体的に挙げた1文だけ残す（english.md 2-1）。中身の無い申し出は削る |

## ワークフロー

文章を書く・直すよう頼まれたら:

1. **STEP 1** で「相手・媒体・用途・最終的な貼り先」を確定し、文体と参照先referenceを決める。**貼り先に既存のやり取り（同じスレッド・同じ相手との直近の投稿）があれば、その書き出し・締め・構造を型にする**（媒体の一般則より、そこで実際に使われている形が優先。取得済みで手元にあるものを見ずに書き始めない）。文末とフィラーは型にせず、STEP 3で決める。情報が足りなければ確認する。複数媒体が絡むときは貼り先の媒体を優先する。
2. 該当referenceを読み、その場面のテンプレに沿って書く。**長文文書なら @references/prose.mdも読み、設計（読み手と主メッセージ・見出しスケルトン・濃淡）を先に済ませてから本文に入る。**
3. **STEP 2**で全体を点検する（特に「結論が先か」「具体か」「事実と推測の書き分け」）。**STEP 3**で各文の文末を働きに合わせる。
4. **STEP 4** の方向に直し、AIっぽさを削る（英語の文章は、この手順の代わりに `/humanizer` スキルを実行する。扱いは「英語の推敲は `/humanizer` に任せる」の表）。**`/yomiyasu` スキルを実行して推敲し（扱いは「書き上げた日本語の推敲は `/yomiyasu` に任せる」の表）、@references/prose.mdの共通層（LLM口調の語彙カタログ）で本文を検索して該当箇所を書き直す。**
5. PR概要・ドキュメント等の構造物は、referenceのテンプレ見出しを踏襲する。
6. **人に共有・公開する長文は、書き上げたら外部レビューに出す**（対象・Severity・ラウンド上限は @references/prose.md「完成時の外部レビュー」、実行手順は `~/.claude/context/agent-cli-guide.md`）。自分で読み直すだけでは、書いたときと同じ判断を繰り返すだけで前提の抜けに気付けない。

### 下書きの出し方

下書きは貼り先の書式（Slack・Discord・GitHub の Markdown）のまま本文として出し、コードブロックで包まない。リンクは実際の URL を埋める（スレッド・PR・ドキュメントを開いて取る）。取れない値だけ `<...>` で残し、何が取れなかったかを1行添える。

例外は references/forum.md の運営チャットの合意形成で、告知文をそのまま見せるために文面をコードブロックに入れる。
