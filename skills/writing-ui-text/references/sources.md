# 規則の出典と、食い違う論点の採否

SKILL.mdの規則がどの公開ガイドラインに基づくかと、ガイドライン同士が食い違う論点でどちらを採ったかを記す。規則を変えるときは、ここの採否理由が今も成り立つかを先に確かめる。

## 目次

- 参照したガイドライン
- 一致している規則
- 食い違う論点と採否
- ガイドラインに明文が無く、導いた規則

| DADS | デジタル庁デザインシステム（インプットテキスト・ボタン・モーダルダイアログ） | https://design.digital.go.jp/dads/components/ |

## 一致している規則

| 規則 | 根拠 |

## 食い違う論点と採否

### ボタンの語形

- SH: 動詞の終止形。「漢語＋する」は「する」を省く（「追加」が可、「追加する」は不可）
- MS: コマンドボタンは体言止め。汎用的に使われてきた語は「選択」ボタンのように漢語のまま
- Ap: 動詞を使う。例は「送信」「削除」「消去」

**採用: 和語は終止形、「漢語＋する」は「する」を省く。** 3者とも「保存」「削除」の形で一致する。「保存する」の形を明示的に勧めるソースは無い。「体言止めは操作か状態か紛れる」という懸念は、ボタンという部品の形が操作であることを示すので当たらない。状態はボタンでなくラベルで示す。

### 見出しとボタンの区別

- SH: 見出しは「{対象}の{操作}」、ボタンは「{対象}を{操作}」と助詞で区別する
- MS・Ap: 規定なし

**採用: SH。** 助詞で役割が区別でき、ダイアログのタイトルとボタンの操作名を機械的に揃えられる。

### 失敗の書き方

- SH: 「{対象}の{操作}に失敗しました」
- MS: 「〜できません（でした）」
- Ap: 「コンテンツを読み込めません」

**採用: 「〜できませんでした」。** ユーザーが何をできなかったかを主語なしで書け、短い。「失敗」はシステムの視点の語で、3要素の「事象」はユーザーにとって何が起きたかを書くというSH自身の説明とも合う。ただしPJが「〜に失敗しました」で統一済みなら変えない（混在のほうが害が大きい）。仕様として不可の文型（「〜は〜できません」）と上限の文型はSHのものをそのまま使う。

### プレースホルダー

- SH: 入力例・説明をプレースホルダーに書かない（必須）
- DADS: サポートテキストの代わりにプレースホルダーを使ってはならない
- Ap: ヒントやプレースホルダーで入力形式を示す

**採用: 説明と入力例はプレースホルダーに書かない。** 入力を始めると消えること、薄い文字が読みにくいことが理由。Apが勧めているのは `name@example.com` のような書式の見本で、Ap自身もラベルを別に付けるとしている。書式の見本だけは許す。

### 入力エラーを出す時点

- SH: 入力欄からフォーカスが外れたとき、または送信時
- DADS: 送信時が望ましく、フォーカスが外れたときの表示は避ける

**採用: 文言の規則としては定めない。** 挙動の規定であり、PJの部品の実装に従う。

### 必須・任意の印

- DADS: 「※必須」「※任意」をラベルに付ける
- SH: 「入力必須」と書く

**採用: PJで1つに決める。少ない方にだけ印を付ける。** 全項目に印を付けると印が情報を持たなくなる。

### 英数字と日本語の間の空白

- SH: 入れない
- MS: 半角の空白を入れる

**採用: 入れない。** 日本語のWebサービスの画面では入れない表記が多数で、幅の狭いボタン・ラベルで空白が語の切れ目に見える。PJが入れる方式で統一済みなら変えない。

### 疑問符・括弧・コロンの幅

- SH: 全角。「？」の後に文が続くときは全角の空白
- MS: 半角

**採用: 全角（SH）。** 日本語の文中で半角の記号は前後の字と詰まって見える。

### 操作の語（クリック・押す）

- SH: 「押す」（リンクは「開く」）
- MS: 例文は「クリック」
- Ap: タッチ端末で「クリック」を使わない

**採用: 「押す」「開く」。** 端末を問わない。

### 二人称

- SH: 権限エラーの文例に「あなたのアカウント権限では」がある
- MS: 省略を先に検討し、「あなた」は慎重に使う
- Ap: 所有代名詞を多用しない

**採用: 省く。** 日本語は主語なしで通じる。

### カタカナ語

- SH: 漢字語への言い換えを先に検討する
- MS: 日常的な語を優先する（「アプリ」）

**採用: 利用者に通じるほうを使う。** 両者の方向は同じ（平易な語）。言い換えた漢字語のほうが通じにくい場合は言い換えない。

## ガイドラインに明文が無く、導いた規則

**「仕組みの説明を画面に書かない」** を直接定めた条文は、上の5つには無い。次から導いている。

- 公: 「伝えることを絞る。副次的な内容は、別に対応する」
- SH: 入力時にユーザーが把握しなくても操作に影響のない情報は、説明文と分けて補足に置く
- DADS: サポートテキストには入力形式の条件や例を書く。読まなくても進められる補足は別の部品に置く
- Ap: 設定の説明は、オンにすると何が起きるかを書く。オフのときに起きないことは書かなくてよい
- MS: ユーザーが課題を達成するために知るべきことを考える

判定の基準を「その文を消しても、読む人の次の操作と判断が変わらないか」に置いたのは、上の5つがいずれも「操作に要るかどうか」で情報を分けているため。
