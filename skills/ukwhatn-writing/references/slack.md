# Slackの書き分け

Slackは相手と用途で文体を切り替える。社内では**社内の目上・公的（完全敬語）**と**業務の依頼・確認・報告（敬体で端的）**の2レジスタを使い分ける。社外の相手とのチャット（Teams・Slack Connect等）は**レジスタD**で書く。雑談・timesの投稿は本スキルの対象外。

---

## レジスタB: 社内の目上・公的（他部署/全社/事務局/上長）（完全敬語）

ビジネス敬語。**「お疲れ様です。」で開始 → 文脈1〜2文 → 「〜でしょうか。」で問う → 「よろしくお願いいたします」で締め**。絵文字は付けない（カスタム絵文字はワークスペースによって存在しない）。

名乗らず、「お疲れ様です。」だけで始める。名前と所属はSlackのプロフィールで分かる。「お疲れ様です」は社内の挨拶なので、社外の相手にはこのレジスタを使わない（レジスタD）。

### 構成: 文脈 → 問い（結論先行ではなく、背景を置いてから用件）

### 質問・確認の定型
- 「〜でしょうか。」「〜という認識／理解で良いでしょうか。」「〜してもよろしいでしょうか。」
- 許可は必ず可否を問う形にする。自分の理解を確認して合意を取る。

### 実例（骨格）
```
<@担当者> san
お疲れ様です。
<対象環境>において<条件>の場合、<期待した挙動>が利用できないようなのですが、こちらは意図した制限でしょうか。
```
```
お疲れ様です、<対象>を対象として参加させていただきたいのですが、一点（念の為）確認させてください。
```
- 依頼＋配慮: `こちら、何か操作方法が間違っていればご教示いただきたく、お手隙でご確認いただけますと幸いです`
- 依頼の締め: `お手数おかけして申し訳ありません、よろしくお願いいたします`
- お礼: `承知いたしました、ありがとうございます` / `素早いご対応ありがとうございました！！`

### 配慮表現（的確に、ただし要件は曖昧にしない）
「お手数ですが」「お手隙で結構です」「念の為」「（メンション失礼します）」を使う。配慮しつつ、可否・対象・期限は具体で書く。根拠リンク（Wiki/Notion/Slackパーマリンク/GitHub）を併記する。

### 事実・依頼が3つ以上なら構造化
用件と問いを先に1〜2文で書き、その下にネストした箇条書きを置く。第一階層は太字のラベル（`**追加したい内容**`）、中身は子項目にする（SKILL.md STEP 2 原則1）。
```
お疲れ様です。
<用件>について、<問い>でしょうか。
- **<ラベル>**
  - <項目>: <値>
  - <項目>: <値>

お手数おかけしますが、よろしくお願いいたします
```
事象の報告では、箇条書きと `=>` で「期待値 vs 実測」を対比する。箇条書きは `- ` で書き、`•` を文字として打たない（描画される経路とされない経路は「MCP経由で投稿するときの書式」）。
```
一応事象の詳細
- プロジェクトコード一覧で〜 => 出る
- 週次入力画面〜 => 出ない
```

## レジスタC: 業務の依頼・確認・報告（自チーム/対等な実務相手）（敬体で端的）

敬体（です・ます）で書く。**「お疲れ様です。」で開始 → 用件 → 依頼 → 「よろしくお願いします。」で締め**。Bとの差は2つで、文脈の説明を省いて用件から入ることと、重い敬語（「いたします」「ご教示」「させていただく」）を使わないこと。依頼は「お手数ですが、〜いただけますでしょうか」「〜お願いします」。絵文字は付けない。

### 実例
```
お疲れ様です。
<対象>の<作業>について連絡です。
- **<作業>**
  - 日時: <日時>
  - 理由: <理由>
- **お願い**
  - <作業>中は<控えてほしい操作>を止めてください
- **終了連絡**
  - 作業が終わったら、このスレッドでお知らせします

よろしくお願いします。
```
- 催促: `本件何らかアップデートありますか？`
- 判断の共有（口語）: `既に離任されているようですが、<担当者>から繋げてもらうのが丸いという結論でした`
- 回答・注意喚起: `postman、アカウント作ると強制的にエンドポイントやmessage bodyの情報がクラウド同期されるので、そこだけ注意必要だと思います`
- 前提の問い返し: `「geminiを利用できる状態」=「GeminiシリーズのAPIを叩ける状態」ですか？`

## レジスタD: 社外とのチャット（顧客・取引先・ベンダー。Teams・Slack Connect等）（完全敬語）

敬語の重さはBと同じ。違うのは書き出しで、**「お疲れ様です」は使わない**（社内の挨拶で、社外の相手には馴れ馴れしく読める）。

- **続いているスレッドへの返信**: 挨拶も名乗りも置かず、受けた内容への返答から入る（「ご確認いただきありがとうございます。」「とんでもございません、こちらこそ〜」）。名前と所属は表示名で分かり、毎回の挨拶は往復のたびに冗長になる
- **新しくスレッドを立てるとき**: 「お世話になっております。」で始める。相手が自分を知らない可能性があるときだけ、読点でつないで名乗る（「お世話になっております、<所属>の<名字>です。」）
- 締めは「よろしくお願いいたします。」
- **同じ相手との過去のやり取りがあれば、その書き出しと締めを型にする**（この節の一般則より優先する）

### 相手の一覧に状況を返すとき（宿題・依頼の棚卸しなど）

相手が項目を並べて状況を尋ねてきたときは、相手が自分の一覧と突き合わせて読めることを優先する。

- **見出しは相手の番号と項目名をそのまま使う**。言い換えると、相手はどの項目への返事かを探し直すことになる。同じ件を指す項目は「② <項目名> / ⑤ <項目名>」と並べてまとめる
- **同じ件か確信が持てないときは、こちらで決めずに相手に尋ねる**。尋ねる理由も添える（「もし別件であれば片方を認識できていない可能性があるため、お手数ですがご教示いただけますと幸いです」）。こちらの解釈で統合すると、相手が持つ別件を落とす
- **状況は相手が知りたい段階まで書き、内部の経過は書かない**。「<相手先>の回答を待っているステータスとなります」「問い合わせ中となります」で足りる。送った日付・自動応答・催促の予定・問い合わせの件数は、相手の次の行動を変えないので省く
- **待たせている件には詫びを添える**（「お待たせしており大変申し訳ありません」）
- **自分の動作は謙譲で書く**（「共有させていただきます」「再確認させていただきます」）。冒頭の詫びは「大変失礼いたしました」まで重くする
- **手を付けていない件は、未着手を詫びる文にせず、次にすることを書く**（「こちらについては担当者に再確認させていただきます」）
- **原因の見立ては、前に伝えた内容とつないで「〜と考えております」で書く**（「定例の中でもお伝えしましたが、<原因>ものと考えております」）。「未検証です」のような断り書きは付けない。根拠となる記載があれば、見立ての前に事実として並べる
- **Markdownの記号（`**` `-`）を使わず**、見出しの行と本文の行を改行で分け、項目の間に空行を入れる
- 添付があるときは、本文の最後の項目で触れる（「ひとまずこちらで<作業>させていただいた内容を添付いたします。ご確認いただけますと幸いです。」）

### 実例（骨格）
```
とんでもございません、こちらこそまとめてご報告できておらず大変失礼いたしました。
こちらで持っているものを、現時点の状況とあわせて整理しました。

①<相手の項目名>
<状況>。<次にすること>させていただきます

②<相手の項目名> / ⑤<相手の項目名>
お待たせしており大変申し訳ありません、こちら<相手先>の回答を待っているステータスとなります
"<項目名A>" と "<項目名B>" については同件（<こちらの理解>）を指しておられますでしょうか。
もし別件であれば片方を認識できていない可能性があるため、お手数ですがご教示いただけますと幸いです。

③<相手の項目名>
<根拠となる記載>
定例の中でもお伝えしましたが、<原因>ものと考えております

ほかに漏れているものがあれば、ご指摘いただけますと幸いです。 引き続きよろしくお願いいたします。
```

## 共通の注意

- B・C・Dはどれも敬体。相手と立場で、敬語の重さと文脈説明の量を切り替える（B: 社内の目上、C: 自チーム・対等、D: 社外）。
- 質問への回答では、まず相手の前提を `=` で言い換え確認してから答えることがある（認識ズレ防止）。
- 締めはBが「よろしくお願いいたします」、Cが「よろしくお願いします」。
- 自嘲の `（）`・三点リーダの引き伸ばし・フィラー（`なんか` `べつに`）は使わない。
- **1メッセージの中でレジスタを混ぜない**。砕けた語り口（タメ口・「おまたせ」・「〜でどうでしょう」）と構造化装飾（太字見出し・表・番号付き節）を同居させると芝居がかった文になる。業務の報告（レジスタC）は敬体を保ったまま事実を並べ、装飾は箇条書きまでにする。

## MCP経由で投稿するときの書式

**目的: 箇条書き・強調・コード・引用が、受け手の画面でネイティブの書式として描画される状態で届ける。** 記号を文字として打った箇条書き（`•` `◦` の直書き）や、変換されずに文字のまま残った箇条書きは、階層の無い平坦なテキストになる。

Slack MCPの送信ツール（`slack_send_message`）と下書き作成ツール（`slack_send_message_draft`）はどちらも `blocks` を受け付けず、`message`（markdown文字列）だけを取るが、**保存される書式が経路で異なる**:

| 経路 | 書式の扱い | 乗せてよい文 |
|---|---|---|
| 送信ツール | 標準markdownをネイティブ書式に変換する（`- ` とインデントの箇条書き、`_斜体_`、`` `code` ``、コードブロック、引用、リンク） | 構造を持つ文を含む全て |
| 下書き作成ツール | レガシーのプレーンテキスト書式で保存する。強調は変換されるが、**箇条書きは文字の `•` に変換される** | 段落だけの文（箇条書き・見出し・表を含まないもの） |

- 箇条書きは `- ` とインデントで書き、`•` `◦` を文字として打たない（送信ツールが変換するのはこの形）
- ユーザーグループのメンションは `<!subteam^グループID>` 形式で書く
- ツールの変換挙動は版で変わる。初めて使う経路・ツールの版が変わった後は、構造を持つ文を検証先に1度送って画面で描画を見る（ドキュメントの記載は実機の挙動を保証しない。AGENTS.md「外部API・ランタイム/プラットフォームAPI」と同じ扱い）

### 承認が要る投稿（対外・公的なもの）の経路

内容の承認と描画の実物確認を両方満たす経路を、文の形で選ぶ:

- **段落だけの文**: 下書き作成ツールを使う。チャンネルの下書き欄に入り、本人が画面で確認・編集して自分で送れる
- **構造を持つ文（箇条書き・見出し・表）**: 下書き経路に乗せない（書式が正しく描画されない状態のものを承認することになる）。次の順で進める
  1. 本文をチャットで提示する（各文の出所を添える。AGENTS.md「最優先指示」）
  2. 送信ツールで検証先へ投稿し、本人が画面で描画と内容を確認する。描画が意図と異なれば直して再投稿する。検証先は自分宛DMでよい（送信ツールの宛先に自分のuser_idを渡せる）。使えないワークスペースでは本人だけが見る場所を1つ決めておく
  3. 確認が取れてから、本番の宛先へ送信ツールで投稿する。本番への投稿は名指しの承認を受けてから行う（AGENTS.md「ユーザーへの質問」の外部作用の承認）
