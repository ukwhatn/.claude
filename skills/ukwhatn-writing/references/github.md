# GitHub の書き分け

PR概要欄 / レビュー指摘 / レビュー返信 の3つ。共通して **絵文字・感嘆符は控えめ（指摘時はほぼ無し）**、技術用語は原語＋ `inline code`、件数・パス・ハッシュは具体で書く。

---

## 1. PR概要欄

### 固定見出しテンプレ（チーム開発）
日本語見出しを順に並べる。**`## やらなかったこと` を立てる**のが最大の特徴（スコープ外があれば理由付きで明示、なければ「特になし」と1行で書く。軽微PRでも見出しは残すが中身は簡潔に）。

```
# 概要
<1〜2文。何をするPRか。背景がいるなら一言>
- closes #<Jira/Issue番号>

## 動機
<なぜ必要か。背景・経緯。関連スレッドのリンクを添える>

## やったこと
- `path/to/file.ts` に `xxx` を追加。<何をするか>
- <体言止め・常体で箇条書き。inline codeでパス/関数/設定値を囲む>

## やらなかったこと
- <スコープ外を明示。理由を「— …のため」「（…のため）」で添える>

## 影響範囲
- <影響する機能・経路>

## テスト方法
ローカル:
- [x] `bun run typecheck` 通過
ユーザー手動確認:
- [ ] <手動確認項目>

## レビュー時チェック
- <見てほしい観点: 境界ケース、すり抜け経路など>
```

### バリエーション
- **軽微PR**: `## やったこと` を数行、`## やらなかったこと` は「特になし」、`## レビュー時チェック` は **「特にありません（普通にレビューしてください）」**。
- **大規模PR**: カテゴリ別見出し＋件数併記（`### セキュリティ修正（8件）`）、冒頭に総数集計（`全73件（critical 4, major 22, minor 34, trivial 13）`）。`| カテゴリ | 件数 | 対応 |` の表で整理。
- **OSS/外部repo**: 英語見出し（`## Summary` / `## Test plan`）＋箇条書きのみの簡素版に切替。
- **運用注意・PoC警告**: 冒頭に GitHub alert。
  ```
  > [!IMPORTANT]
  > developマージ後、terraform applyを各環境に対して実行します
  ```
- **同時マージ等の運用指示**: 末尾に `---` 区切りで太字注意。`**本PRは hotfix の同時PR3本の1つです。…可能な限り同時にマージしてください。**`
- `## やったこと` の中に `### 原因` を入れ子にして根本原因を説明する型もある。

### 実例（抜粋・原文ママ）
`## 検証` は `## テスト方法` の別名（検証手順を書くPRで使う短縮版）。
```
## 概要
dependabot PR #288（dev-dependencies group in /batch）で `ty` が `>=0.0.40` に更新されると、厳格化した型チェックで既存コードの型エラーが顕在化し `Lint (Python)` が失敗していた。型注釈の追加のみで解消する（ロジック変更なし）。

## 検証
- `uv run ty check`（ty 0.0.42 / 0.0.40相当）→ error 0件（残る not-iterable 警告3件は pyproject で `warn` 設定済みのためexit 0）
```

## 2. レビュー指摘（レビュアーとして）

### 2-0. レビュー本文と行コメントの役割分担（最重要）

**指摘の中身は必ず行コメントに置き、レビュー本文には書かない。** 本文は交通整理と結論だけで、ほぼ常に1〜2文。

| 本文に書くこと | 型 |
|---|---|
| どれが必須でどれが nits か | `<ファイル名> へのコメントのみcritical寄りの質問になります、それ以外はnitsです` |
| 必須対応の名指し | `<ファイル>:L<行> の部分だけ必須対応（確実に落ちるので）です` |
| 指摘はあるが approve する旨 | `一点だけコメント入れてますが、全体LGTMです` / `気になったところにコメント入れましたが、今のままでも問題ないと思います` / `すべて軽微な指摘なのでapproveします！` |
| 自信度の留保 | `あとはドキュメント見た限りのコメントなので、間違っているかもしれません 🙏` |
| approve の付帯条件 | `conflictだけ解消いただければLGTMです` / `内容LGTMです、Conflict解消のみお願いします` |
| AI併用の開示 | `確認しました、いくつか気になったので（AIと共同で）コメントを入れています` |
| 再レビュー時の進捗 | `対応ありがとうございます。前回の指摘は全て確認しました。…N件コメントしています` |
| 指摘対応の裁量を返す | `内容的には問題ありませんでした。指摘対応するかはおまかせします。` |

本文に指摘内容の要約・観点別の見出し・「統合サマリ」表の類を置かない（行コメントと重複するだけ）。**本文に書くことが無いなら本文なしで行コメントだけ投稿する。**

### 2-1. 指摘なしの approve

Meowmoji で `LGTM✅` を綴る画像5枚だけを本文にするのが定番。

```html
<img src="https://gh-pages.whatn.uk/blob-emojis/download/Meowmoji%20Signs/meowl.png" width="30"><img src="https://gh-pages.whatn.uk/blob-emojis/download/Meowmoji%20Signs/meowg.png" width="30"><img src="https://gh-pages.whatn.uk/blob-emojis/download/Meowmoji%20Signs/meowt.png" width="30"><img src="https://gh-pages.whatn.uk/blob-emojis/download/Meowmoji%20Signs/meowm.png" width="30"><img src="https://gh-pages.whatn.uk/blob-emojis/download/Meowmoji%20Signs/meowgreentick.png" width="30">
```

短文で済ませる場合は `LGTM` / `LGTMです` / `LGTMです、ありがとうございます`。遅れたときは `遅くなりました 🙇` / `たいへん遅くなりました 🙇 LGTMです`。

### 2-2. 行コメントの型

**1指摘1コメント。複数論点を1つに詰めない。** **根拠の一次ソースURL ＋ 代替案** をセットにする。**事実は断定し、提案・推測だけぼかす**。絵文字なし（`💭` を思考メモの先頭に置くことはある）。

- **断定してよい**: 仕様違反・CI失敗・再現済みバグなど事実（「`個人情報を含ませないでください。` に違反します」「lintも落ちています」）
- **ぼかす**: 確証のない推測・あるべき実装の提案（「〜ではないかと思います（おそらく）」「氏名はDBから引くべきかと思います」）
- **軽さのラベルを先頭に置く**: `[minor]` / `[nits]` / `[just comment]` / `trivial:` / `（念の為）`
- **要望は「〜しておきたいです」**: `timezoneいれておきたいです` / `.default(50) あたりを入れておきたいです` / `<関数> のテストも足しておきたいです`。**変更してほしい内容に使う語尾で、相手の意思決定には使わない**（「どう扱うか決めておきたいです」は決める主体がずれる → 「〜の判断でしょうか。」に倒す）
- **推測は「〜な気がします / 気がしています」**: `<名前A> -> <名前B> な気がしています`
- **判断を委ねる疑問形で締める**: `このガードは…には不要の判断でしょうか。` / `既存の <値> が消えなくなる点は許容の判断でしょうか？` / `如何でしょうか`
- **代替案併走**: 指摘だけで終わらず「`team_reviewers` を使うことでここの処理自体を削除できないでしょうか」
- **相手の裁量に返す**: `お任せします` / `ご意見いただきたいです` / `ご助言いただきたいです`
- typo・命名は超短文で `A` → `B` だけ書く
- 公式ドキュメントは `#:~:text=` フラグメント付きで該当箇所を直リンクし、本文末に裸URLだけ置くこともある
- コード片・ログは ```code block``` で引用してから論じる
- 全角スペース `　` を読点として使う: `<条件>で500が返りそうです　極めて特異なケースなので対応不要の判断でも全く問題ないと思いますが、念の為`

### 2-3. AI草案から削るもの

AI草案は語尾はほぼ揃うが、**量と構造が過剰**になる。次を削ると自筆の密度に近づく。

| AI草案に出るもの | 直し方 |
|---|---|
| 1コメントに3段落以上・複数論点 | 論点ごとに別コメントへ分ける |
| `<file>:<line>` 参照の多量列挙 | 効く1〜2箇所に絞る |
| 「なお」「あわせて」での論点ぶら下げ | 別コメントにする |
| レビュー本文への指摘要約・サマリ表 | 本文は交通整理1〜2文に削る（無ければ本文なし） |
| `[minor]` / `[nits]` ラベルの欠落 | 軽い指摘には付ける |
| 「〜しておきたいです」を避けて全部「〜でしょうか」 | 変更要望は「〜しておきたいです」に戻す |

### 実例（原文ママ）
- `[lint] も落ちていますが、permissionsにmembers scopeは存在しないかと思います`（直後にドキュメントURLのみ連投）
- `このAPI叩くのに org:read が必要なので、GHAのpull_request targetだとPATを別途発行しない限り叩けないのではないかと思います（おそらく）`
- `timezoneいれておきたいです`（＋ドキュメントURL）

## 3. レビュー返信 / 作業報告（自分のPRで）

指摘時よりやや柔らかく、感嘆符が出る。**インラインコメントへの返信は短く（3-1/3-2）、自分から出す作業報告だけ構造化する（3-4）**。

### 3-1. 指摘への回答（意図どおり・仕様判断）

**結論を1文で言い切り、判断理由を1〜2文。全体3文以内・100字前後**。

- 冒頭は結論だけの独立行（`意図して実装しました。` / `意図した実装です。`）
- **レビュアーの分析を復唱しない**（`ご指摘のとおり〜は〜です` は書かない。相手はコードを読んだうえで指摘している）
- **調査の証跡を貼らない**（`file:line`・経路の列挙・ログ）。調べた結果は結論に織り込むだけ
- 理由は1つに絞る。実装コスト・文言追加の手間などを積み増して正当化しない
- 採らなかった案は主体的に書く（`〜という選択はしませんでした`）
- 判断は柔らかく（`〜かなと思い` / `〜と判断しました`）
- 確信が持てない点は議論で押し切らず、フォローアップを宣言する（`念のため仕様確認を実施します。`）
- 見出し・太字・箇条書きを使わない（プレーンな段落）

#### 実例（原文ママ）
```
意図して実装しました。

そのまま送信したうえで受信側で既存のエラー画面を出す形でもあまり困らないかなと思い、ここにわざわざ新しく状態判定を入れる選択はしませんでした。
```
```
意図した実装です。

グループの管理者が変更されても旧管理者が過去に行った同意が無効になるわけではないと判断しました。念のため仕様確認を実施します。
```

### 3-2. 修正した指摘への返信

**短縮sha（7桁前後）＋「で修正しました」/「で対応しました」が基本形**。何をどう直したかは書かない（差分を読めば分かる）。

```
<sha> で修正しました
```

`fixed in <sha>` もある。補足が要るときだけ1〜2文足す（`<既存ファイル> にあわせるかたちで <sha> で修正しました`）。

コミットURL形式も使うが、こちらはやや重い。**採らなかった判断や残した箇所を1〜2文添えるとき**に向く。

```
https://github.com/<org>/<repo>/pull/<n>/commits/<sha> で対応しました、ありがとうございます。

<採らなかった選択と理由を1〜2文>
```

### 3-3. 指摘を採らないときの裁定

自分のPRで指摘を却下・保留するときは、**常体・体言止めで理由だけ**書いて1行で終わらせる。敬体にしない。

- `型整合性は取れているので不要`
- `やりすぎな気がする　時間がかかる処理でもないので不要判断`
- `トランザクションでロールバックされるので問題なし`
- `revertする可能性があるので一旦放置` / `影響が読めないので一旦放置`
- `ちょっと太すぎるので却下`
- `scope外` / `あとで`
- `<既存処理> との整合性を優先`

語彙は `不要` / `不要判断` / `〜の判断` / `却下` / `一旦放置` / `scope外` / `問題なし`。

### 3-4. 受領・次アクション宣言
- `ありがとうございます！念の為update branchしてからマージします`
- close/保留判断（短く逃げ道付き）: `一度closeします、必要であればreopen / recreateしてください`
- close は理由1行で: `急ぎのhotfixは不要そうなので一旦close` / `<後続フェーズ>で回収する close`
- 謝罪は感嘆符 + 🙇: `修正漏れです！<判断>したので削除しました` / `すみません！<経緯>` / `申し訳ありません、<観点>が完全に抜けていたので<対応>`
- 他人のスレッドへの割り込みは `横からすみません 🙇` で入る

### 3-5. PR会話コメント（行コメント以外）
- `@メンション` は独立行で先頭に置く
- 相手の発言は `>` で引いてから答える（引用→回答を論点ごとに繰り返す）
- 余談は `(aside)`、自分向け備忘は `memo:`、残作業は `TODO:` + チェックボックス
- bot / CI の呼び出しは1行だけ投げる（`/review` / `/devin review` / `@<review-bot> re-review` / `@dependabot <subcommand>`）

### 3-6. 自発的な作業報告は構造化
**指摘への返信ではなく、自分から出す報告（dependabot一括対応等）のみ**。見出し＋番号＋表。`**問題**:` → `**対応**:` → `**TODO**:` のラベル太字で因果を整理。
```
## dependabot一括更新に対する手動修正
以下の修正を手動で追加しました。
### 2. tsc型エラー修正 (`37a49a231`)
71パッケージ更新に伴い39件のtsc型エラーが発生。以下を修正:
| カテゴリ | 件数 | 対応 |
|---------|------|------|
| react-hook-form 判別共用体変更 | 35 | ... |
### 3. `<外部SDK>` を 3.19.4 に固定
**問題**: ESM-onlyパッケージを `require()` できず77テストスイートが失敗。…のため対応困難。
**対応**: `<外部SDK>` を `3.19.4` に固定。
**TODO**: 別PRで Jest ESM対応と合わせて個別対応が必要です。
```

## markdown の癖
- インラインコードを多用（パス・関数・変数・設定値・コマンドは必ず `` ` `` で囲む）
- 短い注記はラベルを角括弧/コロンで先頭に置く（`[minor]` `[nits]` `[just comment]` `trivial:` `memo:` `(aside)`）
- 全角スペース `　` を読点の代わりに使う（レビュー指摘・裁定メモの両方で出る）
- チェックリストは担当主体で分ける（`ローカル: [x]` / `ユーザー手動確認: [ ]`）
- 対応関係は表、Slack依頼文/bot指摘/引用は `>` blockquote、運用注意は `> [!IMPORTANT]`
- リンクは `[ラベル](URL)`。公式ドキュメント・Slackスレッド・Jira・関連PR番号(`#<番号>`)を密に相互リンク
- 強調 `**…**` は要点語にピンポイント（乱用しない）
- 「やったこと」箇条書きは体言止め/常体（「〜を追加」「〜化」）、地の文・対人コメントは敬体
