# 日本語文章の規範

このファイルは「日本語としてどう書くか」を定める。
「誰に、どの媒体で書くか」（レジスタ）は SKILL.md と媒体別の reference が定める。

SKILL.md STEP 2 の7原則と STEP 3 の対比表は、成果物の種別によらずすべての文章に効く。
本ファイルはそこに無い規則だけを足す。

---

## 1. 適用範囲

成果物の種別で、適用する層を決める。
文字数では切らない（Slack にも長短があり、PR 概要欄は短くても構造物であるため）。

| 成果物 | 適用する層 |
|---|---|
| Slack（雑談 / 対外 / 業務連絡）、GitHub のレビュー指摘と返信 | 共通層のみ |
| PR 概要欄、負債メモ、リサーチメモ | 共通層 + 構造物の規則（SKILL.md STEP 2 の原則6） |
| Confluence の設計書、手順、告知、記事、レポート、議事録、提案書 | 共通層 + 長文層 + 工程 |

**共通層**（§2）は、一文から数行の短文でも守れる規則だけで構成する。
**長文層**（§3）は、段落が複数あり読み手が構造をたどる文書にだけ効く規則を置く。

### 規則が衝突したときの優先順位

1. **事実性と安全**: 確認していないことを書かない。推測を断定にしない
2. **媒体固有の制約**: 各 reference が定めるレジスタ（敬体/常体、砕け方、テンプレの見出し）
3. **共通層**（§2）
4. **長文層と整形**（§3）

内輪の Slack 文体（`（）` の空欄、三点リーダの引き伸ばし、フィラー、体言止め）は 2 に属する。
共通層より優先し、共通層の規則を理由に削らない。

## 2. 共通層

### 2-1. LLM 口調の語彙カタログ

論点を増やさず「ちゃんと書いている感」だけを付ける型がある。
書き上げたら、この節の語で検索して潰す。

**予告と総括**: 主張の前に置く枠だけの一文を書かず、主張をそのまま書く。

- 「重要なのは〜である」「〜が本節の主題である」「ポイントは〜です」
- 「本章では〜を扱う」「〜について見ていく」「〜を探求する」「以下で詳しく説明します」
- 「まとめると」「要するに」「つまり」（直前の言い換えにしかならないとき）
- 「〜に他ならない」「〜と言っても過言ではない」
- 「正面から扱う」「正面から回収する」「正面から向き合う」（姿勢だけの宣言）

**空虚な形容**: 中身を説明せず強調だけする語を消す。何がどうなのかを書く。

- 不可欠、核心的、鍵となる、根本的な、抜本的な
- 多角的、包括的、総合的、網羅的、体系的（何をどう見たかを書いていないとき）
- 最適な、堅牢な、シームレスな、柔軟な（条件を書いていないとき）

**空虚な動詞**: 何をどう書いたかを示さずに終わる動詞を消す。

- 掘り下げる、深掘りする、紐解く、言語化する、可視化する
- 触れる、言及する（一段落で済ませるだけのとき）
- 整理する、最適化する、活用する（対象と結果を書いていないとき）

**接続の型**: 新情報を足さない接続句を消す。

- 「〜において」「〜という側面から」「〜の観点から」「〜という点で」
- 「さらに」「また」「加えて」「そして」の連打（同じ語で三つ以上つながないこと）
- 「一方で」（対比の中身が無いとき）

**根拠なき緩和と空の強調**: 断定できないから弱めるのは残し、書き手の自信の無さだけを表す語を消す。

- 「〜と言えるだろう」「〜と考えられる」「〜する傾向にある」（根拠が無いとき）
- 非常に、極めて、大いに、しっかりと、きちんと、まさに
- 意見と推測のクッション（「〜かも」「〜と思う」「〜ではないかと思います」）は残す。
  これは SKILL.md STEP 2 の原則4の対象であり、本項では削らない

**おべっか**: 内容に踏み込まない持ち上げを書かない。

- 「すばらしいご質問です」「いい着眼点ですね」「おっしゃるとおりです」
- 「〜という視点は非常に重要です」
- 相手の指摘内容を言い直してから答える形（媒体別の扱いは `github.md` の「指摘への回答」に従う）

### 2-2. 論証の厳密さ

- **異なるものを「同じ」とまとめない。** 別々の決定、別々の原因、種類の違う問題を一括りの語でくくらない。
  まとめる前に、それらが同じものに帰着すると一文で言えるかを確かめる
- **複数の要因がある事象を、単一の原因に還元しない。** 対象が複数種類の問題を含むなら、切り分けて、どの説明がどれに対応するかを書く
- **因果を主張するなら、その機構を一文添える。** 「A だと B になる」だけで理由を省略しない。
  機構を書けないなら、因果ではなく相関として書く
- **「必ず」と書かない。** 検出、保証、解決ができるかのように言い切らず、条件付きで述べる（「〜のときに限り」「〜しやすい」「〜できることが多い」）
- **否定するときは、否定する命題そのものを「」で書き出す。** 「〜がすべてを解決するわけではない」のような漠然とした否定で済ませず、「明文化すれば任せられる」を意味しない、のように否定対象を特定する

### 2-3. 演出の抑制

修辞を全面的に禁じるのではなく、効く箇所に限る。

- **溜めを作らない。** 「ここには〜が潜んでいる」「実は〜だった」で導出を演出しない。説明で足りる箇所ではそのまま述べる
- **修辞疑問で論を進めない。** 答えを自分で持っている問いを、読み手に投げる形で書かない（相手に判断を渡す問いは §2-4 の対象外。SKILL.md STEP 4 の「問いで投げる」はこちらに当たる）
- **短い決め台詞を独立した段落に置かない。** 一行だけの段落で緊張を作る型を多用しない
- **転回点を過剰に劇的にしない。** 事実を述べる一文で足りることが多い
- **帰結を並べて危険を煽らない。** 起こり得ることは、発生条件と影響範囲で書く
- **慣用句をひねった言い回しを使わない。** 平易な動詞でそのまま言う
- **指す内容が一意に決まらない比喩を使わない。** 比喩を置くなら、比喩が何に対応するかをその場で書く

内輪の砕けた文体（自嘲の `（）`、三点リーダ、絵文字ネタ）は演出ではなくレジスタなので、本節では削らない（§1 の優先順位2）。

### 2-4. 冗長の排除

SKILL.md STEP 2 の原則1（短く、自明なことを書かない）に加えて、次を消す。

- **場面を述べた直後に、その内容を要約し直さない。** 意味づけの一文だけを置く
- **接続や評価のためだけの文を置かない。** 「それ自体はよいことである」「ここが難しいところだ」のような、論を進めない一文を書かない
- **想像上の読者との問答を書かない。** 自分で問いを立てて自分で答える形（「〜ではないだろうか。そのとおりである」）を修辞として使わない。相手に判断を委ねる問いはこれに当たらない
- **メタな枠取りで発想を紹介しない。** 「ここまでの話には自然な続きがある」「〜という発想である」と枠を置かず、その発想自体を直接書く

## 3. 長文層

**ここから下は長文文書だけに適用する。**
対象は §1 の表で「共通層 + 長文層 + 工程」を適用するとした成果物（設計書、手順、告知、記事、レポート、議事録、提案書）。
Slack、短いレビュー返信、コミットメッセージには適用しない。

### 3-1. 整形

- 一文ごとに改行する。段落の区切りは空行で示す
- コード、差分、ログ、設定の断片はコードブロックに入れる
- 本筋から一段外れる補足（用語の由来、定式化の名称）は本文に並べず脚注へ降ろす
- 初出の定義は**太字**、以後その語を話題として指すときは「」を使う。両方を同じ語に重ねない
- 太字は一節に一、二箇所まで。誤読を防ぐ否定と、節の帰結に限る
- ダッシュ（`—` `―` `——`）を地の文と見出しで使わない。同格の挿入は（）に、言い換えは句点で二文に分けるか読点でつなぐ。範囲を示す en ダッシュと英語の複合語は対象外
- 中黒（・）を日本語の並列で使わない。読点か「と」でつなぐ。単一の固有名詞の内部では使ってよい
- 見出しに区切り線で二要素を詰め込まない（「種別──主題」の形にしない）。要素を一つに絞るか、助詞でつなぐ
- 用語と定義を並べる箇条書きは「**用語**：説明」と全角コロンで書く

### 3-2. 段落と論証

段落は論証の一歩として扱う。読み手が段落単位で論理を追える状態を保つ。

- **一つの段落に一つのトピックだけを置く。** 調査、報告、検証、評価が混ざった長い段落は、一歩ずつに割る
- **段落の最初の文を読めば、その段落が何の話か分かるようにする**
- **段落の先頭で、前の段落との論理関係を接続表現で示す**（「であれば」「実際」「しかし」）
- **論証は一方向に進める。** 結論を出してから反論を処理し、結論を言い直す構成にしない。反論と疑念の処理を終えてから、結論を一度だけ置く
- **新しい概念を辞書型の断定で始めない。** 「X は Y である」から入らず、先に対象を置き、次にその働きや差分を述べ、必要なら三文目で定義する
- **前方参照（「後の節で扱う」）は、論証が一段落した位置に置く。** 論証の途中に挟んで流れを切らない。前方に逃がした論点は、そこで実際に回収する

### 3-3. 読み手の負荷

読み手の記憶と注意を有限の資源として扱う。

- **後で参照しない固有名（ファイル名、関数名、識別子）を出さない。** 「仕様書」「金額計算のユーティリティ」のような一般的な言い方で済ませる
- **抽象的な言い回しの指す内容が文脈から一意に決まらないときは、丸括弧の同格挿入でその場で特定する。** 読み手に前を読み返させない
- **新しい例を足すときは、前の例との違いと、なぜもう一つ必要かを前置きする**

### 3-4. 視点と語り

- **行為者を主語にした動作の連なりで書く。** 結果の羅列と受動態（「特定され、判明した」）で済ませない
- **読み手を「あなた」と二人称で呼ばない。** 役割名（「開発者」「読み手」）で書く。呼びかけは場面への導入と結びに限る
- **一度導入した術語で通す。** 「文脈」「ツール」「AI」のような曖昧語に後退しない。対象を指す語は具体的に選ぶ
- **イ形容詞の終止に「です」を続けない**（「難しいです」「多いです」）。これは文体の問題ではなく、その文が前後から孤立している兆候なので、文末だけ直さず前後の流れごと書き直す。ナ形容詞（「重要です」）は対象外

### 3-5. 見出しの付け方

- その節が答える問い、または扱う対象を指す句にする
- 作業の手順だけを述べる見出し（「例に戻す」「〜を読み直す」）にしない
- 節の結論を言い切る見出しにしない。見出しの時点で読み手がオチを知る状態を避ける
- 疑問形と名詞句のどちらでもよい。本文のトーンに合うほうを選ぶ

## 4. 長文文書の工程

設計、執筆、検査、収束の順に進める。
書いた後に直すより、書く前の設計で発生を防ぐほうが効く。

### 4-1. 設計

1. **読み手と主メッセージを一文で書く。** 誰が読み、読んだ後に何が起きてほしいかを決める。
   一文で書けないなら素材が足りないのであって、書き方の問題ではない。素材を集めるか、依頼元に確認してから書き始める
2. **見出しスケルトンを作る。** 見出しだけを順に読んで論旨が通ることを確認してから本文に入る
3. **濃淡を設計する。** 全節を同じ厚みで書かない。厚い節と薄い節を先に決める。均質な厚みは、それ自体が読みにくさになる

### 4-2. 執筆

スケルトンに沿って本文を書く。この段階では §2 と §3 の細部を気にしすぎず、内容を出し切ってよい。
細部は次の検査で拾う。

### 4-3. 検査

**スケルトン通読**: 見出しと各段落の先頭文だけを抜き出して読み直し、次を確かめる。

- 見出しと先頭文だけで論旨が追えるか
- 同じ型の反復が無いか（定義文の型、節の内部構成、書き出しの文型）
- 濃淡があるか
- レポート系なら、結びが「だから何をするか」に接続しているか

**語彙の検査**: §2-1 のカタログの語で本文を検索し、該当箇所を書き直す。

**文書タイプの照合**: §4-5 の必須要素が揃っているかを確認する。

### 4-4. 収束

直した結果が新しい違反を生んでいないかを、もう一度スケルトン通読で確かめる。
同じ箇所を2周続けて直しているなら、文の直しではなく構成の問題なので、見出しの単位から組み直す。

既存文書の改稿では、同じ種類の修正（見出しの結論化、箇条書きの地の文化）を全項目に一律に当てない。
元の文書の濃淡を消すと、かえって機械が書いた文書に近づく。

### 4-5. 文書タイプ別の必須要素

| 文書タイプ | 欠けてはいけない要素 |
|---|---|
| 議事録 | 決定事項 / 未決事項と次にそれを決める場 / 担当と期限 / 決定の理由 / 検討して採らなかった案 |
| レポート | この文書が答える問い / 結論 / 根拠となる数値とその出所 / 確認できていない範囲 / 読み手が次に取る行動 |
| ガイドと手順 | 対象読者と前提条件 / 順序どおりの手順 / 非自明な手順の理由 / 失敗時の戻し方 / 完了の確認方法 |
| メモと提案 | 目的1文 / 現状と論点 / 選択肢とトレードオフ / 現時点の推奨と確度 / 未決の問い |

## 5. 完成時の外部レビュー

### 対象

人に共有する、または公開する長文（記事、設計書、告知、レポート、提案書）。チーム内向けを含む。

対象外は次のとおり。

- 外部レビューの結果そのもの（レビュー本文、指摘の統合文）
- メモリディレクトリのファイル
- Slack、レビュー返信、コミットメッセージなどの短文

### 自分で読み直すだけでは足りない理由

同じモデルが同じコンテキストで読み直すと、書いたときの判断がそのまま再生される。
書けた理由と読めた理由が同一なので、前提の抜けは自分の読み直しでは見えない。
文章の欠陥は、書き手の前提を共有しない読み手にだけ現れる。

### レビュアーに渡す情報

- 原稿のパス（本文を貼り付けず、パスを渡して読ませる）
- 媒体
- 想定する読み手
- 適用したレジスタ（どの reference に従って書いたか）

### Severity の定義

| Severity | 対象 | 扱い |
|---|---|---|
| Action Required | 事実性の誤り（未確認の断定、数値や参照先の誤り、根拠のない因果） | 必ず直す |
| Recommended | 文体と構成の違反（本ファイルの規則、レジスタからの逸脱） | 直す。レジスタ側の規定と衝突するときは §1 の優先順位で裁定する |
| Minor | 好み（語の選び方、順序の入れ替え） | 採否は書き手が決める |

### 結果の記録と2ラウンド目

結果は原稿と同じメモリディレクトリの `80_review.md` に記録する。
同じタスクで実装のレビューも回している場合は、見出しで分けて同じファイルに置く。

2ラウンド目はセッションを継続して投入する。
直した箇所と、直さなかった指摘とその理由を渡し、同じ Severity 分類で再レビューさせる。

**上限は2ラウンド**（実装差分のレビューとは別。対象種別ごとの上限は @context/agent-cli-guide.md「レビューループの流れ」）。
文章への指摘はラウンドごとに別の箇所へ発散し、収束条件を長く取っても品質が上がらないため、2ラウンドで打ち切って残りは書き手が裁定する。

実行手順（CLI の選択、コマンド形式、セッション継続の方法）は `~/.claude/context/agent-cli-guide.md` に従う。
本節が定めるのは、渡す情報と Severity と収束条件だけとする。
