# agent cli 使用ガイド（外部レビューの本体）

別ベンダーの LLM（既定は codex CLI）の non-interactive mode で計画・実装をレビューする手順。**本ファイルは末尾まで読んでからコマンドを組む**（空振りする条件は末尾「注意事項」、ループを止める条件は「レビューループ」にあり、コマンド例の中には現れない）。

次に該当するときは、本ファイルに加えて `context/agent-cli-guide-details.md` を Read する:

- codex が無く cursor（`agent` / `cursor-agent`）で実行するとき、または実行主体が Codex のとき
- レビューループを pane（`bin/herdr-delegate.sh --kind codex`）で回すとき、reviewer を別 agent に分けるとき
- 使うモデルを既定から変えるとき

> モデル slug（`gpt-5.6-sol` 等）は 2026-07 時点のもの。使用前に `codex --help` 等で実在を確認する。

## いつ回すか

発火条件は AGENTS.md「作業フロー」が真実源（計画書・実装とも、認証・secret・migration・対外公開・データ削除を含むとき、またはユーザーが求めたとき）。本ファイルは手順だけを扱う。

**自分がレビュアーとして呼ばれた側（`codex exec` 等で本ガイドのプロンプトを受け取った側）なら、以下の lead 用規定は適用しない。** そのレビューを自分で完遂し、他 CLI・他 LLM へ再委託しない（`codex exec` にはグローバル指示がフル注入されるため、この分岐が無いと再委託が起きる）。

## CLI の選択と fallback

1. `command -v codex` があれば codex。無ければ cursor（手順は details）
2. 実行前に codex の残枠を確認する（枯渇の申告をユーザーに求めない）:
   ```bash
   python3 ~/.claude/codex-usage.py --refresh >/dev/null 2>&1
   python3 ~/.claude/codex-usage.py --show   # monthly が null なら credits を見る。両方 null なら照会失敗とみなし実行して判断
   ```
3. 外部 CLI が両方使えない（不在・枠の枯渇・`Your workspace is out of credits`・ネットワーク遮断）ときは **fable subagent** で代替し、切り替えた旨だけ報告して進める:
   ```
   Agent(subagent_type: "general-purpose", model: "fable", prompt: "<下記プロンプト本文をそのまま>")
   ```

fable subagent は lead と同一ベンダーで bias 独立性を持たないため、**別ベンダーのレビューとはみなさない**。

- 完了報告に「別ベンダーのレビュー未実施（fable subagent で代替）」と1行書く
- **変更が認証・secret・migration・対外公開・データ削除を含むときに限り**、外部 CLI 復旧後に codex で裏取りする（PR マージ前に間に合えばよい）。それ以外は報告の1行で足りる
- lead と同じモデルで reviewer role の subagent を立てない（同一モデルの自己検証は指示なしでも行われており、コストだけが倍になる）
- `Agent` ツールが無い環境では外部レビューを省略し、その旨を完了報告に書く

## 基本コマンド（codex）

レビューはツールのタイムアウトを超えることが多いので、**最初からファイルへ落とす形で起動する**。プロンプトはファイルに書いて `"$(cat ...)"` で渡す（ヒアドキュメントで argv に埋めると引用の入れ子で壊れ、壊れても気付けない）:

```bash
# 初回
codex exec --model gpt-5.6-sol -c model_reasoning_effort="medium" \
  -o "<出力先>/review.txt" "$(cat "<プロンプトファイル>")" \
  < /dev/null > "<出力先>/review.log" 2>&1

# 2回目以降（CWD の直近セッションを継続。特定セッションは resume <SESSION_ID>）
codex exec resume --last -o "<出力先>/review-2.txt" "$(cat "<プロンプトファイル>")" \
  < /dev/null > "<出力先>/review-2.log" 2>&1
```

起動後は AGENTS.md「バックグラウンドプロセスの後始末」に従って進んでいる証拠を確認してからターンを終える。確実に短く終わる確認だけは、`--json "<プロンプト>" < /dev/null 2>/dev/null | jq -r 'select(.type=="item.completed" and .item.type=="agent_message") | .item.text'` の前景実行でよい。

- `-c model_reasoning_effort` は既定値に依存せず必ず明示する。`gpt-5.6-sol-medium` のような合成 slug は codex には存在しない（cursor 側の表記）
- 既定の read-only sandbox・承認なしで完走するので、レビューは `--sandbox` を変えない
- 認証は保存済みログインを再利用する。CI 等では `CODEX_API_KEY` を当該コマンド限定で付与する

## プロンプト

**diff・ファイル内容をプロンプトに埋め込まない**（`$(git diff ...)` / `$(cat plan.md)` を本文に入れない）。CLI は自分で Bash / Read を使えるので「何を取得してレビューするか」だけを書く。埋め込むと長さ上限・バイナリで壊れる。

どのレビュー種別でも、本文に次を含める:

- `~/.claude/context/code-review-checklist.md` を Read して各セクションをチェックせよ（抽象観点だけでは具体的 anti-pattern を見落とす）
- あなたはレビュアーとして呼ばれている。他の CLI・LLM へ再委託せず、自分で完遂せよ
- 差分が読み書きするもの（テーブル・レコード・セッションキー・URL 空間・外部 API）を列挙し、既存の触っている箇所を grep で洗い出し、既存経路のガード（認可・ロック・入力検証・履歴記録・冪等性・削除ガード）と差分側を突き合わせて、差分側に無いものを挙げよ（diff の内側だけを見るレビューの構造的な盲点。人間レビューの指摘の多くはこの型）
- 差分が新たに依存する共通ラッパー・ミドルウェア・フレームワーク API の実装か公式ドキュメントを読み、失敗時の挙動・副作用の順序・状態の反映タイミングが差分側の前提と一致するか確認せよ
- 各指摘に発生確率の根拠・発生時の損失・対策コストを付けよ。対策コストが期待損失を上回る指摘は出すな。既存機構で代替できる新機構（テーブル・状態・インフラ・運用プロセス）の提案は Recommended とせよ
- バグ・不整合・堅牢性の指摘には、実際に起きる入力・状態と誤動作を付けよ。付けられない指摘は Recommended 以下とせよ
- 識別子・用語が「何か」でなく「どこから来たか」（由来システム・案件名・新旧・暫定）で付いていないか検査せよ。自分が提案する語彙にも適用せよ
- 指摘は **Action Required**（バグ・セキュリティ・データ損失。マージ不可）/ **Recommended** / **Minor** に分類し、指摘が無ければ「指摘なし」とだけ答えよ

対象ごとの冒頭文:

| 種別 | 冒頭文 |
|---|---|
| 計画 | `${MEMORY_DIR}/memory/<task>/30_plan.md を読んで、抜け漏れ・リスク・より良いアプローチの観点でレビューしてください。` |
| 実装 | `git diff $BASE_BRANCH を実行して、バグ・セキュリティ・パフォーマンス・ベストプラクティス違反の観点でレビューしてください。`（BASE_BRANCH は PJ CLAUDE.md の値） |
| PR | `gh pr diff <番号> を実行して、変更の妥当性・テストの十分性・ドキュメント更新の要否をレビューしてください。` |
| 2回目以降 | `以下の改善を行いました: <改善内容の箇条書き> 再度レビューしてください。同じ Severity 分類で、指摘がなければ「指摘なし」とだけ回答してください。` |

**「重大な問題のみ報告せよ」「保守的に判定せよ」等の絞り込みを書かない**（モデルが文字通り報告自体を減らす）。絞り込みは lead 側で行う。

## レビューループ

1. 初回を実行し、Severity 別に lead が修正 / スキップを判断する
2. 修正したら `resume --last` で再レビューする
3. **打ち切り条件（いずれか）**:
   - Action Required がゼロ
   - 同じ指摘が2ラウンド連続（既知制限として記録）
   - 安全上限: 実装差分は5ラウンド（残存指摘は issue ファイルへ）、**設計文書（計画・方針・要件）は2〜3ラウンド**。設計文書で毎ラウンド新規指摘が湧くのは LLM レビューの非収束特性で、品質不足の証拠ではない
   - 膨張シグナル: 成果物の機構数・文書量・diff の分岐やガードがラウンドごとに単調増加している。修正を続けず、減算パスへ移るかユーザー確認で打ち切る
4. ラウンド3到達時・膨張シグナル検知時は、次の修正ラウンドの前に `/gal-check` スキルを1回実行する（lead はループ継続の妥当性を自己判定できない）
5. **減算パス**: 実装レビューで**修正ラウンドが2回以上あった、または修正で diff が増えた**ときに、収束後（または打ち切り時）1回だけ行う。ビルトイン `/simplify`、または外部 CLI に「git diff $BASE_BRANCH を実行し、削除・簡素化できるもののみを挙げてください。バグ探し・堅牢性向上の提案は不要です。特に: 型・上流・DB 制約で保証済みの値への再ガード、利用実績のない抽象化、レビュー中に追加された重複防御」。減算適用後の再レビューは1回だけで、そこで出た新規指摘は Action Required のみ対応する（加算と減算を同じレビューに混ぜると加算が常に勝つため別パスにする）

## Severity 別の lead 判断

| Severity | 判断 |
|---|---|
| Action Required | 修正する。ただし採用するのは correctness / security / data integrity / 明示要件に影響する gap のみで、それ以外は Recommended / Minor へ再分類する |
| Recommended | 将来のバグ温床・保守性低下なら修正、好みの問題・実害なしならスキップ |
| Minor | 一貫性・生産性に影響するなら修正、純粋なスタイル差ならスキップ |

- **適用前に指摘の根拠を実挙動・一次情報で確認する**。反証できた指摘はスキップする
- **新機構（テーブル・状態 / enum・インフラ・運用プロセス）を伴う指摘は、「データ損失」と書かれていても自動修正しない**。Recommended 扱いでユーザー確認に回す（AGENTS.md「中長期最適と機構追加」）。事実として正しい指摘と採用すべき指摘は別物で、費用対効果で決める
- 指摘が名指しした機構を、自分の判断で別機構に置き換えない。置き換えるなら実機で動くことを確認してから入れる（後続ラウンドは自分が入れた機構を疑わない）
- 同じ Recommended を2ラウンド続けてスキップするなら、スキップ理由を再検証するかユーザーに判断を仰ぐ（繰り返し指摘されるテスト不足の層はバグが出る層と一致しやすい）
- スキップした指摘と理由は 05_log.md に1行ずつ記録する。同じ類型を同じ理由でスキップすることが2タスク以上続いたら、PJ CLAUDE.md「レビュー方針」の却下類型に追記する（`/update-inst`）

## 注意事項

### `codex exec` は stdin を読む（ハーネスから起動すると前景でも止まる）

`codex exec` はプロンプトを位置引数で渡しても stdin を読もうとし（`Reading additional input from stdin...`）、ツール経由の Bash では stdin が開いたままなので**前景・背景を問わず**そこで待ち続ける。**ツール経由で起動するときは常に stdin を閉じる**（`< /dev/null`。`resume` も同じ）。

空振りの見分け方（プロセスは生きたまま待ち続けるので、生死では判定できない）:

1. codex のセッションファイルが増えたか（増えていなければレビューは始まっていない）
2. `ps aux` の累積 CPU 時間が経過時間に対してほぼゼロか（応答待ちでも低いので単独では断定しない）
3. 出力ファイルが空のままか

切り分けは、パイプを外して前景で軽いプロンプト（`"1+1 は？"`）を投げて CLI 自体が生きているかを先に見る。

### バックグラウンド実行

パイプを付けたまま背景に回さない（AGENTS.md「バックグラウンドプロセスの後始末」）。codex は `-o <file>` で落とし、整形は読む側で行う。

### パイプ実行時のエラー

`codex exec ... | jq` はCLI側のエラーが jq のパースエラーに隠れる。

1. `2>/dev/null` で stderr を分離する
2. jq がパースエラーを返したら、パイプを外して CLI 単体で再実行しエラーを見る。jq の書式変更やプロンプト簡素化でリトライしない（原因はほぼ CLI 側の出力）
3. 出力が「空」なのはパースエラーとは別物で、上の stdin 待ちを疑う
