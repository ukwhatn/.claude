# UI成果物の基準

ユーザーに見せる画面・モック・ダッシュボード・ギャラリーについて、画面に何を出すか・UI仕様の確かめ方・提示前の完了基準を扱う。

コードの実装原則は `/writing-code`、日本語の文章は `/writing-prose`、出すと決めた文字の書き方（ボタン・見出し・入力欄の説明・エラー・用字用語）は `/writing-ui-text`、ナビゲーション・重ね方・通知・外枠の型の選び方とレイアウトは `/designing-ui` が真実源。PJに文言ガイドがあればそちらが優先する。

## UI仕様の確かめ方

- UI仕様はFigmaのノードツリーで文言・親子関係・ラベルを確かめる（Dev Mode MCPの `get_design_context`、使えなければRESTのnodes API）。スクリーンショットとローカルの仕様書は俯瞰・Node ID参照の補助で、食い違えばFigmaが正

## 画面上の文字

- **画面上の文字は、読む人がその場で取る行動か、見ている対象の名前だけにする**。要素が何であるかの説明・凡例・注釈をラベルに書かない。説明が必要だと感じるのは、要素の設計か配置が読み手に伝わっていないとき
- **見出し・ボタン・ラベル・凡例に句点を付けない**
- **役割名・ペルソナ名・開発上の呼称をそのまま画面に出さない**（誰向けの画面かは配置と導線で示す）
- 比喩・造語でナビゲーションを表さない。既存プロダクトで使われている語か、その領域の一般的な語を使う
- 文言を改めるときは、改定前より良いという判断を規則の名前で言える状態にする

## 提示前の完了基準

次を全て満たしてから見せる。満たせないものが残る場合は、どれが未完成かを提示時に明示する。

- [ ] 画面を設計する前に、**誰がいつ何のためにその画面を見るか**を言葉にした（見る人が決まっていない画面は要素の取捨ができない）
- [ ] プレースホルダ・ダミーデータ・押しても動かない要素が残っていない
- [ ] 画面上の全テキストを列挙し、1件ずつ「実運用でこの語が画面に出ていて成立するか」を判定した。落ちた語は消すか置き換えた
- [ ] **画面の裏側（実行トリガー・データの保存先・更新頻度）を画面と同時に説明できる**。見た目だけ先に見せない
- [ ] 想定する表示環境（モバイル / デスクトップ）で、ローカルで動かして確かめ、スクリーンショットを撮った（PRに貼る手段は `context/github-cli-notes.md`「画像・動画の添付」。いつ貼るかはAGENTS.md「進め方の既定」と `/create-draft-pr`）

## 中間報告と最終提示を区別する

- **中間報告なら、中間だと明示し、何が未確定かを列挙する**
- 最終提示として出すものは、上の完了基準を満たしていること。満たさないまま出すと、要求水準の議論ではなく作り直しの往復になる
- 方向性そのものへの否定が続いたときは、文言やレイアウトの個別修正で対応しない。要件から組み直す（`/grilling` で前提を洗い直す）
