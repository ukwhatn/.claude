# UI 成果物の基準

Read when: ユーザーに見せる画面・モック・ダッシュボード・ギャラリーを作る前、UI文言（ラベル・ボタン・見出し・空状態・エラー文）を書く・書き換える前。

コードの実装原則は `/writing-code`、日本語の文章は `/ukwhatn-writing` が真実源。本ファイルは**画面に出る文字とレイアウト**だけを扱う。

## 画面上の文字

- **画面上の文字は、読む人がその場で取る行動か、見ている対象の名前だけにする**。要素が何であるかの説明・凡例・注釈をラベルに書かない。説明が必要だと感じたら、それは要素の設計か配置が伝わっていないサイン
- **見出し・ボタン・ラベル・凡例に句点を付けない**
- **役割名・ペルソナ名・開発上の呼称をそのまま画面に出さない**（誰向けの画面かは配置と導線で示す）
- **提示前に画面上の全テキストを列挙し、1件ずつ「実運用でこの語が画面に出ていて成立するか」を判定する**。判定に落ちた語は消すか置き換える
- 比喩・造語でナビゲーションを表さない。既存プロダクトで使われている語か、その領域の一般的な語を使う
- **UI文言の「改善」を提案するときは、その領域の実例・スタイルガイドを調査してから出す**。改定前より良いという判断を根拠なしに置かない

## レイアウト

- **既存の同種画面か、参照するデザインガイドの型を先に決めてから要素を置く**。型を決めずに要素を足し続けると、あとから文言だけ直しても読みにくさは消えない
- 情報量の多い一覧・比較はサイドバー付きの多カラムを既定とする。単一カラムに詰めて縦に伸ばさない
- 詳細をその場で開く導線（サイドビュー・モーダル）を使う場合、開いた先が読める幅・高さを持つことを確認してから提示する

## 提示前の完了基準

次を全て満たしてから見せる。満たせないものが残る場合は、**どれが未完成かを提示時に明示する**。

- [ ] 画面を設計する前に、**誰がいつ何のためにその画面を見るか**を言葉にした（見る人が決まっていない画面は要素の取捨ができない）
- [ ] プレースホルダ・ダミーデータ・押しても動かない要素が残っていない
- [ ] 全テキストの列挙と判定が済んでいる（上記「画面上の文字」）
- [ ] **画面の裏側（実行トリガー・データの保存先・更新頻度）を画面と同時に説明できる**。見た目だけ先に見せない
- [ ] 想定する表示環境（モバイル / デスクトップ）で確認した

## 中間報告と最終提示を区別する

- **中間報告なら、中間だと明示し、何が未確定かを列挙する**
- 最終提示として出すものは、上の完了基準を満たしていること。満たさないまま出すと、要求水準の議論ではなく作り直しの往復になる
- 方向性そのものへの否定が続いたときは、文言やレイアウトの個別修正で追わない。要件から組み直す（`/grilling` で前提を洗い直す）
