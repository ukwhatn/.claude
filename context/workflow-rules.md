# 作業ルール詳細（Phase 0-5）

Read when: AGENTS.md「作業フロー」の Phase 0-5 適用条件に該当したとき。適用条件・外部レビューの発火条件・計画の既定値・完了報告の型は AGENTS.md が真実源で、本ファイルは各 Phase の手順と計画書の書き方だけを扱う。

## Phase 0: 準備

1. PJ CLAUDE.md の `MEMORY_DIR` を確認（未定義なら `.local/`）
2. メモリディレクトリを決める: `ls ${MEMORY_DIR}/memory/` で同一コンテキスト（同じ機能・同じバグ・同じ PJ の継続）のディレクトリを探し、あれば再利用する。無ければ `${MEMORY_DIR}/memory/YYMMDD_<context_name>/` を新規作成する（形式: `context/memory-file-formats.md`）
3. 05_log.md の冒頭にメモリディレクトリの絶対パスを書く
4. `/findmem` で過去タスク・issue を検索する（変更対象ファイルが見えたらそのパスでも実行する）

## Phase 1: 調査

1. 過去タスク・issue: `/findmem` のヒットを開いて読む。issue を解決するタスクなら該当 issue を必ず読む
2. 既存コードと議論経緯: 対象チケット・PR のスレッドとコメントを決着まで読む（解決済みコメント・構造化フィールドを含む）
3. 公式仕様: 外部ライブラリ・SDK・ランタイムに依存する部分は context7 / 公式 docs で確認する。エラー修正で最初の修正が効かなければ `/systematic-debugging` に従う
4. 実装方針: 複数選択肢があれば pros / cons を整理し、選択理由を 99_history.md に残す

## Phase 2: 計画

計画は Task ごとに「調査 → 計画 → 実行 → レビュー」の 4 ステップで書く（テンプレート: `context/memory-file-formats.md`「30_plan.md」）。

- **計画が規定する成果物・手順も一次ソース確認の対象**: ドキュメント・スキーマ等の形式を計画に書く前に、その形式が PJ でどう扱われているか（生成物か手書きか・CI 検査・既存スクリプト）を確認する
- **計画書には今回やることのみを書く**。「スコープ外」「変更しない」の列挙はしない（PR テンプレート等でフォーマットが規定するセクションは対象外）
- **計画書には計画だけを置く**。調査・実測の生データと導出過程は `20_survey.md`、レビュー指摘と対応の履歴は `80_review.md`、対外共有文の草案は別成果物へ出し、計画書からは結論だけを引く。載せるのは、実装セッションが実装するために読む情報と、ユーザーが判断するために読む情報だけ
- **レビュー対応での追記は、実装に必要か・ユーザーの判断に必要かで残すかを決める**。レビューは指摘を出す方向にしか働かないため、ラウンドごとに計画書が単調増加していないかを確認する
- 計画には具体的な行動・判断基準を書き、「検討」「場合によっては」「必要に応じて」等の曖昧語を残さない

## Phase 3: 実装

### 実装開始前ゲート

1. **計画書を作成したなら、ユーザーが着手を承認していることを確認する**。外部レビューの通過は承認ではない。ユーザーが着手までを含めて自律実行を委任している場合は満たす
2. コミットを作る場合は、直コミット可否を AGENTS.md「コミット・ブランチ・PR」の手順で確認する
3. 計画からの方針変更・スコープ変更は着手前にユーザーに確認する

### 実装

- 委譲の要否は `context/tool-claude-code.md`「委譲判断」、経路・指示書・結果の回収は `context/herdr-delegation.md` に従う。並列で委譲する場合、各担当のファイルを起動前にリストアップし、複数領域が集約された共有ファイル（ルーティングの集約・`migrations/`・スキーマ定義）は担当を分離するか順次実行にする
- 実装前に同類の既存画面・Usecase を特定してパターン（セキュリティ・UI / UX・依存サービスの過不足）を踏襲する
- 品質チェック（format / lint / typecheck）はコミット前に実行する。コミットは意味的に独立した単位で作る

## Phase 4: 品質確認

- PJ CLAUDE.md に記載のコマンドで lint / format / typecheck / test を実行する
- **集約ブランチの通しレビュー**: epic ブランチ・スタック PR に複数の PR を積んだ場合、集約後の差分を通しで 1 回レビューする（サブ PR ごとの承認は集約後の整合性・PR 間の相互作用を保証しない）。承認コメントが条件付き（「〜のレビューを受けてから」）なら、その条件の消化を確認してからマージする
- 実装の外部レビュー（発火条件は AGENTS.md）の手順・打ち切り条件は `context/agent-cli-guide.md` に従う

## Phase 5: 完了報告

型は AGENTS.md「作業フロー」の完了報告。

## 記録

- 05_log.md に書くのは、メモリディレクトリの絶対パス・委譲の起動記録（agent 名・tab_id）・ユーザー裁定・スキップしたレビュー指摘とその理由だけ。やり取りの複写はしない（transcript と重複する）
- 「後回し」「実装しない」判断は、依存待ち・情報不足・明確なスコープ外の場合のみ許容し、`99_history.md` に判断理由・代替案・再開条件を記録する
