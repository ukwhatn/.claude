# 作業ルール詳細

## 適用範囲

**このフレームワーク（Phase 0-5）は複雑タスク向け。** 複雑タスクの判定条件は `CLAUDE.md`（実体 `AGENTS.md`）「作業フロー」の4条件（変更対象ファイルが3つ以上 / 調査と実装の混在 / ユーザーが「大規模」「複数日」「段階的に」等の語を使った / 途中で訂正・やり直しの指示を受けた）を真実源とする。

- **skipしてよい**: 上記4条件のいずれにも該当しないタスク（1ファイルの軽微な修正、既知の単純なバグ修正、文書の typo 修正等）
- **判断に迷う場合**: Phase 1（調査）と Phase 2（計画）だけは実施し、Phase 3 以降は規模に応じて省略

## Phase 0: 準備

1. PJ CLAUDE.mdの`MEMORY_DIR`を確認（未定義なら`.local/`）
2. **システムプロンプトの`Today's date`から日付を取得**（例示をコピーしない）
3. メモリディレクトリの決定（新規作成 or 既存再利用）
   - **既存ディレクトリ検索**: `ls ${MEMORY_DIR}/memory/` で同一コンテキスト（同じ機能・プロジェクト）のディレクトリを探す
   - **既存あり → 再利用**: そのディレクトリを使用し、05_log.mdに新しい日付セクションを追記
   - **既存なし → 新規作成**: `${MEMORY_DIR}/memory/YYMMDD_<context_name>/` を作成（YYMMDDは最初の作成日）
   - **判断基準**: 同じ機能開発・同じバグ修正・同じプロジェクトの継続作業は同一コンテキスト。独立した別タスクは新規作成
   - **セッションも同様**: 同一タスクの進行中セッションがあればresume/継続を優先し、新セッションの乱立を避ける（タイトル表記揺れによる分裂は再開ごとの再Readコストを生む）
4. global gitignoreで`.local/`は除外済みのためコミット不要
5. **05_log.mdを初期化し、ユーザーからの最初の指示を記録**
6. **関連する過去タスク・issueを検索**（詳細は1.0参照）
7. **タスク管理機構でタスクを作成し、依存関係を設定**（Claude Code: TaskCreate、Codex: plan）
8. （Claude Code）委譲する場合は `context/tool-claude-code.md`「委譲判断」で手法を確定する

## Phase 1: 調査（最重要）

**IMPORTANT**: 調査中の発見・試行錯誤は逐次05_log.mdに記録すること（調査完了後ではなく、調査中に）

### 1.0 過去タスク・issueの参照

現在のタスクに関連する過去の情報を検索し、参照する:

1. **`/findmem <キーワード>` スキルを実行し、過去のメモリディレクトリ・issueを横断検索する**（`ls`/`grep`の直接実行はしない。スキル発火ルール「該当するスキルが存在する場合は直接ツールを呼び出さない」を参照）

2. **変更対象ファイルが見えたら、そのパス・ファイル名でも `/findmem` を実行する**（キーワード検索とは別に実施）。issueは対象ファイルを本文に持つため、タスクのキーワードで外してもパスなら当たる。**ヒットしたファイルは開いて読む**（ファイル名だけで無関係と判断しない）

3. **関連する過去タスクのログを確認**
   - 関連しそうなディレクトリの`05_log.md`を読む
   - 過去の調査結果、決定事項、発生した問題を把握

4. **関連issueの内容を確認**
   - 現在のタスクに関連するissueがあれば読む
   - issueを解決するタスクなら、該当issueを必ず読む

5. **参照結果を05_log.mdに記録**

**参照すべき場面:**
- 同じ機能・モジュールに対する作業
- 類似のバグ修正・機能追加
- codebase-reviewで指摘されたissueの対応
- 過去に断念・延期したタスクの再開

### 1.1 既存コードベースの調査
- 関連コードを特定・読解
- 設計パターン、命名規則、ディレクトリ構成を把握
- 変更の影響範囲を特定
- **→ 発見した内容を05_log.mdに記録**

### 1.2 公式仕様・ベストプラクティスの調査
- **CRITICAL**: context7またはWebSearchで対象技術の公式仕様を調査すること（必須）
- 正しい仕様・ベストプラクティスを把握するまで調査を継続すること
- **エラー修正時**: エラーメッセージの原因を公式ドキュメントで特定してから修正に着手すること。推測で修正を試みることを禁止する。バグ・エラー・テスト失敗の修正は `/systematic-debugging` スキルの4フェーズに従う
- 調査で得た仕様情報は、修正計画の根拠として明示的に記録すること
- **→ 参照結果を05_log.mdに記録**

### 1.3 実装方針の決定
- 複数選択肢がある場合はpros/consを整理
- 既存コードとの整合性を最優先
- **→ 選択理由を05_log.mdに記録**

## Phase 2: 計画

4ステップ構造でタスクを作成:

```
### Task N: <タスク名>
**変更対象ファイル:** <パス>

#### 1. 調査
- [ ] 確認すべき既存コード
- [ ] 参照すべき外部情報

#### 2. 計画
- [ ] 詳細な実装手順
- [ ] 依存関係の確認

#### 3. 実行
- [ ] 実装内容
- [ ] コミット: `<メッセージ>`

#### 4. レビュー
- [ ] 計画通りか確認
- [ ] 整合性確認
- [ ] 型チェック・lint確認
```

### 計画の既定値と成果物形式（IMPORTANT）

- **計画の既定値は PJ の運用実績から取る**: 計画を立てる前に、同 PJ でユーザーが過去に覆した・修正した判断を確認する（99_history / 05_log / PJ CLAUDE.md）。覆された判断は覆された側を新しい既定にする。一般的ベストプラクティスや外部レビュアーの推奨が過去の裁定と食い違うときは裁定側が勝ち、裁定を覆したい場合はユーザー確認事項として扱う（AGENTS.md「ユーザーへの質問」）
- **計画が規定する成果物・手順も一次ソース確認の対象**: ドキュメント・仕様ファイル・スキーマ等の形式を計画に書く前に、その形式が PJ でどう扱われているか（生成物か手書きか・CI 検査・既存スクリプトの有無）を確認する。修正対象コードだけでなく、計画が生む全ての成果物に適用する

### 実装計画書の記載範囲（IMPORTANT）

実装計画書（30_plan.md等）には**今回やることのみ**を記載する。「スコープ外」「変更しない」「含まないもの」の列挙はしない。やらない判断の記録が必要な場合は99_history.mdに記録する（理由・代替案・再開条件）。
**計画書には計画だけを置く。** 次のものは計画書に混ぜず、既定のファイルに置いて計画書からは結論だけを引く: 調査・実測の生データと導出過程（`20_survey.md`）/ レビュー指摘と対応の履歴・版間の変更点（`80_review.md`）/ 対外共有文・回答文の草案（成果物として別に提示する）。計画書に載せるのは、実装セッションが実装するために読む情報と、ユーザーが判断するために読む情報だけ。

**レビュー対応での追記は、実装に必要か・ユーザーの判断に必要かで残すかを決める。** レビュアーを納得させるための根拠は `20_survey.md` / `80_review.md` に置き、計画書からは結論だけを引く。レビューは指摘を出す方向にしか働かないため、ラウンドごとに計画書が単調増加していないかを確認する。

※これは計画書の書き方のルールであり、スコープの縮小判断自体にユーザー確認が必要である点（`CLAUDE.md`「ユーザーへの質問」の確認必須カテゴリ参照）は変わらない。PRテンプレートの「やらなかったこと」等、フォーマットで規定されたセクションは対象外。

### 計画の外部レビュー（必須）

**計画書を作成したら、実装着手前に必ず外部レビューを通す。** 変更の可逆性・規模・トリガー条件の該当有無を判断材料にしない（Phase 0-5 を適用する時点で対象。skip 判定は「適用範囲」の4条件だけで行う）。

指摘が Action Required ゼロになるまでループする（安全上限5R）。実行前に `context/agent-cli-guide.md` を必ずRead（CLI選択・コマンド形式・レビューループの規定）。レビュー結果と対応は計画書に記録する。

省略できるのは外部CLIが使えない環境のときだけで、その場合は計画書と完了報告の双方に省略した旨を明記する（Claude 自身を reviewer role で spawn する自己検証で代替しない）。

## Phase 3: 実装

### 実装開始前ゲート（CRITICAL）

実装に着手する前に以下4点を確認する（過去の頻出違反の再発防止）:

1. **計画書を作成したなら、ユーザーが着手を承認していることを確認する**。外部レビューの通過は承認ではない（レビューは成果物の欠陥を見るものであり、着手可否の判断ではない）。承認が確認できないなら、計画を提示して可否を問う。何を承認と数えるかは AGENTS.md「ユーザーへの質問」に従う。ユーザーが着手までを含めて自律実行を委任している場合は本項を満たす
2. **コミットを作成する場合は（非コードのdocs等でも）**、そのリポジトリでの直コミット可否を後述「直コミット可否の判定」で確認する。チーム開発リポジトリでは作業ブランチ（feature/*等）を用い、main/develop直コミットは禁止。対象外は**コミットしない作業のみ**（メモリディレクトリ編集・読み取り専用調査）
3. **品質チェック・破壊的操作・副作用の大きいコマンド**はPJ規定（PJ CLAUDE.mdの規定コマンド）に従い、規定と異なるコマンドを独断で使わない（例: `tsc`直叩きでなく`npm run tsc`）。調査用の読み取り系コマンドは対象外
4. 計画からの方針変更・スコープ変更は着手前にユーザーに確認する（Claude Code: AskUserQuestion）

### 直コミット可否の判定

PJ `CLAUDE.md` / `CLAUDE.local.md` に判定結果の記載があればそれに従う。記載が無ければ次の事実を集め、**このリポジトリで自分が実際どう運用してきたか**を読み取って判断する（閾値で機械的に決めない）。判断後は**結果を永続化してから**コミットする（次回以降の再判定を省くため）。

**1. ブランチ保護 / ruleset を確認する**（履歴からの推測より確実。`pull_request` ルールがあれば直コミットは物理的に不可能）:

```bash
BASE=$(git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null || echo origin/main)
gh api "repos/$(gh repo view --json nameWithOwner -q .nameWithOwner)/rules/branches/${BASE#origin/}"
```

- `pull_request` を含むルールが返る → **PR運用確定**。作業ブランチ必須（履歴を見るまでもない）
- `[]` が返る、または `gh` が使えない → 2へ

**2. 履歴を集める**（`$BASE` を必ず明示する。省略すると `HEAD` が対象になり、**worktree 内では feature branch の履歴を「baseの履歴」として誤読する**）:

```bash
MY=$(git config user.email)
git log "$BASE" --format='%ae' | sort | uniq -c | sort -rn | head    # 誰が書いているか
git log "$BASE" --first-parent --no-merges --author="$MY" --format='%h %ce %s' | head -20
                                                                     # 自分のcommitがbaseに直接載っているか
git log "$BASE" --first-parent -20 --format='%h %ce %s'              # 直近の変更がどう入っているか
```

読み取り方:

- 自分のコミットが main に直接並び、PR / merge の痕跡がほとんどない → **直コミット運用**。main 直コミット可
- 自分のコミットが merge commit 経由、または squash（committer が `noreply@github.com`）でしか入っていない → **PR運用**。作業ブランチ必須
- 他の書き手がPRを使っていても、**自分がほぼ直コミットしているなら直コミット運用として扱う**（判定するのは自分の運用実態であって、リポジトリの人数ではない）
- 過去と直近で運用が変わっている場合は**直近を優先する**（PR運用へ移行済みのrepoで、過去の直コミットを根拠にしない）
- 直コミットとPRが拮抗していて読み取れない場合は、推測せずユーザーに確認する（Claude Code: AskUserQuestion）
- **永続化した判定は陳腐化する**。記載に従う場合も、記載と直近履歴が食い違うとき（PR運用へ移行した等）は再判定して記載を更新する

判定結果の永続化先:

| 書き手 | 永続化先 | 理由 |
|---|---|---|
| 自分のみ | PJ `CLAUDE.md` | 自分しか使わないため、コミットされて問題ない |
| 他にもいる | `CLAUDE.local.md` | 他メンバーの運用に影響させない（git管理外） |

記載例:

```markdown
## コミット運用
全コミットが自分の直コミットで、PR/mergeの痕跡なし（判定日: YYYY-MM-DD）。main への直コミットを許容する。
```

委譲の要否と構成は `context/tool-claude-code.md`（Claude Code）／`context/tool-codex.md`（Codex）の基準で決める。各タスクを「調査→計画→実行→レビュー」で進める。

### 委譲する場合

lead は依存関係に基づく実行順序の管理、spawn とタスク割り当て、完了報告の統合、05_log.md への進捗記録を担う。ただし方針判断を伴う中核ファイルなど、lead が直接実装した方が明らかに効率的なものは自身で編集してよい（「leadは絶対にコードを書かない」という強制ルールではない）。

並列で spawn する場合、各 agent の担当ファイルを spawn 前にリストアップする。複数領域が集約された共有ファイル（`routes/*.ts` の集約・`migrations/`・スキーマ定義等）は分担境界が曖昧になるため、担当を分離するか順次実行に切り替える。

### 共通の実装品質ルール

- **プロダクションコードの新規実装・修正・機能追加・リファクタでは常に `/writing-code` スキルの原則（設計語彙・テスタビリティ・シーム限定TDD・コメント規約）に従う**（トリビアルな1行修正・設定ファイルのみの変更は本スキルの「適用外」条件に従う。スキル側の完了基準が軽微な変更では自然に短時間で通過するため、規模で発火要否を自己判断しない）
- **実装前に同類の既存画面・Usecaseを特定し、パターンを踏襲する**
  - セキュリティパターン（サニタイズ、認可チェック等）
  - UI/UXパターン（hook使用、エラーハンドリング、レイアウト構成）
  - 依存サービスの過不足（既存の同類Usecaseと比較）
  - 重複コードがあれば共通化を検討
- **品質チェック（format/lint/typecheck）はコミット前に実行**
  - エラーがあれば即座に修正
- **コミットは意味的に独立した単位で作成**
  - git-cz形式
  - 大きな変更を溜め込まない
- コメント配分: How=コード自体、What=テストコード、Why=コミットログ、**コードコメントはWhy notのみ**（詳細・具体例は`/writing-code`参照。本行を満たしただけで発火済みとみなさない）
- docstring/jsdoc: 既存形式に従う

## Phase 4: 品質確認

### 自動チェック
PJ CLAUDE.mdに記載のコマンドで実行:
- lint
- format
- typecheck
- test

### 検証機構（PJ責務）

検証機構の供給は最も効果が高い。PJ側で以下を整備すること:

- **テストコード**: 主要ロジックにユニットテスト・統合テスト
- **E2Eテスト**: Playwright等によるフロントエンドE2E
- **スクリーンショット供給**: UI変更時は変更前後のスクショを残す
- **期待出力**: 主要コマンド・APIの期待出力を `tests/fixtures/` 等に保存
- **Stop Hook**: settings.json で `Stop` フックにテスト自動実行を登録（PJ独自に判断）

詳細はPJ CLAUDE.mdの「検証方針」セクションに記載すること。

### 実装品質チェック
- **セキュリティパターン適用**: サニタイズ・認可チェック等が既存パターンに沿っているか
- **既存パターン踏襲**: 同類の既存画面・Usecaseと比較し、パターンの乖離がないか
- **重複コード**: 2箇所以上に同じロジックが存在する場合、共通化を検討したか
- **権限変更の網羅性**: Procedure変更時、影響を受ける全routerを確認したか
- **ドキュメント同期**: 変更によりCLAUDE.md・context/・READMEの記述がoutdatedになっていないか確認し、必要なら同じPRで追随する
- **集約ブランチの通しレビュー**: epic ブランチ・スタックPRに複数のPRを積んだ場合、集約後の差分を通しで1回レビューする（サブPRごとの承認は、集約後の整合性・同一要件の実装揺れ・PR間の相互作用を保証しない）。承認コメントが条件付き（「〜のレビューを受けてから」等）の場合は、その条件の消化を確認してからマージする

### 外部レビュー（任意）

トリガー条件は AGENTS.md「作業フロー」の外部レビュー節と共通。実装段階では以下の手順でレビューする:
1. 指摘があればSeverityに基づいて判断:
   - Action Required → 修正
   - Recommended/Minor → 必要性に基づいて修正/スキップ
2. 修正後、`--resume` で再レビュー
3. 打ち切り条件: Action Required = 0 / 同一指摘2R連続 / 安全上限5R

**外部CLIが使えない環境では、外部レビューを省略し、その旨を完了報告に明記する。Claude 自身を reviewer role で spawn する自己検証で代替しない**（外部レビューの価値は別ベンダー LLM の bias 独立性にある）。

**実行前に必ずRead:**
- `context/agent-cli-guide.md`（CLI 選択・コマンド形式・Claude fallback pattern・レビューループの規定）
- `context/code-review-checklist.md`（汎用の実装 anti-pattern チェックリスト。BOLA/BOPLA / CSRF 登録漏れ / falsy check / Drizzle encoder / LLM injection 等を具体レベルで列挙）

## Phase 5: 完了報告

1. 実装内容の概要
2. 自律決定した事項
3. 作成したブランチ名
4. 残存する課題
5. 実行した検証と、その検証が担保していない範囲（機械検証（lint / スキーマ検証 / CI）の通過を、内容品質の担保として報告しない）

## 長時間タスクの区切り運用

Phase完了・ユーザー承認待ち・compaction接近などの区切りでは、`/handoff` スキルで50_handoff.mdを自律更新する（ユーザーの明示指示を待たない。過去の長時間タスクで区切りごとに手動指示が反復されたため）。

## ユーザーへの質問

真実源は `CLAUDE.md`（実体 `AGENTS.md`）「ユーザーへの質問」。確認必須カテゴリ・質問前の詳細説明・複数question を1回に詰め込まない規定はそちらを参照する。

## 守る項目（本ファイル固有）

`CLAUDE.md`（実体 `AGENTS.md`）の「緩和しない安全項目」「スキル発動ルール」「規約遵守」「worktree 運用ルール」「ユーザーへの質問」「コミット・ブランチ・PR」に規定がある項目は、そちらを真実源とする。以下は本ファイル固有の項目。

- シークレット（APIキー・トークン等）は環境変数・ファイル経由で渡す。チャット出力・コマンドライン引数に平文で含めない（識別が必要な場合はプレフィックスのみ表示する）
- 複雑タスクでは Phase 1（調査）を経てから実装方針を決める。外部情報（context7 / Web検索）と既存コードの確認を根拠として 05_log.md に残す
- 複雑タスクでは Phase 2 の4ステップ構造（調査→計画→実行→レビュー）でタスクを組む
- 計画には具体的な行動・判断基準を書く（「検討」「場合によっては」「必要に応じて」等の曖昧語が残っていないか、計画完了前に見直す）
- 品質チェック（lint/format/typecheck/test）はコミット前に実行する
- PRテンプレートの項目は該当なしの場合も保持し、省略が必要ならユーザーに確認する
- 問題の原因を報告する前に、自分の直前の操作が原因である可能性をログ・差分等の一次情報で確認する
- **多バイト文字列の集計に `sort | uniq -c` を使わない**（ロケール依存の照合により異なる文字列が誤って統合され、カテゴリ数が実際より少なく出る）。集計は Python 等の明示的なカウントで行い、**チャンク別の集計と全体集計が矛盾しないか突き合わせて検証する**
- メモリファイルの編集はファイル編集ツールで行う（Claude Code: Edit/Write、Codex: apply_patch。詳細: @context/memory-file-formats.md「ファイル運用ルール」）
- PJ既存パターンからの逸脱可否の具体例（原則は AGENTS.md「規約遵守」参照）: 全テーブルがDrizzle管理なのに生SQLを使う、全サービスがDomainResultを返すのにtry-catchなしにする、等はユーザーに確認する

## 「後回し」「実装しない」判断時のルール

- 完全に禁止ではないが、判断には理由と記録が必須
- `99_history.md`に以下を記録:
  - 判断理由
  - 代替案（あれば）
  - 再開条件（いつ実装すべきか）
- 依存待ち・情報不足・明確なスコープ外の場合のみ許容
