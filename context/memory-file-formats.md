# メモリファイル形式

Read when: メモリディレクトリを作る前・05_log / issue ファイルを書く前。場所（`${MEMORY_DIR}/memory/YYMMDD_<context_name>/`、issue は `${MEMORY_DIR}/issues/`）と絶対パス固定・編集ツールの規則は AGENTS.md「メモリ・issue ディレクトリ」が真実源。

- **YYMMDD** はディレクトリを最初に作成した日付（システムプロンプトの日付を使う）。context_name は機能・PJ を識別する短い名前
- 同一コンテキスト（同じ機能開発・同じバグ修正・同じ PJ の継続作業）は既存ディレクトリを再利用し、新規作成しない
- 頻繁に参照・編集する working memory ファイル（00_spec.md 等）が 300 行を超えたら分割する（例: `00_spec.md` → `00a_登録.md` / `00b_昇格.md`）。分割時は親ファイルに目次（各分割ファイルの 1 行要約）を残す。完成済みで参照頻度の低い成果物は機械的に分割しない

## issues/ の構成とファイル形式

- **未解決だけを `issues/` 直下に置く。決着したら `resolved/` へ移す。削除しない**（`.local/` は git 管理外で復元手段が無い）
- 各ファイルは H1 タイトルの直後に状態を持つ。状態欄の無い issue は修正されても見た目が変わらず、バックログ全体を 1 件ずつコードと突き合わせ直すことになる:

```markdown
# [<優先度> / <観点>] <タイトル>

**状態**: **OPEN**
```

| 値 | 意味 | 置き場所 |
|---|---|---|
| `OPEN` | 未対応 | `issues/` |
| `FIXED` | 修正済み | `resolved/` |
| `受容` | リスクを受容して対応しない判断をした | `resolved/` |
| `決着済み` | 複数論点を個別に処理し終えた | `resolved/` |
| `統合済み` | 重複起票のため他ファイルへ統合した | `resolved/` |

状態を変えるときは判断の根拠を一緒に書く（無いと次の再検証で同じ調査をやり直す）:

| 変更 | 一緒に書く |
|---|---|
| 対応した | `**対応状況**: <何をしたか>`（PR 番号があれば添える） |
| 受容した | 受容理由と、再評価が必要になる条件 |
| 統合した | 統合元に `**統合先**: <ファイル名>`、統合先に統合元の固有論点 |
| 再検証した | 確認した一次情報（`ファイル:行`）。判定だけ書き換えない |

同一欠陥が複数ファイルに分かれて起票されることがある（レビューの担当領域が別だと独立に検出される）。見つけたら 1 件へ統合し、統合元の固有論点（別の主眼・別の対策案・敵対的検証での訂正）を統合先へ引き継いでから移す。タイトルが違っても、根拠のファイル・行が重なれば同一欠陥を疑う。

## メモリディレクトリのファイル

| ファイル | 用途 | 作成タイミング |
|---------|------|--------------|
| 00_spec.md | 機能要求・要件定義 | タスク開始時 |
| 05_log.md | ユーザー指示とレスポンス・実施内容のログ | タスク開始時（随時追記） |
| 10_task.md | タスク一覧 | 要件定義後 |
| 20_survey.md | 調査結果 | 調査完了後 |
| 30_plan.md | 実装計画 | 計画立案後 |
| 40_progress.md | 実装進捗 | 実装中（随時更新） |
| 50_handoff.md | 引き継ぎスナップショット | 区切りで `/handoff` |
| 80_review.md | レビュー結果 | レビュー実施後 |
| 90_pr.md | PR 内容 | PR 作成時 |
| 99_history.md | 意思決定ログ | 随時 |

### 99_history.md

判断・理由・代替案・再開条件を記録する。確認必須カテゴリ（AGENTS.md「ユーザーへの質問」）の決着は**決着の主体**（ユーザー裁定 / 事前委任に基づく自律決定）を明記する。主体が書かれていない項目は未決として扱う。「後回し」「実装しない」判断も、理由・代替案・再開条件をここに書く。

### 05_log.md

ユーザーからの指示とそれに対するレスポンス・実施内容を逐一記録する。冒頭にメモリディレクトリの絶対パスを書く。

```markdown
# 作業ログ

メモリディレクトリ絶対パス: `<絶対パス>`

## YYYY-MM-DD HH:MM - 初期指示

**ユーザー指示:**
> [最初の作業指示]

**レスポンス:**
- [実施したこと]

---

## YYYY-MM-DD HH:MM - 追加指示

**ユーザー指示:**
> [追加の指示]

**レスポンス:**
- [実施したこと]

---
```

```markdown
# 機能要求

## 概要
[1-2文で記述]

## 背景・目的

## 機能要件
### 必須要件
- [ ] 要件1

### 任意要件
- [ ] 要件1

## 非機能要件
- パフォーマンス:
- セキュリティ:

## 制約事項
```

### 30_plan.md

```markdown
# 実装計画

## 概要
[アプローチの概要]

## タスク一覧

### Task 1: <タスク名>
**変更対象:** <パス>

#### 1. 調査
- [ ] 確認すべき既存コード・参照すべき外部情報

#### 2. 計画
- [ ] 詳細な実装手順・依存関係の確認

#### 3. 実行
- [ ] 実装内容
- [ ] コミット: `<メッセージ>`

#### 4. レビュー
- [ ] 計画通りか・整合性・型チェック / lint

## レビュー結果
[Action Required と対応の結論のみ。指摘の全文・版間の変更点は 80_review.md へ]

## リスク・懸念事項
| リスク | 影響度 | 対策 |
|-------|-------|------|
```
