# Claude Code 固有指示

AGENTS.md から @import され、Claude Code では毎セッション常駐する。Codex 等の他エージェントはこのファイルを読む必要はない（対応表は context/tool-codex.md 参照）。

## 自律実行の前提

- 初回プロンプトに Goal / Constraints / Acceptance criteria を整理して渡されたら、途中介入を最小化して自律的に進める
- ペアプログラミング型の細かい指示・「こまめに」「逐一」等の過度な強制は避ける
- 検証機構（テスト・スクリーンショット・期待出力）の供給は最も効果が高い。PJ側で整備すること（@context/workflow-rules.md「検証機構」参照）
- **自己検証を促す指示は書かない**（「最終検証ステップを含める」「応答前に再検証する」「サブエージェントを使って検証する」等）。自己検証と自己修正は指示がなくても行われるため、重複はコストだけを増やす
- effort は既定の `high` から始め、評価に基づいて調整する。品質が保てる範囲では `low`/`medium` をコストとレイテンシの制御手段として使い、要求の厳しいコーディング・エージェント作業では `xhigh` に上げる。旧世代から引き継いだ既定値はそのまま使わず再評価する
- 委譲の要否と構成（体数・相互通信・共有タスクリスト）は後述「委譲判断」で決める

## 委譲判断

leadは計画・タスク分解・結果の統合を担う。**委譲した作業には自分で手を付けず、結果が返るまで同じ対象を触らない**（ユーザー指示による委譲でも自己判断の委譲でも同じ。spawn 直後の振る舞いは「spawn 後の実務」）。指示書に書く前提は、確認済みの事実と未確認の推測を分けて書く（推測を事実の顔で渡すと委譲先はそれを検証しない）。

**ユーザーが委譲・オーケストレーション専念を指示した場合、以下の自己判断より優先する**。

**実装フェーズに入る時点で、委譲構成を1行で宣言してから着手する**（担当・担当ファイル・model）。宣言せずに自分で編集を始めない。宣言の時点でユーザーが構成に介入できることが目的であり、宣言そのものが承認ではない。

**実装の既定は委譲**とする。自分で実装するのは、方針判断を伴う中核ファイルと、委譲の準備が実装より重くなる場合に限る（実装は着手前に規模を過小に見積もりやすく、「数回のツール呼び出しで終わる」の自己申告は自分でやる側に倒れる）。

**委譲する**: 真に独立していて並列化できる作業（大量のファイル読み・コードベース横断調査・ログ解析、複数ファイルにまたがる実装）

**委譲しない**:
- 自分が数回のツール呼び出しで終えられる作業、および「小規模タスク」（`context/workflow-rules.md`「適用範囲」の skip 基準）
- 自分の作業の検証・ダブルチェック
- 1体で足りる作業に複数体を使うこと（必要な体数そのものは制限しない）

委譲する場合は次を決める。**「Agent Teams」は下表のうち相互通信と共有タスクリストを使う構成の呼称であり、別の機構ではない**（spawn は同じ `Agent` ツール。セッションに単一の暗黙チームがあり、チームを作る/消す操作は存在せず `team_name` は Deprecated/ignored）。

| 決めること | 選び方 |
|---|---|
| 体数 | 独立した作業単位の数に合わせる。担当ファイルが重なるなら分割し直す（同一ファイルを複数体に編集させない） |
| model | **設計判断を含む実装・難所の切り分けは `opus`、パターンが確立した実装と調査は `sonnet`**。壁打ち・対話での検討は `fable`（モデル世代交代時は見直す） |
| 相互通信 | 各体が独立して結論を返せるなら使わない（結果は lead が統合する）。インターフェース調整のように作業中の情報交換が必要なときだけ `name` を付けて `SendMessage` で繋ぐ |
| 共有タスクリスト | 依存関係のあるタスクを順序付ける必要があるときだけ TaskCreate/TaskUpdate で管理する |

ユーザーが「チームで」「Agent Teamsで」等と明示した場合は、相互通信と共有タスクリストを使う構成を採る。

委譲の目的は並列性だけでなく、lead（会話・計画・統合）と実装のモデル階層分離、およびコンテキスト保護（委譲セッションはトークン消費が約半分、compaction 頻度が大幅に下がる）。leadは結論のみを受け取り、**報告は一次情報と突き合わせて検証してから採用する**（Writer/Reviewer分離、@context/claude-customization-guide.md §8）。

## spawn 後の実務（1体でも同じ）

- **spawn したら、そのターンは「<agent名>に委譲した。結果待ち」と1文書いて終える**。完了報告はシステムが次のターンとして配信する。結果待ちで終えるのは委譲の正規の手順であって空転ではない。「何もしていない」状態を埋めるために委譲先と同じ対象（同じファイル・同じ問い）に自分で手を付けると、どちらの結果も採用できなくなる
- idle 通知は通常イベントなので催促しない。**idle 通知が届いたのに期待する最終報告が未着の場合のみ**、報告フォーマットを再掲して送信を依頼する（作業の催促ではなく成果物の回収）
- interrupted（failure）通知は idle と区別する。初回1回だけ状況確認を送り、復帰後は agent 自身の報告を待つ。ユーザーが stop した可能性があるため、復帰可否を lead 判断で決めない
- 並列 spawn 中のコミットは `git add <file>` で対象を選別する（`git add -A` は他 agent が編集中のファイルを巻き込む）
- **裁定を求められたら、判断材料が揃っている限りその場で決める**。保留してよいのは「何を待つのか」と「それが届いたら判断がどう変わるか」を書けるときだけで、書けないなら決める。委譲先が「blocker にしない」と明示した指摘や、既に検証済みの結論を、相手の反応待ちを理由に寝かせない（待ちを既定にすると、後から同じ材料で同じ結論に達するだけで着手が遅れる）
